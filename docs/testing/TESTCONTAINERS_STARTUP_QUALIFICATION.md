## Regression guard and cleanup

`TestcontainersLifecycleTests` in the existing IdentityAccess.Postgres project runs real containers. It requires a running, session-labelled Reaper and inspects Docker to prove removal after ordinary completion, an injected readiness failure after container creation, and cancellation at an invoked running-container wait. The [upstream readiness implementation](https://github.com/testcontainers/testcontainers-dotnet/blob/3e8e1dbdcdcfff0fb916f6f96927b27668f22d0f/src/Testcontainers/Configurations/WaitStrategies/WaitStrategy.cs) races a canceled delay against the canceled readiness task, so documented cancellation can surface as either cancellation or timeout. The regression requires the actual wait to have run and its token to be canceled; it does not accept an unrelated startup failure.

One test intentionally leaves a real container undisposed to exercise Ryuk cleanup independently of fixture disposal. `python3 eng/qualify-testcontainers-startup.py` launches six fresh test processes concurrently without builds, retries or a shared warm Reaper. Each runs all four lifecycle cases. The guard requires four passes in every TRX, observes six distinct actual Reaper sessions, then requires every probe container and those six Reapers to disappear within 60 seconds. It preserves every process transcript and result under a unique ignored artifact directory; Docker assertions never manually delete resources to manufacture a pass. Build the existing IdentityAccess.Postgres test project in Release first.

Requalification triggers: Testcontainers or Docker client graph changes; .NET runtime/SDK changes; Docker/runtime/socket changes; Ryuk image/configuration changes; fixture cleanup changes; recurring parallel initialization failure. Permanent guard: these lifecycle tests in the normal gate; recurring process-boundary guard: the six-process command above on these triggers, followed by affected PostgreSQL tests and the exact normal `./eng/verify.sh`.
