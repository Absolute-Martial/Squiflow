# COM-011 and profile prerequisites: accepted owner decisions

**Status: accepted by the owner on 2026-10-08.** This record closes the remaining COM-011 product and authority choices and the first ADM-018–021 profile contract. It does not qualify the new implementation. The canonical runtime owner is [Order program reference policy](../implementation/ORDER_PROGRAM_REFERENCE_POLICY.md); the profile authority boundary is owned by [Tenant Application Profiles](../architecture/TENANT_APPLICATION_PROFILES_AND_EXTENSIBILITY.md).

## Accepted contract

1. **Reference meaning and validation.** The Order stores one customer-supplied `ExternalProgramReference`, displayed as “Program reference.” It records operator-supplied information and does not verify a purchase order or establish approval/payment. Trim outer Unicode whitespace, map blank to absent, preserve case/internal whitespace, reject Unicode Control runes and malformed UTF-16, and limit the normalized value to 128 Unicode scalar values. Errors never disclose the supplied text.

2. **Policy applicability.** One typed Boolean setting, `RequireReferenceForProgramOrders`, defaults to `false`; `true` requires reference text before commitment for every Order with validated tenant-owned program attribution. Non-program Orders remain optional. There are no per-program exemptions, custom expressions, generic setting bags, additional stage, or workflow engine.

3. **Initial catalog.** The four stable feature IDs are `customers.organizations`, `customers.programs` (depends on organizations), `orders.drafts`, and `orders.program-attribution` (depends on drafts and programs). Every definition is always enabled and nonselectable. This is metadata for the admitted operations; it does not introduce tenant feature toggling, disabling, dormant-grant reactivation, or a Customers dependency for direct Orders. Permission metadata continues to come from the capability-owned Tenancy catalog, and feature selection never grants permission.

4. **Separate authorization owners.** Tenant Web → CoreApi policy view/edit/publish uses `profiles.policy.view`, `profiles.policy.edit`, and `profiles.policy.publish`. These are distinct, explicitly delegated tenant permissions; initial Owner status and Order permissions do not grant them automatically. No Workstation authoring surface is introduced. Private AdminApi separately publishes and activates tenant profiles under `can_publish_tenant_profile` and `can_activate_tenant_profile`, in addition to existing Platform Admin identity, registered-device, private-entry, and authorization checks. Tenant policy publication does not activate a profile; profile activation does not edit a policy.

5. **Immutable policy and profile versions.** Policy edits remain drafts until a current authorized policy publisher publishes an immutable policy revision. The first profile contract is `tenant-profile/v1`; it retains tenant identity, catalog fingerprint and feature selection, the exact published policy revision, publication actor/device/time, and observed authorization revision. Unknown versions, unsupported catalog/selection, inconsistent data, and cross-tenant references fail closed. Expected revisions, caller-scoped semantic idempotency, immutable receipts, and one atomic durable effect govern mutations. Current membership and operation authority are rechecked before replay.

6. **Work pinning.** A new direct Order draft pins the active compatible profile when created; a quotation-origin Order pins the profile at conversion. Later publication or activation applies to new work. Already-pinned drafts retain their profile revision. Successful commitment freezes the reference and exact profile/policy evidence. Reference editing on a quoted draft is metadata-only: it can change the reference, Order revision, and its own history/receipt, but it never changes accepted quotation summary, currency, total, attribution, lines/source facts, origin, or original conversion snapshot.

7. **Legacy draft treatment.** A draft with no profile pin is not implicitly assigned `false`; it fails closed until an authorized Platform Admin explicitly assigns the retained false baseline using compare-and-set on the draft's current Order revision. Selecting the retained legacy baseline is a separate one-time compare-and-set operation on the tenant profile authority revision. The assignment records an immutable actor/device receipt and coordinates with concurrent Order creation. It changes profile-pin authority only; it does not increment the Order revision, rewrite the Order, or alter prior Order receipts. Legacy work is never silently migrated to the new required policy.

8. **Failure and rollback.** Missing, unavailable, or incompatible profile authority fails closed; absence never means optional. A compatible rollback selects a retained profile for new work while preserving historical policy/profile facts and committed business facts. The optional baseline is valid only when durably assigned through the accepted legacy procedure.

## Qualification boundary

The fixed catalog, typed policy/profile authority and persistence, and Order reference consumer subsequently received local qualification under the [implementation receipt](COM_011_IMPLEMENTATION_RECEIPT.md), with the exact normal gate and real PostgreSQL/OpenFGA/host guards. The owner decision and runtime qualification remain separate records. Existing live object-storage/provider blockers remain separate and are not changed by this decision. Product version remains `v0.0.1`.

Requalify when catalog IDs/fingerprint/dependencies, policy meaning or permissions, profile version/evidence, legacy baseline behavior, activation/pinning, failure outcomes, or quoted-Order facts change. This accepted contract does not introduce general feature release channels, experiments, runtime module selection, dynamic forms, arbitrary tenant code, Worker workflow behavior, or a general profile editor.
