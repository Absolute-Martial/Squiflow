# 081 — Design Patterns Cheat Sheet

## A. Identification
- **PDF pages:** `159-161`
- **Original archive pages:** `305-307`
- **Visual-heavy pages:** `159-160`
- **Patterns shown:** Factory, Abstract Factory, Builder, Prototype, Singleton, Chain of Responsibility, Command, Iterator, Observer, State, Strategy, Adapter, Bridge, Composite, Facade, Flyweight, Proxy.
- **Classification:** `KEEP AS DESIGN VOCABULARY / FIT BY CONCRETE PROBLEM`; do not convert the catalog into a class/interface backlog.

## B. Core concept — SOURCE
The source presents classic object-oriented design patterns as reusable structures for recurring design problems. Each panel gives a short intent statement and a UML-like class diagram showing participants and relationships.

## C. Important concepts — SOURCE
- **Factory:** creates objects while allowing subclasses/implementations to determine concrete creation.
- **Abstract Factory:** creates related families of objects without naming concrete classes directly.
- **Builder:** constructs a complex object step by step, separating construction from representation.
- **Prototype:** creates new objects by copying/cloning an existing prototype.
- **Singleton:** restricts a class to one instance with a global access point.
- **Chain of Responsibility:** passes a request along handlers until one processes it or the chain ends.
- **Command:** encapsulates a request as an object, enabling parameterization, queuing, history, or undo-style structures.
- **Iterator:** traverses a collection without exposing its internal representation.
- **Observer:** establishes one-to-many notification when a subject changes.
- **State:** changes behavior according to internal state through state-specific implementations.
- **Strategy:** encapsulates interchangeable algorithms behind one context/contract.
- **Adapter:** translates one interface into another expected by a client.
- **Bridge:** separates an abstraction from its implementation so both can vary independently.
- **Composite:** treats individual objects and object trees uniformly.
- **Facade:** provides a simpler interface over a more complex subsystem.
- **Flyweight:** shares common state among many similar objects to reduce memory use.
- **Proxy:** stands in for another object to control access or add indirection such as lazy loading, logging, or access control.

## D. Diagram / visual explanation
Pages `159-160` are almost entirely diagrams. They show why patterns are structural relationships rather than technology products: factories point clients toward abstract products; builders split construction; chains link handlers; strategies hang interchangeable algorithms off a context; adapters bridge incompatible contracts; composites build trees; proxies interpose a surrogate; observers connect a subject to multiple dependents.

The diagrams are useful as vocabulary, but they are intentionally small and omit real production concerns such as async failure, transactions, distributed calls, cancellation, observability, security and lifecycle ownership.

## E. How it works step by step — INFERENCE
A pattern is useful only after a concrete change/failure pressure appears:
1. identify the changing or coupled responsibility;
2. identify which part should remain stable;
3. introduce the smallest contract/structure that isolates the variation;
4. prove callers depend on the stable semantics rather than provider-specific detail;
5. test replacement/failure semantics, not only type compatibility;
6. remove or avoid the abstraction if it adds indirection without reducing a real cost.

## F. Why it matters
Patterns can make intent easier to communicate and can isolate real volatility. They become harmful when the team uses pattern names as a reason to manufacture classes, interfaces, global state or event chains without a concrete problem.

## G. Trade-offs / limitations — EXTERNAL KNOWLEDGE
- **Singleton** can hide global mutable state, initialization order, test contamination and process-local assumptions. A DI `Singleton` lifetime is not automatically the GoF Singleton pattern and does not make state durable/shared across processes.
- **Observer** can create ordering, reentrancy, lifetime/leak and hidden-coupling problems; distributed events require durability/idempotency beyond an in-memory Observer.
- **Chain of Responsibility** is excellent for middleware-style cross-cutting flow, but handler order becomes part of correctness and business mutation should not be spread unpredictably across handlers.
- **Command** is useful for explicit intent but does not require one class per trivial operation or imply a message broker.
- **State** can clarify real state-machine behavior; it can also overcomplicate small enums/transitions.
- **Strategy** is useful when two or more algorithms/providers genuinely vary. One implementation behind one interface can be pointless ceremony.
- **Adapter** is especially valuable at provider/replacement boundaries, but must preserve failure/cancellation/retry semantics, not only method names.
- **Facade** can become a god-object if it absorbs business decisions rather than simplifying composition.
- **Proxy** can hide an expensive remote/network call behind a local-looking method; remote failure/latency must stay visible.
- **Builder/Abstract Factory/Bridge/Flyweight/Prototype** are niche-to-specific pressures; they should not be introduced only because they exist in the cheat sheet.

## H. Alternatives / comparisons
Patterns can coexist because they address different dimensions. The meaningful comparison is not “which pattern is best?” but whether simple direct code, composition, language/runtime features, framework middleware/DI, or one explicit adapter already solves the concrete problem more clearly.

## I. Real implementation considerations
Before introducing any pattern in SquiFlow, require:
- concrete change/failure pressure;
- named owner and boundary;
- one-sentence reason it improves that boundary;
- test proving the abstraction preserves semantics;
- lifecycle/disposal/concurrency expectations;
- no hidden provider/network cost;
- evidence that the abstraction reduces rather than increases navigation/maintenance burden.

## Implications for the Current Implementation
**What are we actually doing?** The current repository has documented architecture, not application code, so we can only identify **planned/accepted pattern-shaped boundaries**, not claim pattern implementation.

- **Adapter — strong documented fit:** `IObjectStore` / `IBackupTarget` are intentional SquiFlow-facing provider seams. The reason is not “Adapter is a good pattern”; it is that object/backup providers are expected replacement/failure boundaries and provider SDK types must not leak into business contracts.
- **Command — strong semantic fit:** Core API docs distinguish business commands such as `ApproveQuote`, `RefundPayment`, `AdjustInventory` from generic update operations. This protects business intent, idempotency, authorization and concurrency semantics. It does **not** require a command-bus framework.
- **State — domain-specific fit:** quotation/payment/workflow states already exist because transition validity and historical truth matter. Use a richer State-pattern implementation only if state-specific behavior becomes difficult to keep explicit with current domain code.
- **Chain of Responsibility — framework-level fit:** the documented ASP.NET request pipeline is naturally chain-like (correlation → rate/admission → auth → tenant context → resource authorization → domain validation → transaction). The reason is staged cross-cutting responsibility, not pattern purity.
- **Strategy — candidate fit:** transport/provider choices may need replaceable algorithms/implementations, but only where a real boundary has two viable implementations and replacement is valuable.
- **Observer/domain events — carefully scoped:** after-commit consequences may use domain/integration events and an outbox, but an in-memory Observer must not be confused with durable event delivery.
- **Singleton/Flyweight/Prototype/Bridge/etc.:** no current SquiFlow requirement is established merely from this source.

**Critical decision sentence:** We use an abstraction/pattern only at a boundary where its structural property solves a demonstrated coupling, lifecycle, replacement or state problem; we change/remove it if the abstraction adds indirection without reducing real maintenance/failure cost.

## Critical questions
**Foundation**

# 082 — CI/CD Simplified Visual Guide

## A. Identification
- **PDF pages:** `162-163`
- **Original archive pages:** `308-309`
- **Visual-heavy page:** `162`
- **Classification:** `PLANNED DELIVERY CAPABILITY / IMPLEMENTATION GAP`; the release contract is documented, but the current repository root contains no committed CI configuration.

## B-C. Core concept and important concepts — SOURCE
The source shows a feature-branch workflow: developer writes code, pushes to Git, a Jenkins build runs, failed checks send the developer back to fix code, changes are reviewed/approved, merged to main, then another integration/build stage performs application build, code analysis, unit tests, integration tests and security scanning. A Docker image is produced/pushed, and the bottom of the visual depicts deployment to Kubernetes.

Page `163` defines Continuous Integration as frequent combination of code changes with automated checks and Continuous Deployment as automatically moving changes into real-world/production use.

## D. Diagram / visual explanation
The visual mixes **workflow policy** (feature branch, review, merge), **CI evidence** (build, tests, analysis, scanning), **artifact packaging** (Docker image/registry), and **deployment topology** (Kubernetes). These are separate decisions even though they appear in one vertical path.

## E-F. How it works and why it matters
CI/CD reduces integration risk when each change can be rebuilt and checked consistently and when deployment promotes known artifacts through a controlled recovery path. Its value is reproducibility and evidence, not the specific logos shown.

## G-H. Trade-offs / limitations — EXTERNAL KNOWLEDGE
- CI does not require Jenkins, feature branches or one exact branching model.
- “CD” is ambiguous in industry: it can mean Continuous Delivery or Continuous Deployment. The source explicitly describes **Continuous Deployment**.
- Automatic deployment is not automatically safer for a single owned rack with schema changes, limited spare capacity and explicit maintenance/recovery needs.
- A green unit/integration/security-scan pipeline cannot prove restore, power-loss recovery, provider outage, hardware capacity, identity integration or migration compatibility unless those tests actually ran.
- Docker/Kubernetes are packaging/orchestration options, not mandatory CI/CD stages.
- Rebuilding per environment destroys artifact identity; production should promote the same verified bytes/image.
- Security scanning has false positives/negatives and requires triage; passing a scanner is not proof of application security.

## Implications for the Current Implementation
**What are we actually doing?** SquiFlow already documents a release/qualification contract: immutable versioned artifact, checksum/provenance, config/secrets external to artifact, migration/dependency/capacity preflight, health + authorized smoke journey, and tested rollback/roll-forward/maintenance recovery. The current GitLab repository, however, does **not** yet contain `.gitlab-ci.yml` or application source, so the automated pipeline is **not verified implemented**.

**Why this approach?** The architecture needs reproducible evidence and recoverability on lower-spec owned hardware; it does not need Jenkins/Docker/Kubernetes merely to match the visual.

- **IMPROVE WHEN IMPLEMENTATION STARTS:** create the smallest CI pipeline that builds/tests the real artifact and enforces architecture/security/test gates.
- **KEEP:** release qualification outside CI where real hardware, provider, restore or manual recovery evidence is required.
- **DELIVERY MODE:** a human-approved maintenance deployment can be correct for the initial single-active-node profile. Continuous Deployment becomes a separate operational decision only when automatic promotion is demonstrably safer.
- **ARTIFACT RULE:** build once, verify once, promote the same bytes.
- **FALSIFICATION:** if CI becomes so slow/flaky that developers bypass it, split fast merge gates from scheduled/release qualification rather than deleting required evidence.

## Critical questions
1. Which claims can a merge pipeline prove, and which SquiFlow production claims require real provider/hardware/restore evidence?
2. Why does “green CI” not prove a database migration is safe for an old Workstation returning after months offline?
3. Does the current repository actually have a CI pipeline, or only a documented requirement?
4. Why would auto-deploying every merge to a single customer rack be riskier than a controlled maintenance release today?
5. What is the immutable artifact in the first implementation if containers are not selected?
6. Which checks must block merge versus run on schedule/release qualification?
7. How should failed security scans be triaged instead of blindly ignored or blindly blocking forever?
8. What exact evidence would justify moving from human-approved deployment toward Continuous Deployment?
9. **Challenge:** design the first GitLab CI/release flow for SquiFlow without assuming Docker or Kubernetes, and state exactly what each stage proves and what it explicitly does not prove.

# 083 — How Apache Kafka Works?

## A. Identification
- **PDF pages:** `164-165`
- **Original archive pages:** `310-311`
- **Visual-heavy page:** `164`
- **Related prior material:** messaging patterns, RabbitMQ, CQRS, outbox/Worker.
- **Classification:** `POSITIVE FIT FOR REPLAYABLE EVENT-STREAM WORKLOADS / NOT CURRENTLY REQUIRED FOR FIRST WORKER PATH`.

## B-C. Core concept and important concepts — SOURCE
The source describes Kafka as a distributed event streaming platform. Flow:
1. producer creates data such as clicks or payment events;
2. serializer converts data to bytes;
3. partitioner chooses a topic partition;
4. message is published to a Kafka broker cluster;
5. brokers store topic partitions and replicate them;
6. messages inside partitions are stored in order and remain available for reading;
7. a consumer group subscribes;
8. consumers in the group read different partitions to balance work;
9. consumers process the records for dashboards/actions.

The visual shows producer → serializer → partitioners → replicated topic partitions across brokers → several consumers inside one consumer group.

## D-F. Diagram, mechanics, why it matters
Partitioning is the central scaling/ordering mechanism. Consumers in one group divide partitions; replication gives broker-failure tolerance; retained records allow consumers to maintain/rebuild their own position and derived state.

Kafka is most valuable when durable replay, independent consumers, high sustained throughput and partition-scoped ordering are real requirements.

## G-H. Trade-offs / limitations — EXTERNAL KNOWLEDGE
- Ordering is guaranteed only **within a partition**, not globally across a topic.
- Replication does not automatically mean “no loss”; producer `acks`, replication factor, in-sync replicas and broker settings define the durability envelope.
- Consumers need offset-commit semantics. Commit-before-effect risks loss; effect-before-commit risks duplicate processing.
- Rebalancing changes partition ownership and can pause/repeat work.
- Kafka retention is independent of consumption; records are not normally deleted simply because one consumer read them.
- “Exactly-once” Kafka features have a defined scope and do not magically make external business effects exactly once.
- Schema/key evolution, partition-key selection, hot partitions, lag, storage retention, broker upgrades and capacity planning become operational responsibilities.
- Multi-tenant workloads need fairness/isolation and must not encode PII/secrets carelessly into topics/keys/headers.

## Implications for the Current Implementation
**What are we actually doing?** Current SquiFlow architecture uses transactional authoritative relational state plus an outbox and a future Worker/job mechanism for durable after-commit consequences. The first Worker may use a simple durable database-backed job store.

**Why?** The initial named workloads are one-owner work items (PDF generation, notifications, reconciliation, scheduled jobs) and independent after-commit consequences. A DB-backed outbox/job path is simpler to operate on the owned rack and can preserve atomicity with the business transaction.

**Where Kafka could be better:** if SquiFlow later has a real stream where multiple independent consumers need durable replay/history/independent offsets, sustained throughput, and partition-key ordering that the DB job/outbox path handles poorly, Kafka becomes a strong candidate.

**Complementary fit:** a transactional outbox can remain the business-commit boundary and later publish committed facts into Kafka. Kafka would then be transport/replay infrastructure, not the source of current payment/stock/authorization truth unless a separate explicit architecture decision says otherwise.

**Adoption evidence required:** measured event volume/retention, consumer count, replay requirement, acceptable partition key, lag target, storage footprint, broker topology, failure/rebalance behavior and small-team operational cost.

**Falsification:** if the real workload is merely “process this one job once eventually,” Kafka is likely excess complexity relative to the simpler durable job/outbox mechanism.

## Critical questions
1. What ordering guarantee does a Kafka partition provide, and what does it not provide across partitions?
2. What is the actual SquiFlow workload that would require replayable history rather than one durable job?
3. Why can consumer offset management create duplicates or loss depending on commit timing?
4. If payment-related facts are published, which system remains authoritative and why?
5. What partition key would preserve the ordering SquiFlow actually needs without creating hot partitions?
6. How many truly independent consumers justify pub/sub/stream semantics rather than multiple outbox deliveries?
7. What does Kafka add to failure recovery, and what new broker/storage/rebalance/schema obligations does it create?
8. Can the same SquiFlow deployment use a DB-backed job queue for PDFs and Kafka for a future analytics stream? Why is that not inconsistent?
9. What measurement would prove the DB outbox/job path is no longer economical?
10. **Challenge:** design a future `InvoiceIssued` flow with three consumers (PDF, external accounting export, analytics). Decide which parts remain in the DB transaction/outbox, whether Kafka is justified, what the partition key is, and how each consumer handles duplicate/out-of-order delivery.

# 084 — Load Balancers vs API Gateways vs Reverse Proxy! And how can they Work Together?

## A. Identification
- **PDF pages:** `166-167`
- **Original archive pages:** `312-313`
- **Visual-heavy page:** `166`
- **Classification:** `COMPLEMENTARY EDGE CAPABILITIES / FIT BY TOPOLOGY`; do not infer three separate products from three labels.

## B-C. Core concept and important concepts — SOURCE
The source says the three roles overlap but can be combined. Its example flow is:
1. client reaches an edge load balancer;
2. API Gateway performs parameter validation;
3. whitelist verification;
4. authentication and authorization;
5. rate limiting;
6. reverse proxy forwards to the right service endpoint;
7. another load balancer distributes among instances of a target microservice;
8. service processes and returns the response.

The visual additionally places service discovery, request transformation, circuit breaker, caching, error handling and logging inside the API Gateway box.

## D-F. Diagram / mechanics / why it matters
The diagram shows **north-south traffic management**: one public entry point can terminate/route traffic and perform coarse policy before forwarding to backend services. Load balancing only becomes meaningful when there are multiple viable backends; reverse proxying is routing/mediation; API-gateway capability is higher-level API policy/composition.

## G-H. Trade-offs / limitations — EXTERNAL KNOWLEDGE
- One product can perform reverse proxy, TLS termination, routing, health checks, rate limiting and load balancing; the conceptual roles do not require separate infrastructure products.
- A gateway that performs business authorization becomes a dangerous single policy point if backends can be reached another way or if authorization depends on current resource/domain state.
- “Whitelist” rules are coarse network/client admission, not tenant/resource authorization.
- Request transformation can create hidden contract/version complexity.
- Service discovery is unnecessary in a small static topology and becomes valuable only as endpoints become dynamic.
- A load balancer does not create HA if the DB, edge, rack power/network or identity dependency remains a single point of failure.
- The edge/gateway itself can become a bottleneck/SPOF and needs health, capacity, timeout, header-trust, TLS, log and recovery design.
- `X-Forwarded-*`/forwarded headers must be trusted only from known proxies; otherwise scheme/host/client-IP confusion can undermine security.

## Implications for the Current Implementation
**What are we actually doing?** SquiFlow already documents an **edge reverse proxy/API-gateway capability** for TLS termination, hostname/custom-domain routing, request-size/WAF/private-access policy where configured, coarse public/admin exposure and coarse rate limiting. Core API and Admin API still independently authenticate/authorize/validate business/resource state.

**Why?** External traffic needs a stable edge/TLS/routing boundary, and custom-domain/public-vs-admin exposure are edge concerns. Business authorization remains in the owning backend because it needs TenantContext, OpenFGA and domain/resource state.

- **Reverse proxy capability — current documented fit:** route accepted hosts/paths to Core/Admin without leaking business logic into the edge.
- **API-gateway capabilities — selective fit:** coarse rate/admission, request-size, edge auth support, WAF/private policy, protocol negotiation, observability where they simplify north-south controls.
- **Load balancing — topology-triggered:** useful when multiple healthy Core/Admin instances actually exist. With one active rack instance, an internal service LB adds little and must not be described as HA.
- **No microservice inference:** the source's `/users`, `/orders`, `/inventory` microservices do not change SquiFlow's modular-monolith decision.
- **Recovery:** private recovery access must not depend entirely on the same failed public edge.

**Critical decision sentence:** We use the edge/reverse-proxy capability because TLS, host routing and coarse exposure belong at the public boundary; we add load-balancing/gateway features only when the deployment topology or abuse/capacity requirement makes them useful, while backend business authorization remains unchanged.

## Critical questions
1. Which of load balancing, reverse proxying and API-gateway policy does the initial SquiFlow edge actually need?
2. Why can one edge component implement several of those capabilities without violating architecture clarity?
3. What authorization can safely happen at the edge, and what must remain in Core/Admin?
4. If there is one Core API instance, what does an internal load balancer actually improve?
5. What happens if the edge is down while Core API and the DB are healthy?
6. How are forwarded host/scheme/client-IP headers constrained so an attacker cannot spoof trusted proxy context?
7. Should Core and Admin share one public edge, and how do we preserve their independent security/runtime planes?
8. When would service discovery become real rather than decorative?
9. What metric/topology would justify a second Core instance and actual load balancing?
10. **Challenge:** design the initial single-rack edge and a future two-node edge evolution. Name exactly which functions are reverse proxy, gateway policy and load balancing, and explain why the business authorization path stays the same in both topologies.

# 085 — The Life of a Redis Query

## A. Identification
- **PDF pages:** `168-169`
- **Original archive pages:** `318-319`
- **Visual-heavy page:** `168`
- **Classification:** `REDIS ROLE-SPECIFIC FIT / PERSISTENCE POLICY DEPENDS ON WHAT REDIS IS FOR`.

## B-C. Core concept and important concepts — SOURCE
The source describes Redis as an in-memory database and focuses on two persistence mechanisms:
- **AOF:** client command is executed in memory, then appended to an AOF on disk so commands can be replayed during recovery.
- **RDB:** Redis periodically snapshots the dataset; the main process forks a `bgsave` subprocess and uses copy-on-write while the child writes the snapshot to disk.
- **Mixed approach:** the source says production often uses both, with RDB for compact/fast reload and AOF for recording operations since the last snapshot.

The diagram shows a client cache operation, Redis/main thread/RAM, AOF write path, forked `bgsave`, copy-on-write memory, and AOF/RDB files on disk.

## D-F. How it works and why it matters
Redis performance comes primarily from serving data from memory. Persistence changes the recovery/durability contract and introduces disk/fsync/fork/rewrite considerations. Whether persistence is useful depends on the role Redis is playing.

## G-H. Trade-offs / source caveats — EXTERNAL KNOWLEDGE
- The statement that “execute then append ensures every operation can be replayed” is too strong without the configured **AOF fsync policy**. Durability can range from stronger per-write syncing to bounded-loss approaches such as `everysec`.
- “Writes are non-blocking” is also too broad. AOF fsync/rewrite and system I/O can create latency, and persistence policy changes the acknowledgment/durability window.
- RDB snapshotting can lose updates since the last successful snapshot if it is the only persistence mechanism.
- Fork + copy-on-write can create significant temporary memory pressure and latency on large/write-heavy datasets; low-spec hardware must be measured.
- AOF rewrite, disk full, corruption/recovery, replication/failover, eviction/maxmemory and persistence startup time are not shown.
- If Redis is merely a disposable cache, persistence may be unnecessary or even counterproductive; if it stores session/revocation/coordination state, loss semantics may be materially different.
- Redis can be used as cache, data structure server, stream/queue-ish component, session store and more; “Redis persistence” cannot be decided without first deciding its exact authority/role.

## Implications for the Current Implementation
**What are we actually doing?** SquiFlow does not currently require Redis. The accepted cache rule says caches are disposable, bounded, tenant-scoped and non-authoritative. Identity docs say shared/durable session-revocation state may become necessary if multi-node behavior requires it, but no Redis session architecture has been selected.

**Why not add Redis now?** There is no measured shared-cache/session/coordination workload that the current database/process topology cannot handle more simply.

**Where Redis could fit:**
- shared hot-data cache when repeated reads and DB pressure justify it;
- distributed server-session/revocation state if future multi-node Web topology requires shared low-latency session state;
- specialized rate/admission counters or coordination only if correctness/availability semantics are explicit.

**Why persistence depends on the role:**
- disposable cache → usually rebuildable; persistence may not be required;
- session/revocation state → persistence/failover may matter depending on logout/revocation guarantees;
- authoritative payment/stock/credit/tenant state → Redis should not silently replace the relational authority without a separate demonstrated design.

**Adoption evidence:** measured cache repetition, DB load reduction, latency benefit, memory envelope, cold-start behavior, failure mode, session/revocation semantics, persistence/failover needs and operator cost.

## Critical questions
1. What exact SquiFlow state would Redis hold, and is it authoritative, derived, cached or session/coordination state?
2. If Redis is only a cache, why would we pay AOF/RDB durability and recovery cost?
3. If Redis stores revocation/session state, what loss window is acceptable after restart?
4. Which AOF fsync policy would match that requirement, and what latency/disk cost does it create?
5. How much extra RAM can fork/copy-on-write require during RDB snapshotting on the actual rack?
6. What happens when Redis is unavailable: bypass to DB, fail closed, disable optional feature, or block login/session validation?
7. Why must a persisted Redis dataset still not become current OpenFGA/payment/stock authority by accident?
8. What measured symptom would justify Redis over an in-process cache or direct PostgreSQL read?
9. **Challenge:** compare two hypothetical SquiFlow uses—product-list cache and shared Web session/revocation state. For each, decide whether AOF/RDB persistence is needed, what failure means, and what rebuild/recovery path exists.

# 086 — Cookies vs Sessions

## A. Identification
- **PDF pages:** `170-171`
- **Original archive pages:** `322-323`
- **Visual-heavy page:** `170`
- **Classification:** `COMPLEMENTARY MECHANISMS`; cookie and server session are usually parts of one session design, not mutually exclusive technologies.

## B-C. Core concept and important concepts — SOURCE
The source says:
- **Cookies** store data on the client and are sent back with each request; they are simpler but can expose data if not secured.
- **Sessions** store data on the server; the client stores a session ID in a cookie and the server retrieves session data from a session store; this requires server-side storage/management and is described as more secure.

The visual contrasts a client-stored-data path against a session-ID + server lookup path.

## D-F. How it works and why it matters
A browser cookie is a client storage/transport mechanism. A server-managed session normally still uses a cookie to carry an opaque session identifier. The real architecture question is what information is client-held versus server-held, how the credential is protected, how revocation/expiry works, and whether session state must be shared across nodes.

## G-H. Trade-offs / source caveats — EXTERNAL KNOWLEDGE
- “Cookies vs sessions” is not a strict either/or comparison; sessions commonly depend on cookies.
- “Sessions are more secure” is too broad. A stolen session-ID cookie can still hijack the session; server-side storage helps keep sensitive state out of the browser and can improve revocation/control.
- Cookies need `Secure`, `HttpOnly`, deliberate `SameSite`, appropriate path/domain, expiry and CSRF handling.
- Cookie size is limited and every matching request carries it, so large client-side state hurts bandwidth and exposure.
- Server sessions require storage, cleanup, rotation/fixation protection and shared/durable state when multiple server nodes need continuity/revocation.
- XSS and CSRF are different threats: `HttpOnly` helps against script reading but does not itself solve CSRF; `SameSite`/antiforgery and output encoding remain relevant.
- OIDC IdP session, SquiFlow application session and Blazor circuit/session state are separate lifecycles.

## Implications for the Current Implementation
**What are we actually doing?** SquiFlow's identity architecture favors hardened **server-managed/browser sessions** for Web where practical, with ZITADEL/OIDC performing authentication. Exact cookie/session and Blazor topology remains an implementation POC.

# 087 — Access Control Clearly Explained

## A. Identification
- **PDF pages:** `172-173`
- **Original archive pages:** `324-325`
- **Visual-heavy page:** `172`
- **Classification:** `COMPOSE AUTHORIZATION MODELS BY RULE SHAPE`; SquiFlow already combines role, relationship and domain/context semantics.

## B-C. Core concept and important concepts — SOURCE
The source compares:
- **RBAC:** permissions attached to roles; example GitHub Maintainer/Viewer roles.
- **ABAC:** policy decision from user/resource/environment attributes; example department, clearance, classification, IP/time.
- **ACL:** explicit entries on a resource for users/groups and operations.

It summarizes: RBAC = roles, ABAC = attributes, ACL = explicit permissions.

## D-F. Diagram / mechanics / why it matters
The visual shows three different decision shapes. RBAC resolves user → role → permissions. ABAC combines attributes in a policy engine. ACL loads explicit resource entries and checks user/group membership. They can solve different parts of one authorization architecture.

## G-H. Trade-offs / limitations — EXTERNAL KNOWLEDGE
- The source omits **relationship-based access control (ReBAC)**, which is highly relevant to OpenFGA/Zanzibar-style models.
- RBAC can suffer role explosion when every resource/context variation becomes another role.
- ABAC is flexible but policy testing, explainability, conflict/precedence and attribute freshness can become difficult.
- ACLs are direct and understandable for one resource, but per-resource/user management can become expensive at scale.
- Real systems frequently combine models: role groups for coarse capability, relationships for resource scope, and domain/context checks for current state.
- Authentication and authorization remain separate; no model here proves the caller's identity.
- Cached authorization decisions have freshness/revocation implications regardless of model.

## Implications for the Current Implementation
**What are we actually doing?** SquiFlow has already selected OpenFGA for application authorization, but it is **not using one pure textbook model**:
- tenant custom roles + stable permission vocabulary are **RBAC-like grouping**;
- OpenFGA user/object/role relationships provide **ReBAC/resource scope**;
- tenant/resource current state, workflow state, delegation ceiling and other business/context checks remain in SquiFlow domain/application code and are **attribute/state-like constraints**;
- database TenantId scoping/RLS defense is independent isolation, not an authorization-model substitute.

**Why this composition?** SquiFlow needs tenant-customizable roles without generating arbitrary policy code, relationship-aware resource scope, current revocation/freshness, and strong domain invariants that do not belong in the authorization engine.

**Where ACL-style explicit relationships may fit:** narrow per-resource sharing/assignment rules where explicit user/group membership is genuinely the business model. Do not create per-row ACL tuples merely because possible.

**What remains unchanged:** OpenFGA `allow` never bypasses tenant filtering, domain state, idempotency, concurrency or protected financial rules.

**Falsification/change trigger:** if authorization rules become mostly dynamic attributes/environmental policies that OpenFGA relationships express awkwardly, evaluate whether a bounded policy engine/ABAC capability is justified for that exact surface rather than replacing the whole authorization model.

## Critical questions
1. Is SquiFlow currently “RBAC”, “ABAC”, “ACL” or something more compositional?
2. Why are tenant custom roles not sufficient for resource-specific relationships such as assigned program/project/branch?
3. Which current rules must stay outside OpenFGA even though they look like attributes?
4. How does role explosion happen if every workflow state or branch becomes a new role?
5. When is an explicit ACL easier to understand than a generalized relationship model?
6. What is the revocation/freshness requirement for a payment refund versus a low-risk read?
7. How do we explain an authorization denial to an Owner without exposing internal policy details or PII?
8. What evidence would justify introducing a real ABAC/policy engine for one SquiFlow surface?
9. **Challenge:** model a Staff member who may view all orders in Branch A, edit only orders assigned to them, and refund payments only with a Manager role while the payment is in a refundable state. Separate RBAC-like, ReBAC, tenant isolation and domain-state responsibilities.

# 088 — API Vs SDK!

## A. Identification
- **PDF pages:** `174-175`
- **Original archive pages:** `339-340`
- **Visual-heavy page:** `174`
- **Classification:** `API AND SDK ARE COMPLEMENTARY`; API is the contract/protocol surface, SDK is one implementation toolkit/client over that surface.

## B-C. Core concept and important concepts — SOURCE
The source defines an **API** as rules/protocols allowing applications/services to communicate, typically through endpoints, requests, responses, status codes and data formats. It defines an **SDK** as a package of libraries, tools, sample code and documentation tailored to a platform/framework/hardware and offering higher-level abstractions/capabilities.

The visual's API half uses an HTTP-method/endpoint/query-parameter request to a maps API. The SDK half shows language/platform toolkits and then an application using an API integration.

## D-F. How it works and why it matters
An API is the externally observable contract. An SDK can reduce implementation boilerplate for authentication, serialization, request construction, streaming, retries and models. A robust architecture can deliberately use an SDK internally while keeping SquiFlow's business contract independent from the SDK.

## G-H. Trade-offs / source caveats — EXTERNAL KNOWLEDGE
- API and SDK are not competing alternatives; an SDK normally calls an API.
- SDKs can lag new API features, pin dependency versions, hide transport/retry behavior or expose provider-specific models deeply into application code.
- Raw HTTP/API use gives more control and fewer dependencies but increases protocol/auth/error/serialization work.
- Generated clients are another middle ground.
- Provider SDK retry defaults can multiply SquiFlow's own retries and duplicate non-idempotent effects if retry ownership is not explicit.
- The source visual places an API key in a query string. For sensitive bearer-like API keys, URLs are often a poor carrier because URLs can leak into logs/history/referrers; provider-supported authorization headers or signed mechanisms are preferable when available.

## Implications for the Current Implementation
**What are we actually doing?** Current SquiFlow documents **provider APIs/protocols as boundaries** and explicitly prevents provider SDK types from leaking into business/domain records. It also defines intentional SquiFlow-facing adapters such as `IObjectStore` and `IBackupTarget`. Because there is no application code committed yet, we cannot claim which provider SDK packages are actually in use.

**Why this rule?** The API/provider owns external semantics, while SquiFlow needs stable application contracts and the ability to replace providers without rewriting business logic.

- **ZITADEL/OIDC:** use standards-compliant OIDC/.NET integration rather than custom protocol code; an SDK/library is an implementation aid, not the identity authority.
- **OpenFGA:** the real authorization semantics are OpenFGA model/tuple/check API semantics; an official SDK can simplify transport/types, but SquiFlow's authorization requirements remain semantic and testable against the real service.
- **Object/backup providers:** SDK/API details belong inside adapters; contract tests prove SquiFlow semantics across providers.
- **Raw API versus SDK selection:** decide per provider from SDK quality, feature coverage, streaming support, error transparency, retry control, dependency footprint and maintenance—not from a generic “SDK is easier” rule.

## Critical questions
1. What is the stable contract: the provider API, its SDK, or SquiFlow's own application boundary?
2. Why can an SDK make development easier while increasing dependency/version/retry coupling?
3. When should SquiFlow call a provider through raw HTTP rather than its official SDK?
4. How do we stop provider request/response models from leaking into domain records?
5. Who owns retries when both an SDK and SquiFlow have retry policies?
6. What happens if an SDK hides a provider-specific error that matters for reconciliation?
7. Why should a bearer API key usually not be placed in a URL/query string when a safer supported carrier exists?
8. Which contract tests prove an `IObjectStore` adapter is substitutable beyond method signatures?
9. **Challenge:** a provider SDK offers automatic retries, object models and upload helpers but is two API versions behind and hides raw error bodies. Decide whether to use it, wrap it, combine it with direct API calls, or avoid it for one SquiFlow integration, and justify the operational trade-off.

# 089 — SQL Injection (SQLi)

## A. Identification
- **PDF pages:** `176-177`
- **Original archive pages:** `341-342`
- **Visual-heavy page:** `176`
- **Classification:** `KEEP SECURITY INVARIANT / IMPLEMENTATION MUST BE PROVEN`; current docs specify controls but source code is not yet present to verify them.

## B-C. Core concept and important concepts — SOURCE
The source explains SQL injection as crafted input that changes database query meaning. It shows:
- **tautology/basic SQLi:** conditions such as `1=1` bypass intended filtering/authentication;
- **in-band union/error-based:** UNION or database errors return sensitive information directly;
- **blind boolean-based:** attacker infers information from differences in result behavior;
- **blind time-based:** attacker infers information from induced response delay such as `SLEEP(5)`.

The visual repeatedly shows attacker input becoming part of the final SQL query and the application leaking either rows, errors, boolean outcome or timing information.

## D-F. How it works and why it matters
SQLi happens when untrusted data is interpreted as SQL structure rather than bound data. The primary defense is to keep query syntax/identifiers controlled by trusted code and bind untrusted values as parameters. Defense-in-depth limits damage when a defect exists.

## G-H. Trade-offs / caveats — EXTERNAL KNOWLEDGE
- Parameterization is the primary defense for values, but parameters generally cannot safely substitute arbitrary table/column/order/operator identifiers; dynamic identifiers require allow-lists/structured query composition.
- ORMs are not automatically safe if raw SQL, string interpolation or unsafe dynamic query construction is used.
- Stored procedures are not automatically safe if they concatenate dynamic SQL.
- Input validation, WAF signatures, escaping and DB timeouts can help but do not replace parameterization/allow-listed query structure.
- Least-privilege DB accounts reduce blast radius; the runtime account should not be superuser or bypass tenant isolation for convenience.
- Safe error responses prevent error-based leakage but do not fix the injection bug itself.
- Time-based blind attacks demonstrate why “we do not display SQL errors” is not enough.

## Implications for the Current Implementation
**What are we actually doing?** SquiFlow's Application Security Baseline already requires parameterized commands/ORM binding/provider-safe query composition, allow-listed dynamic filters/sorts/search/report/import/custom-field/admin identifiers/operators, least-privilege DB identity, safe errors, TenantContext scoping and hostile SQLi tests.

**Critical evidence distinction:** this is currently a **documented requirement, not verified implementation**, because the repository contains no application data-access code yet.

**Why these controls?** SquiFlow has inherently dynamic surfaces—filter/sort/report/import/configuration/custom-field and tenant-admin queries—where simple “ORM = safe” assumptions are insufficient. Tenant isolation makes injection impact especially severe because one defect could become cross-tenant disclosure/modification.

- **KEEP:** value parameterization.
- **KEEP:** identifier/operator allow-listing for dynamic query features.
- **KEEP:** least-privilege runtime DB identity and no `BYPASSRLS` convenience.
- **KEEP:** API field/output allow-lists, stable safe errors and tenant-scoped queries.
- **PROVE IN TESTS:** tautology, UNION/error, boolean/time-based payloads across every actual dynamic query path.
- **DO NOT OVERCLAIM:** RLS, ORM or WAF alone is not the SQLi solution.

## Critical questions
1. Which planned SquiFlow endpoints will construct dynamic filter, sort, report or custom-field queries?
2. Where can parameters safely bind values, and where are identifier/operator allow-lists required?
3. Could a raw SQL optimization reintroduce injection after most code uses an ORM safely?
4. What DB privileges does the runtime account actually need, and what damage would an injection have under that identity?
5. How does TenantContext scoping reduce but not eliminate SQLi risk?
6. What error/latency differences could still leak data in blind SQLi even with generic error pages?
7. Which tests should use two tenants so SQLi cannot silently cross isolation boundaries?
8. Would a DB statement timeout stop time-based extraction completely, or only make it harder? Why is that secondary?
9. **Challenge:** implement a flexible `GET /orders?sort=...&filter=...` design that supports tenant-selected columns without concatenating arbitrary SQL identifiers/operators. Define the allow-list, parameterization, authorization and hostile tests.
