# 071 — Key Terms in Domain-Driven Design

## Identification
- **PDF pages:** `142-143`
- **Original archive pages:** `272-273`
- **Related prior material:** `028`, `032`, `035`, `049`, `055`, `056`, `066`, `068`.
- **Current SquiFlow owners consulted:** `docs/domain/BUSINESS_MODEL.md`, `docs/domain/CROSS_CUTTING_BUSINESS_PRIMITIVES.md`.
- **Classification:** `KEEP DDD AS MODELING DISCIPLINE`; `AVOID` converting every table/class into ceremonial DDD artifacts.

## SOURCE
The article summarizes:
- **Entity** — domain object with an ID and lifecycle.
- **Value Object** — domain object without an ID, used to describe an Entity.
- **Aggregate** — collection of Entities bounded by an Aggregate Root; described as the “unit of storage.”
- **Repository** — stores and loads the Aggregate.
- **Factory** — handles Aggregate creation.
- **Domain Service** — orchestrates multiple Aggregates.
- **Domain Event** — describes what happened to an Aggregate; the source says publication allows others to consume and reconstruct it.

The article closes by asking how equality differs for Value Objects and Entities.

## Diagram / visual
The diagram groups the concepts into three regions:
- **composition:** Value Object → Entity → Aggregate → Aggregate Root;
- **lifecycle:** Factory and Repository around the Aggregate;
- **behavior:** Domain Service coordinating Aggregates and Domain Event publishing changes.

Its strongest useful idea is that **identity, composition, lifecycle and behavior are different modeling concerns**.

## INFERENCE
DDD is valuable when business rules are difficult enough that the code needs explicit language and ownership boundaries. The critical question is not “where do we put the Aggregate class?” but:

> **Which business invariant must be consistent together, and which object owns the right to change it?**

That question determines whether a boundary is real.

## EXTERNAL KNOWLEDGE / caveats
- An Aggregate is more usefully understood as a **consistency/transaction boundary around invariants** than merely a “unit of storage.” One aggregate may map to several tables.
- Not every Entity inside an Aggregate should have its own Repository. Repositories are commonly exposed around Aggregate Roots.
- A Value Object typically uses structural/value equality; an Entity is identified by stable identity across state changes.
- A Domain Service is appropriate for domain behavior that does not naturally belong to one Entity/Value Object. Cross-aggregate workflow orchestration is often an **application-service/process** concern instead of automatically a Domain Service.
- A Domain Event is not automatically an integration event and does not imply Event Sourcing. Publishing externally usually needs an explicit after-commit/outbox boundary.
- “Others can consume and reconstruct it” risks conflating ordinary domain events with replay-derived Event Sourcing.
- Factories are most useful when construction is complex/invariant-heavy; ordinary constructors/static creation functions can be enough for simple cases.
- DDD also includes concepts absent from this article, especially Ubiquitous Language, Bounded Contexts, Context Maps and Anti-Corruption Layers.

## Implications for the Current Implementation
- **WHAT WE ARE DOING:** SquiFlow models real small-business concepts such as Party, Order, Quotation, Payment, Inventory, Purchasing and Documents with explicit historical/correction rules. It does **not** adopt a generic ERP taxonomy simply because DDD terminology exists.
- **WHY:** business invariants—issued history, payment/refund safety, stock concurrency, workflow continuation, tenant authority—need explicit owners and transaction/concurrency rules.
- **WHAT DDD BUYS US:** a disciplined way to ask which object/boundary owns identity, invariants, transitions and historical truth.
- **WHAT WE SHOULD NOT DO:** create `Repository<T>` for every table, one Aggregate project per noun, or Domain Events for ordinary internal method calls.
- **AGGREGATE REVIEW GATE:** before calling a SquiFlow concept an Aggregate, state the invariant it protects, what must commit atomically, expected-version boundary, and what may be eventually coordinated outside it.
- **DOMAIN EVENT GATE:** before publishing an event, ask whether it is only in-process domain notification, durable after-commit integration work, audit/history, or Event Sourcing. Those are not equivalent.
- **NO OWNER CHANGE:** current business/domain documents already prefer concrete business semantics over framework ceremony.

## Critical fit interrogation
1. **What exactly are we modeling as one consistency boundary, and what invariant requires that boundary?**
2. If two records are in one Aggregate only because the UI edits them together, is that actually a domain reason?
3. What operation must be atomic, and what can safely happen after commit?
4. Would a plain domain method be clearer than a Domain Service?
5. Is a proposed Domain Event needed for durable consequences, or is it just hiding a direct in-process call?
6. What evidence would show an Aggregate boundary is too large—lock contention, write conflicts, workflow coupling, or inability to scale?
7. What evidence would show it is too small—distributed invariant repair, partial-state bugs, or repeated cross-aggregate transactions?

## Critical questions
**Foundation**
1. Why is Entity equality different from Value Object equality?
2. What makes an Aggregate Root different from an arbitrary parent row?
3. Why is a Repository normally aligned with an Aggregate boundary?

**Reasoning / trade-offs**
4. Why is “Aggregate = unit of storage” an unsafe literal interpretation?
5. When should creation logic use a Factory versus a simple constructor/static method?
6. Why can cross-aggregate orchestration belong outside the domain object model?
7. How is a Domain Event different from a durable integration event?

**SquiFlow challenge**
8. For `RecordPayment`, identify the exact invariant, transaction boundary, idempotency evidence and any after-commit consequence. Which pieces belong inside the Aggregate transaction, and which do not?

```text
Edge
    -> reverse proxy/TLS/routing where deployment requires it

Integration/API
    -> ASP.NET Core Core API
    -> future separate Admin API

Async
    -> transactional outbox + future durable Worker
    -> broker only when workload earns it

Business logic
    -> in-process modular-monolith modules/domain/application logic

Data access/storage
    -> central relational candidate + local Workstation store

Analytics/ML
    -> not a baseline production dependency

Infrastructure
    -> small owned rack + selected external providers
    -> containers optional; Kubernetes only after orchestration trigger
```

- **WHAT WE ARE DOING:** using the smallest physical topology that preserves accepted security/fault/data boundaries.
- **WHY:** fewer distributed components reduce operational cost while the business workload is still small.
- **CRITICAL CHECK:** every new “layer” must name a real problem, authority boundary and failure contract. A box is not justified by being common in an infographic.

# 073 — Concurrency is NOT Parallelism

## Identification
- **PDF pages:** `146-147`
- **Original archive pages:** `280-281`
- **Related prior material:** database concurrency (`009`, `051`, `058`), async work (`015`, `052`), API/Worker bounds (`064`, `070`).
- **Classification:** `KEEP`; concurrency correctness is universal, parallelism is workload-specific.

## SOURCE
The article distinguishes:
- **Concurrency:** tasks start/run/complete in overlapping periods, even on one CPU core, with context switching creating the appearance of simultaneous progress; useful for waiting/I/O.
- **Parallelism:** multiple tasks execute simultaneously using multiple CPU cores; useful for heavy computation such as analysis/rendering.
- A well-designed concurrent program can scale to multiple cores for parallelism.

## Diagram / visual
The visual has:
- interleaved task slices on one CPU core for concurrency;
- simultaneous task sections across multiple CPU cores for parallelism;
- a combined diagram showing concurrent tasks scheduled across multiple cores.

## INFERENCE
The important architectural distinction is:
```text
concurrency
    -> how multiple in-flight activities are coordinated safely

parallelism
    -> how actual compute is executed simultaneously
```
Concurrency creates correctness/resource questions even when it does not improve CPU throughput.

## EXTERNAL KNOWLEDGE / caveats
- Concurrency does not require CPU context-switching between runnable threads; asynchronous I/O can overlap while threads are idle or reused.
- Parallelism can occur across processes, machines or accelerators, not only CPU cores.
- A concurrent design does not automatically become safely parallel. Shared mutable state, ordering assumptions, lock contention and thread-affinity can prevent scaling.
- Increasing concurrency can reduce throughput when the bottleneck is DB connections, disk, provider quota, memory, cache contention or a single lock.
- Parallel CPU work can starve latency-sensitive API/sync work on a small machine.
- Correctness mechanisms include transactions, optimistic concurrency, immutable data, queues, structured cancellation, bounded channels and ownership—not merely locks.

## Implications for the Current Implementation
- **Workstation:** network sync can be concurrent with local UI work, but local durable transaction/outbox semantics must prevent corruption.
- **Core API:** many requests are concurrent; DB pool, tenant fairness, rate/admission and expected-version rules bound their effects.
- **Worker:** concurrency is deliberately bounded by workload/resource/provider capacity. “More workers” is not automatically faster.
- **DB:** concurrent business writes use transaction/concurrency rules; generic last-write-wins is not acceptable for stock/payments/protected transitions.
- **CPU-heavy document/image work:** parallelism may help, but only after measurement on the actual rack; it can also harm API/DB/Guard responsiveness.
- **WHAT WE ARE DOING:** separating **correct concurrent coordination** from **performance parallelism**.
- **WHY:** the former is required for safety; the latter is optional optimization.

## Critical fit interrogation
1. What is the shared resource being accessed concurrently?
2. Which invariant can race, and where is the atomic boundary?
3. Is the work I/O-bound or CPU-bound?
4. Which resource actually limits concurrency: CPU, RAM, DB pool, disk, provider quota, network or lock?
5. What happens when cancellation/timeout occurs halfway through?
6. Could serialized execution be simpler and still meet the measured target?
7. What evidence proves increasing concurrency improves throughput rather than amplifying contention?

## Critical questions
1. Why can concurrency exist on one core?
2. Why can asynchronous I/O be concurrent without one dedicated thread per request?
3. Why does more concurrency sometimes lower throughput?
4. What is the difference between optimistic concurrency and parallel execution?
5. Which SquiFlow operations require strict serialization or expected-version protection?
6. How should Worker concurrency react to provider `429` or DB pool saturation?
7. **Challenge:** 10,000 Workstations reconnect after an outage. Design concurrency/admission/fairness without assuming parallelizing every sync item is the fastest recovery.

# 074 — JWT vs PASETO: The Two Players of Token-Based Authentication

## Identification
- **PDF pages:** `148-149`
- **Original archive pages:** `282-283`
- **Related prior material:** `005`, `008`, `010`, `022`, `039`, `043`, `061`, `069`.
- **Current SquiFlow owner:** `docs/security/IDENTITY_AND_SESSIONS.md`.
- **Classification:** `FIT BY PROTOCOL/ECOSYSTEM`; no custom token-format migration is justified from this comparison.

## SOURCE
The source describes:
- **JWT:** Header + Payload + Signature; open standard for transmitting information; can be used for stateless authentication.
- **PASETO:** modern alternative intended to provide safer defaults and stronger algorithm choices.
- PASETO structure: Version, Purpose, Payload.
- **Public PASETO:** asymmetric signature/integrity, not confidentiality.
- **Local PASETO:** symmetric encryption providing confidentiality.

The visual contrasts JWT's configurable algorithm/header model with PASETO's version/purpose model and shows public/local token flows.

## INFERENCE
This is primarily a **token-format and cryptographic-footgun** comparison, not a complete identity architecture comparison. A secure authentication system also needs issuer, audience, key lifecycle, client/session protocol, revocation/freshness, authorization and recovery.

## EXTERNAL KNOWLEDGE / caveats
- JWT is a token format, not an authentication protocol. OIDC/OAuth define protocol behavior around tokens.
- JWT can be implemented securely when the verifier—not untrusted token input—controls accepted algorithms, issuer/audience, keys, time and claims policy.
- PASETO reduces certain algorithm-agility mistakes by defining opinionated version/purpose suites, but it does not remove key management, replay, theft, audience/scope, expiry or authorization problems.
- Both are normally bearer credentials unless a separate proof-of-possession mechanism is used.
- Signed JWT/PASETO public tokens do not hide payload content.
- PASETO ecosystem/interoperability is much smaller than OIDC/JWT tooling. Replacing provider-issued OIDC tokens with a custom format can destroy interoperability without solving a real SquiFlow problem.
- PASETO versions and recommended primitives evolve; exact security properties are version-specific.

## Implications for the Current Implementation
- **WHAT WE ARE DOING:** SquiFlow delegates interactive identity to ZITADEL via standards-based OIDC/OAuth and validates provider-issued protocol tokens through maintained .NET integration.
- **WHY:** interoperability, SSO/MFA/passkeys/federation/session lifecycle matter more than owning a custom token format.
- **WHAT WE ARE NOT DOING:** inventing an independent SquiFlow JWT or PASETO authentication authority.
- **PASETO POSITIVE FIT:** it remains a legitimate option in a future **SquiFlow-owned token protocol** if a concrete boundary does not need OIDC interoperability and its security/default model materially helps.
- **ADOPTION GATE:** first prove that SquiFlow actually owns a token-format problem. If the requirement is identity, session revocation, machine credentials or authorization, changing JWT→PASETO may be solving the wrong layer.
- **UNCHANGED:** TenantContext, OpenFGA and domain/current-state validation remain authorization authority regardless of token format.

## Critical fit interrogation
1. What problem are we actually trying to solve: authentication protocol, token serialization, cryptographic algorithm safety, revocation, or authorization?
2. Who issues the token, and do we control that issuer?
3. Does the client ecosystem require OIDC/OAuth interoperability?
4. What security incident or requirement would a format change prevent?
5. What key-rotation/revocation/session lifecycle remains even after changing formats?
6. Are we trading a mature ecosystem for a format benefit that our current provider already handles?
7. What evidence would justify introducing a SquiFlow-owned token format at all?

## Critical questions
1. Why does a JWT signature not provide confidentiality?
2. What does PASETO's `public` purpose protect, and what does it not protect?
3. How does `local` differ from `public`?
4. Why does “secure defaults” not eliminate bearer-token theft?
5. Why is JWT-vs-PASETO not the same decision as OIDC-vs-custom-authentication?
6. **Challenge:** a team proposes PASETO because “JWT is insecure.” Determine whether SquiFlow has an actual vulnerability in issuer/audience/algorithm/key/session handling that PASETO would fix, or whether the proposal changes format without changing the real risk.

# 075 — The Lifecycle of a Kubernetes Pod

## Identification
- **PDF pages:** `150-151`
- **Original archive pages:** `288-289`
- **Related prior material:** `002`, `025`, `040`, `048`, `053`, `064`.
- **Classification:** `LATER / ORCHESTRATION TRIGGER`; lifecycle lessons are useful even while Kubernetes remains non-baseline.

## SOURCE
The source sequence is:
1. Pod manifest submitted to API Server and stored in etcd.
2. Scheduler selects/binds a node using resources/affinity.
3. Kubelet prepares the Pod: network namespace, IP, volumes, images.
4. Containers move Waiting → Running; kubelet monitors liveness/readiness.
5. Pod phase progresses through Pending, Running, Succeeded/Failed/Unknown.
6. Termination sends SIGTERM and SIGKILL if needed.
7. Resources are cleaned up and Pod details removed from etcd.

## Diagram / visual
The figure connects API Server, etcd, Scheduler, nodes, Kubelet, image registry, Pod sandbox/container runtime, networking/volumes, lifecycle phases, termination and cleanup. It makes **reconciliation plus lifecycle state** the main idea rather than “container starts and stops.”

## INFERENCE
Even if SquiFlow does not use Kubernetes, the lifecycle exposes universal operational questions:
- readiness versus process-alive;
- startup dependency;
- graceful shutdown/drain;
- immutable image/artifact;
- ephemeral versus durable state;
- cleanup after abnormal termination.

## EXTERNAL KNOWLEDGE / caveats
- The API Server is the Kubernetes API boundary; etcd is its backing state store rather than an application clients should manipulate directly.
- Kubelet coordinates Pod startup, but container runtime and CNI/CSI plugins perform important runtime/network/storage work; “kubelet creates network namespace/IP” is simplified.
- `Terminating` is not one of the Pod **phase** values shown; deletion has separate metadata/termination behavior.
- Graceful termination can include `preStop`, readiness removal, termination grace period and SIGTERM before SIGKILL.
- `readiness`, `liveness` and `startup` probes have different purposes; bad liveness probes can create restart loops.
- Stateful durability depends on the storage backend/PV contract and remains separate from Pod lifecycle.
- A Kubernetes Pod restart does not make an external effect or DB transaction “retry-safe.”

## Implications for the Current Implementation
- **WHAT WE ARE DOING NOW:** simple host/container/service deployment on a small rack, with explicit health, shutdown/drain, resource and recovery requirements.
- **WHY NOT KUBERNETES:** there is no proven recurring multi-node placement/reconciliation/service-discovery problem yet.
- **WHAT WE STILL LEARN:** distinguish liveness from readiness, bound startup/shutdown, keep authoritative state outside disposable process memory, and make drain/restart behavior explicit.
- **KUBERNETES ADOPTION TRIGGER:** repeated real operational pain around multi-node desired-state placement, replica replacement, rollout, discovery or failover that simpler tooling cannot manage reliably.
- **NO OWNER CHANGE:** current deployment owner already contains these gates.

## Critical fit interrogation
1. What exact operational problem would a Pod solve that a system service/container runtime does not?
2. Which SquiFlow state is disposable with the process, and which must survive?
3. What does “ready” mean beyond “port is open”?
4. What work must drain before SIGTERM completes?
5. Can a health probe accidentally restart a healthy-but-slow process and amplify an outage?
6. What stateful dependency still remains a SPOF even if the Pod is automatically replaced?
7. What measured operational burden would justify adopting Kubernetes?

## Critical questions
1. What is the role of the Scheduler versus Kubelet?
2. Why are readiness and liveness different?
3. Why is a PersistentVolume not automatically a backup?
4. What should happen to in-flight Worker jobs during graceful termination?
5. Why does automatic Pod restart not provide application-level idempotency?
6. **Challenge:** define readiness, liveness, startup and graceful shutdown semantics for Core API and Worker first on a simple host deployment; then show exactly what Kubernetes would add later.

# 076 — CI/CD Pipeline Explained

## Identification
- **PDF page:** `152`
- **Original archive page:** `290`
- **Related prior material:** `003`, `040`, `048`; later `082`.
- **Classification:** `KEEP CONTROL OBJECTIVES`; tool logos are examples, not requirements.

## SOURCE
The source defines a CI/CD pipeline as automation of building, testing and deploying software, integrating code creation/revision, testing and deployment. The diagram places CI and CD in a loop with example tools around coding, build/test, release/deploy and monitoring.

## Diagram / visual
Examples include source/project tools, build/test tooling, container/orchestration/deployment products and monitoring systems. The figure communicates continuity from **code → build/test → release/deploy → monitor**, but it mixes product categories and does not specify safety gates.

## INFERENCE
A useful pipeline is not the number of automated steps. Its job is to make a release **repeatable, attributable, testable and recoverable**.

## EXTERNAL KNOWLEDGE / caveats
- CI, continuous delivery and continuous deployment are distinct practices; CD does not require every passing commit to automatically reach production.
- A green pipeline does not prove production safety if it omits real provider, migration, restore, security, load or actual-hardware qualification.
- Toolchains need secret isolation, least privilege, protected release credentials, dependency/supply-chain controls, artifact provenance and retention.
- Rebuilding separately per environment undermines “same verified artifact” assurance.
- Deployment must account for schema compatibility, in-flight work, old clients, roll-forward/rollback and post-deploy smoke evidence.
- Monitoring after deploy is part of release validation, not a substitute for pre-release testing.

## Implications for the Current Implementation
SquiFlow already requires:
- one immutable artifact/image with checksum/provenance;
- config/secrets outside artifact;
- fast deterministic merge tests;
- real adapter/integration tests where practical;
- scheduled provider/failure/load tests;
- actual-hardware release qualification;
- migration preflight and compatibility;
- process health **plus authorized smoke journey**;
- explicit rollback/roll-forward/maintenance recovery.

**WHAT WE ARE DOING:** treating CI as one evidence layer and production qualification as a broader release gate.  
**WHY:** the small owned-rack environment has failure modes CI runners cannot reproduce honestly.

## Critical fit interrogation
1. What exact claim does each pipeline stage prove?
2. Which important production risk is **not** tested in ordinary CI?
3. Are we promoting the same immutable bytes, or rebuilding per environment?
4. Who/what can deploy to production and rotate secrets?
5. What happens if schema migration succeeds but the new app fails?
6. How do we know old Workstations and pending durable work remain compatible?
7. What evidence triggers stop/rollback/roll-forward after deployment?

## Critical questions
1. Why is “pipeline passed” not equivalent to “release is safe”?
2. What is the difference between continuous delivery and continuous deployment?
3. Why should artifact provenance/checksum be retained?
4. Which SquiFlow tests belong on every merge versus scheduled/release qualification?
5. Why can binary rollback be unsafe after a destructive schema change?
6. **Challenge:** design the minimum SquiFlow release pipeline for one rack node that is honest about maintenance downtime, schema compatibility, smoke verification and recovery.

# 077 — What are some of the most popular versioning strategies?

## Identification
- **PDF page:** `153`
- **Original archive page:** `293`
- **Related prior material:** `030`, `048`, `067`, `070`; later URL `040`.
- **Classification:** `KEEP VERSION DOMAINS SEPARATE`; no single version scheme fits every SquiFlow contract.

## SOURCE
The page text names:
- **Semantic Versioning (SemVer):** `MAJOR.MINOR.PATCH`, communicating scope of release change.
- **Calendar Versioning (CalVer):** date/year/month based.

The visual additionally shows:
- **Sequential Versioning:** `v1`, `v2`, `v3`.
- **API Versioning** placement examples:
  - request/query parameter;
  - URL component/path;
  - HTTP header / media-type-style header.

## Diagram / visual
The infographic separates:
- release-number **semantics** (SemVer/CalVer/sequential);
- API **version-selection/transport** techniques.

That distinction is important because putting `v1` in a URL does not define the compatibility promise.

## INFERENCE
Versioning works only after answering:
```text
what artifact/contract is versioned?
who consumes it?
what does compatibility mean?
what happens across skipped versions?
how is old usage inventoried and retired?
```

## EXTERNAL KNOWLEDGE / caveats
- SemVer assumes a defined public compatibility surface. Without one, `major/minor/patch` can communicate false precision.
- CalVer communicates release time more than compatibility.
- Sequential numbering is simple but intentionally carries little semantic meaning.
- API path/header/query versioning is an **exposure mechanism**, not the compatibility strategy itself.
- Database schema, API protocol, Workstation sync protocol, durable message, rule/workflow/form snapshot and product release versions may need different evolution rules.
- Compatibility often depends on additive changes, feature negotiation, expand/migrate/contract and explicit retirement—not version number syntax.

## Implications for the Current Implementation
SquiFlow already separates:
- product release;
- HTTP API contract;
- Workstation sync protocol;
- central/local schema;
- Guard↔Workstation IPC;
- durable message/job;
- OpenFGA model/config;
- rule/workflow/form/config snapshots.

- **WHAT WE ARE DOING:** versioning each long-lived boundary according to its consumers and compatibility risk rather than forcing one project-wide SemVer mechanism.
- **WHY:** Workstations can skip releases and durable state can outlive a running binary.
- **OPEN IMPLEMENTATION DETAIL:** exact HTTP API version carrier (URI/header/media type/narrow combination) remains evidence-driven.
- **UNCHANGED:** destructive contraction waits for inventory/drain/compatibility evidence.

## Critical fit interrogation
1. What exactly is being versioned?
2. Who can be older/newer than whom?
3. What does “compatible” mean for that boundary?
4. Can consumers skip versions?
5. Is the version visible for communication, protocol negotiation, data interpretation, or all three?
6. How do we know when an old version is no longer in use?
7. What recovery exists if a version rollout is partially complete?

## Critical questions
1. What does SemVer communicate that CalVer does not?
2. Why is `/v1` not by itself an API compatibility policy?
3. Which SquiFlow version domains can evolve independently?
4. Why can `0.x` still require strict customer-data/client compatibility?
5. What evidence is required before removing an old sync or message version?
6. **Challenge:** a Workstation skips three releases while the central DB schema and sync protocol evolved. Define the compatibility/version checks that prevent partial corruption.

# 078 — The Testing Pyramid

## Identification
- **PDF page:** `154`
- **Original archive page:** `294`
- **Current SquiFlow owner:** `docs/testing/VERIFICATION_STRATEGY.md`.
- **Classification:** `KEEP HEURISTIC / REJECT FIXED TEST QUOTAS`.

## SOURCE
The source defines:
- **Unit Tests:** fast, isolated, low-cost tests of functions/methods/components.
- **Integration Tests:** validate interactions between APIs, databases and external services; slower/more setup.
- **E2E Tests:** full user flows; slow and expensive.
- Cost, execution time and maintenance increase toward the top.

## Diagram / visual
The pyramid is wide at unit tests, narrower for integration, smallest at E2E. The visual suggests “many fast tests, fewer expensive end-to-end tests.”

## INFERENCE
The useful principle is **use the cheapest layer that can prove the real behavior**. The dangerous interpretation is “maximize unit tests even when the risk exists in a real database/provider/process boundary.”

## EXTERNAL KNOWLEDGE / caveats
- The pyramid is a heuristic, not a universal numeric ratio.
- Over-mocked unit tests can pass while real SQL transactions, OIDC, authorization, filesystem, network or process behavior is broken.
- Other useful test types include property tests, contract tests, component/API tests, architecture tests, migration tests, concurrency tests, security tests, failure injection, load tests and restore drills.
- Some systems prefer “testing trophy” or contract-heavy shapes depending on architecture/tooling; the invariant under test should decide.
- E2E tests should be selective and stable, not duplicate every branch already proven lower in the stack.

## Implications for the Current Implementation
SquiFlow's current strategy already asks for the **smallest test layer that proves a real invariant**:
- pure domain/property tests;
- application tests;
- real PostgreSQL/SQLite adapter tests;
- real ZITADEL/OpenFGA integration tests;
- real ASP.NET pipeline/security tests;
- provider contract tests;
- real Guard/Workstation process tests;
- observability runtime tests;
- selective E2E journeys;
- failure injection, migration, restore and actual-hardware qualification.

- **WHAT WE ARE DOING:** optimizing test placement for evidence, not for pyramid percentages.
- **WHY:** SquiFlow's highest-risk defects often live at persistence, identity, process, recovery and offline boundaries that mocks cannot prove.

## Critical fit interrogation
1. What invariant/failure are we trying to prove?
2. What is the **lowest** test layer that can prove it without lying?
3. Does a mock remove the behavior we actually care about?
4. Is a high-cost E2E test duplicating evidence already proven below?
5. Which failure can only be proven with a real provider/process/hardware?
6. What production incident would escape the current test portfolio?
7. What test is missing because it is hard, not because it is unnecessary?

## Critical questions
1. Why are unit tests insufficient for DB transaction/isolation behavior?
2. When is an integration test more valuable than many mocked unit tests?
3. Why should E2E tests remain selective?
4. Which SquiFlow behaviors require actual process or provider tests?
5. Why is restore verification not represented by the ordinary three-layer pyramid?
6. **Challenge:** choose `Workstation local commit → crash → Guard restart → reconnect → authoritative sync`. Partition the evidence across domain, local-store, process, API/OpenFGA/DB and E2E tests without making every scenario one giant E2E test.

## EXTERNAL KNOWLEDGE / caveats

- no production secrets in layers;
- non-root/least privilege;
- only required ports/capabilities/writable storage;
- health/shutdown/drain/resource/temp/log bounds;
- promote same verified image.

- **WHAT WE ARE DOING:** keeping containerization optional until packaging/reproducibility/isolation benefits justify it on the rack.
- **WHY:** containers add a runtime/patching/storage/network layer; they are useful only if that operational trade is positive.
- **IMPORTANT CORRECTION:** “use environment variables” means configuration injection, **not** “store all secrets in plaintext env vars.”

# 080 — Where Do We Cache Data?

## Identification
- **PDF pages:** `157-158`
- **Original archive pages:** `301-302`
- **Related prior material:** `016`, `019`, `021`, `023`, `054`, `059`, `063`; later `085`.
- **Classification:** `KEEP DERIVED-DATA INVENTORY / STRONGLY QUALIFY TERMINOLOGY`; several structures in the source are not caches in the same semantic sense.

## SOURCE
The source says data may be “cached” at:
1. client/browser HTTP cache;
2. CDN;
3. load balancer;
4. messaging infrastructure/Kafka retention;
5. service CPU/RAM/disk caches;
6. distributed cache such as Redis;
7. full-text search such as Elasticsearch;
8. database mechanisms:
   - WAL;
   - buffer pool;
   - materialized view;
   - transaction log;
   - replication log.

The article ends with an important privacy question: with data copied across many levels, how can sensitive user data be completely erased?

## Diagram / visual
The diagram follows traffic from Client → Load Balancer/CDN → API Gateway → services/broker/distributed cache/search → relational DB and places yellow “cached/derived” boxes at each tier. Its strongest lesson is **copy proliferation**: one logical datum can exist in many technical representations.

## INFERENCE
The architectural value of the article is not that every listed mechanism is a cache. It is that **data lifecycle must account for every derived, buffered, indexed, replicated, logged and backed-up copy**.

## EXTERNAL KNOWLEDGE / important corrections
Several source labels are materially simplified:
- Kafka/broker retention is durable message/log storage with delivery/replay semantics; treating it as an ordinary cache can hide retention and correctness obligations.
- Elasticsearch/full-text indexes are derived searchable copies, not merely a latency cache; they need freshness, rebuild and deletion propagation.
- WAL/transaction/replication logs are **durability/replication records**, not caches. They can intentionally retain historical bytes after the current row is changed/deleted.
- A database buffer pool normally caches **pages/blocks**, not simply “query results.”
- A materialized view is persisted derived data and may behave cache-like, but it has explicit refresh/freshness semantics.
- CPU cache is hardware-managed and not equivalent to an application cache with explicit keys/TTL.
- Some reverse proxies/load balancers can cache, but caching is not an inherent property of every load balancer.
- “Complete erasure” can conflict with backups, legal retention, immutable audit, transaction logs and delayed replica/object lifecycle. The product must define what deletion means for each data class and retention basis rather than promise instantaneous physical disappearance everywhere.

## Implications for the Current Implementation
- **WHAT WE ARE DOING:** SquiFlow distinguishes authoritative state from derived/ephemeral/operational copies and already refuses one universal privacy-delete rule before legal/product requirements are known.
- **CACHE AUTHORITY:** browser/CDN/in-process/shared caches are disposable and never payment/stock/tenant/permission authority.
- **SEARCH/PROJECTIONS:** if added, they declare source, tenant/authorization scope, freshness, rebuild and deletion propagation.
- **BROKER/OUTBOX:** durable messages are retained according to delivery/audit/recovery semantics, not silently called cache.
- **DATABASE LOGS/BACKUP:** WAL/logs and backup have recovery/retention purposes and require separate lifecycle handling.
- **PRIVACY OWNER GAP IS INTENTIONAL:** profile/contact data, financial history, security audit, diagnostics, usage records, object files, backups and Workstation-local copies may legitimately have different retention/erasure rules.
- **NO SHARED CACHE ADOPTION:** this article still does not prove SquiFlow needs Redis or another distributed cache.

## Critical fit interrogation
1. What kind of copy is this: cache, replica, queue/log, search index, projection, WAL, backup or authoritative record?
2. What is its source of truth and can it be rebuilt?
3. What is its freshness/retention contract?
4. Does it contain tenant-sensitive or permission-sensitive data?
5. How does deletion/correction propagate, and how long can old bytes remain?
6. Is the copy required for recovery/legal audit, making immediate erasure impossible or inappropriate?
7. What evidence shows the copy is worth its privacy/operations complexity?
8. If the copy is unavailable, what correct degraded behavior remains?

## Critical questions
1. Why is Kafka retention not equivalent to a Redis cache?
2. Why is WAL not a cache?
3. What does a buffer pool actually cache?
4. How is a materialized view different from an ordinary cache entry?
5. Why can a search index require its own deletion/rebuild contract?
6. Which SquiFlow data classes may have different retention rules?
7. Why can “delete immediately from every byte everywhere” conflict with recovery and legal/audit requirements?
8. **Challenge:** a customer asks to delete a user's profile. Trace the request across authoritative DB rows, browser/server caches, search projections, telemetry, objects, Workstation local state, WAL/replication logs and backups, and state which copies should disappear immediately, later, be anonymized, or be retained under an explicit policy.
