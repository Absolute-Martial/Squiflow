# 011 — 12 Algorithms for System Design Interviews

## A. Identification

- **Archive entry:** `011`
- **Title:** *12 Algorithms for System Design Interviews*
- **PDF pages:** `25-26`
- **Original archive pages:** `59-60`
- **Multi-page:** yes
- **Duplicate indexed occurrence:** none

## B. Core concept

### SOURCE

The article presents twelve algorithms/data structures that commonly appear in system-design discussions: Bloom Filter, Geohash, HyperLogLog, Consistent Hashing, Merkle Tree, Raft, Lossy Count, QuadTree, Operational Transformation, Leaky Bucket, Rsync, and Ray Casting.

### INFERENCE

The useful lesson is not “implement these twelve things.” It is to recognize a problem shape and know which established mechanism may solve it. Several items are actually data structures or protocols/techniques rather than algorithms in a narrow academic sense.

## C. Important concepts

### SOURCE

1. **Bloom Filter** — probabilistic membership check; article example is avoiding expensive cache/disk lookups.
2. **Geohash** — spatial encoding for location-based services.
3. **HyperLogLog** — approximate unique-count estimation.
4. **Consistent Hashing** — distributes keys/data around a changing cluster with reduced reshuffling.
5. **Merkle Tree** — hierarchical hashes used to detect replica differences.
6. **Raft** — leader/follower consensus for replicated logs.
7. **Lossy Count** — approximate frequency/heavy-hitter analysis.
8. **QuadTree** — hierarchical spatial subdivision.
9. **Operational Transformation** — concurrent collaborative-editing transformation.
10. **Leaky Bucket** — rate-limiting/traffic-shaping model.
11. **Rsync** — efficient file/directory synchronization using delta-style transfer.
12. **Ray Casting** — geometric visibility/intersection technique.

### EXTERNAL KNOWLEDGE / CAVEATS

- Bloom Filters allow false positives but not false negatives under normal construction; they trade memory for probabilistic accuracy.
- HyperLogLog and Lossy Count trade exactness for bounded memory.
- Consistent hashing does not by itself provide replication, durability, balancing quality, membership safety, or consensus.
- Raft solves replicated-log consensus, not every distributed-system problem.
- Rsync-style byte/file synchronization is fundamentally different from SquiFlow's semantic business synchronization.

## D. Diagram / visual explanation

### SOURCE — PDF page 25

The visual is a 4x3 grid. Each cell shows one mechanism and its conceptual topology:

- Bloom Filter maps an input such as “John” through several hash paths into a bit array.
- Geohash overlays a character grid on a map.
- HyperLogLog shows a stream reduced into a compact bit/register representation and an estimate.
- Consistent Hashing shows keys and nodes placed on a ring.
- Merkle Tree shows parent hashes over child hashes for mismatch localization.
- Raft shows one leader connected to multiple followers.
- Lossy Count shows a stream/frequency histogram reduced into counters.
- QuadTree shows recursive spatial subdivision.
- Operational Transformation shows edits converging through transformation paths.
- Leaky Bucket shows incoming items regulated through a bucket.
- Rsync shows only changed blocks being transferred between two structures.
- Ray Casting shows rays intersecting scene objects.

The visual reinforces that these solve very different classes of problems and are not interchangeable “scale techniques.”

## E. How it works

### SOURCE + EXTERNAL KNOWLEDGE

There is no single common lifecycle; each mechanism has its own:

- Bloom Filter: item → multiple hashes → bit positions → membership test.
- HyperLogLog: item → hash → register update → cardinality estimate.
- Consistent Hashing: hash keys/nodes → place on ring/space → assign key to nearest node rule → remap subset when membership changes.
- Merkle Tree: hash leaves → hash parent groups recursively → compare roots/branches → localize divergence.
- Raft: elect leader → append log entries → replicate to quorum → commit → apply.
- Leaky Bucket: accept arrivals → queue/bucket → release at controlled rate → drop/reject when capacity exhausted.

## F. Why it matters

These mechanisms can reduce memory, reduce data movement, improve availability, coordinate distributed replicas, regulate overload, or support specialized spatial/collaborative workloads. They matter only when the system actually has that problem.

## G. Trade-offs and limitations

- Approximate structures save resources but sacrifice exactness.
- Consensus algorithms add operational complexity and latency but create coordination guarantees.
- Consistent hashing helps redistribution but does not eliminate hotspots or capacity imbalance.
- Merkle trees help compare replicas but still require repair semantics and authoritative conflict rules.
- Rate-limiter algorithms can protect infrastructure but can also reject valid bursts if budgets are poorly chosen.
- OT is complex and unnecessary without real-time collaborative editing.
- Rsync is efficient for files but unsafe as a substitute for domain-aware business synchronization.

## H. Alternatives and comparisons

- Bloom Filter vs exact set: choose probabilistic memory savings only when false positives are acceptable.
- HyperLogLog vs exact `COUNT(DISTINCT)`: approximate analytics vs exact business authority.
- Consistent hashing vs static partition map: dynamic membership flexibility vs operational simplicity.
- Raft vs single authoritative DB/process: distributed fault tolerance vs substantially more coordination cost.
- Rsync vs semantic outbox sync: byte/block transfer vs domain-command/version/conflict semantics.

## I. Real implementation considerations

At 10x/100x scale, approximate data structures can become useful only when exact-memory/query cost is actually limiting. Distributed algorithms become relevant only after there are genuinely independent nodes/replicas requiring membership, ownership, repair or consensus.

Partial failure questions are mechanism-specific: a Raft leader can fail; a consistent-hash node can disappear; an rsync transfer can interrupt; a rate limiter can lose shared counter state. Each mechanism needs explicit recovery/state ownership.

## Implications for the Current Implementation

- **KEEP:** SquiFlow does not implement custom Raft, consistent hashing or Merkle-repair infrastructure now.
- **KEEP:** Workstation sync remains semantic, authenticated, idempotent and conflict-aware; do not replace it with rsync.
- **LATER / SCALE TRIGGER:** Bloom Filter/HyperLogLog/Lossy Count become candidates only for a measured high-volume lookup/analytics problem where approximation is acceptable.
- **KEEP:** rate limiting is required, but use mature platform/runtime mechanisms before writing a custom Leaky Bucket service.
- **AVOID:** OT unless SquiFlow actually introduces simultaneous collaborative editing of the same document/state.

### SOURCE — PDF page 27

The most operationally important visual relationship for SquiFlow is that many application connections imply backend/process/resource cost, while durability and recovery depend on WAL/checkpoint/archive behavior rather than application code alone.

## E. How it works

A client establishes a DB connection → PostgreSQL backend handles the session → query/transaction work uses shared buffers and storage → WAL records changes for crash durability → background/checkpoint/vacuum processes maintain storage and write progress → physical data/log/archive files preserve database state and recovery evidence.

## F. Why it matters

Understanding PostgreSQL at this level matters because an application can be logically correct while failing operationally due to connection pressure, WAL growth, checkpoint spikes, vacuum lag, disk exhaustion or long recovery.

## G. Trade-offs and limitations

- Process-per-connection architecture means connection count has real memory/process cost.
- WAL improves durability/recovery but consumes I/O and disk and needs retention discipline.
- Checkpoints bound recovery work but can create write/I/O bursts.
- Autovacuum protects MVCC storage health but consumes resources and can fall behind.
- Replication/archiving improve resilience but add storage, network and operational obligations.
- PostgreSQL's broad feature set is not a reason to force every workload into one database.

## H. Alternatives and comparisons

- PostgreSQL vs embedded SQLite/libSQL: central multi-user authority vs local embedded/offline store.
- PostgreSQL vs specialized NoSQL/key-value: relational transactions/invariants vs workload-specific distribution/data model.
- direct high connection counts vs bounded pooling: simplicity at small load vs predictable backend resource consumption.

## I. Real implementation considerations

For SquiFlow, representative tests need connection pool wait, backend memory/process cost, WAL growth during reconnect/import bursts, checkpoint latency, autovacuum under update/delete churn, temp/sort spill, crash recovery, archive/log retention and disk-full behavior. Database performance must be measured with the actual tenant and sync workload, not synthetic SELECT-only traffic.

## Implications for the Current Implementation

- **KEEP:** PostgreSQL remains the strongest central reference candidate, but still not silently final until Phase 3 POC closes the decision.
- **IMPROVE NOW (already captured in plan):** Phase-3 proof includes operational internals, not just SQL correctness/RLS.
- **NEEDS MEASUREMENT:** pool size, WAL/checkpoint behavior, vacuum, sort/temp spill, disk growth and recovery time.
- **KEEP:** Workstation database remains a separate local-store decision; this article does not justify PostgreSQL on the desktop.

## D. Diagram / visual explanation

### SOURCE — PDF page 29

The infographic is a 3x4 grid. It visually distinguishes HTTPS transport, OAuth resource-owner/authorization-server flow, WebAuthn relying party/authenticator, API-key signing, authorization allow/deny, rate-limiter filtering, API-version paths, allowlist policy, OWASP review, API gateway routing, safe error messages and validation before application handling.

A critical visual lesson is layering: these controls sit at different boundaries and no single box replaces the others.

## E. How it works

A production request should traverse secure transport → authentication/session validation → tenant/context resolution → coarse endpoint policy → input/schema validation → resource loading → current resource authorization → domain/concurrency checks → effect → safe result/error, with rate/admission and observability spanning the path.

## F. Why it matters

API compromise can cross tenant boundaries, expose data, automate expensive flows, or execute privileged functions. Security therefore requires identity, authorization, input control, resource limits and safe failure behavior together.

## G. Trade-offs and limitations

- HTTPS protects transport, not authorization/business validity.
- OAuth2 is a framework, not a magic authorization policy for application resources.
- WebAuthn improves authentication security but does not decide SquiFlow permissions.
- API keys are useful for machine/integration identity but create rotation/revocation/least-privilege obligations.
- IP allowlists are supplementary and can be brittle behind NAT/mobile/cloud networks.
- rate limiting can protect capacity but can also deny legitimate burst traffic.
- gateways centralize edge concerns but can become a false single security authority.
- strict validation can reject forward-compatible clients if versioning is poorly designed.

## H. Alternatives and comparisons

- user OIDC session vs API key: human interactive identity vs machine/integration credential.
- gateway policy vs backend authorization: edge protection vs authoritative resource/domain decision.
- IP allowlist vs identity authorization: network-origin constraint vs user/service permission.

## I. Real implementation considerations

At larger scale, attackers exploit object IDs, expensive endpoints, pagination/batch amplification, recovery/login flows, provider callbacks and cross-tenant mistakes. Every endpoint needs audience classification, bounded input/output, resource authorization and observability. Security controls must also fail safely when ZITADEL/OpenFGA/provider dependencies are unavailable.

## Implications for the Current Implementation

- **KEEP:** ZITADEL owns primary interactive authentication, MFA/passkey/WebAuthn capability.
- **KEEP:** OpenFGA + SquiFlow resource/domain checks remain authoritative; gateway authentication cannot replace them.
- **KEEP:** HTTPS/TLS, endpoint inventory, input/property allowlists, safe errors and rate/admission controls are already explicit requirements.
- **LATER / SCALE TRIGGER:** API keys only for a concrete partner/service integration requiring machine credentials.
- **AVOID:** building a separate SquiFlow WebAuthn/password/authentication subsystem.
- **IMPROVE NOW:** none beyond already-owned application-security gates; exhaustive review confirms them.

# 015 — SQS vs SNS vs EventBridge vs Kinesis

## A. Identification

## B. Core concept

### SOURCE

The article distinguishes four AWS messaging categories by semantics: SQS queue, SNS publish/subscribe notification, EventBridge event routing/bus, and Kinesis high-volume streaming.

## C. Important concepts

- queue / competing-consumer work;
- topic-based fan-out;
- event bus rules/filters;
- real-time stream ingestion;
- producer/consumer decoupling;
- one-consumer job examples;
- multi-subscriber notification/event examples;
- high-volume clickstream examples.

## D. Diagram / visual explanation

### SOURCE — PDF page 33

The visual has four quadrants:

- **SQS:** several Lambda producers feed one queue and a consumer Lambda receives work.
- **SNS:** an S3 event feeds an SNS topic that fans out to SQS, mobile, Lambda and email endpoints.
- **EventBridge:** CodePipeline/Lambda/EC2 produce events; rules route them to Lambda/SNS/SQS/Step Functions/services.
- **Kinesis:** multiple producers feed Kinesis Data Streams; multiple consumer applications process the stream.

The diagram's most useful contribution is the different fan-out/ownership/replay-flow shape, not the AWS branding.

## E. How it works

Queue: producer → durable queue → one processing path/competing consumers → acknowledge/retry.

Pub/sub: publisher → topic → independent subscribers each receive the event.

Event bus: producers → event envelope → rules/filters → selected targets.

Stream: producers → ordered/partitioned stream → consumers with their own processing positions/offset semantics.

## F. Why it matters

Choosing the wrong messaging semantics creates hidden duplication, lost ownership, poor replay behavior or unnecessary infrastructure. Queue, pub/sub, bus and stream solve different coordination problems.

## G. Trade-offs and limitations

- Queues simplify single-work ownership but do not provide independent replay to many consumers by default.
- Pub/sub enables fan-out but multiplies delivery, retry and failure obligations.
- Event buses improve routing flexibility but can hide ownership/choreography and become difficult to reason about.
- Streams support high throughput/replay but require partitioning, offset, retention and consumer-lag operations.
- Managed AWS products add provider-specific operational/cost semantics that do not map directly to SquiFlow's owned-rack deployment.

## H. Alternatives and comparisons

For SquiFlow semantics:

- one durable PDF/notification/reconciliation job → DB-backed queue/job first;
- several independent consequences from one committed fact → outbox fan-out/pub-sub semantics when real;
- complex event routing among many independent systems → event bus only when topology earns it;
- durable replay/independent offsets/high throughput → stream platform only when measured.

## I. Real implementation considerations

At 10x load, queue age/fairness/backpressure matter before broker brand. At 100x or many consumers, independent replay/retention may justify stream infrastructure. Duplicates, out-of-order delivery, poison messages, consumer crashes and external-effect ambiguity must be handled regardless of product.

## Implications for the Current Implementation

- **KEEP:** first Worker workload should use simplest durable DB-backed job/outbox mechanism that satisfies semantics.
- **KEEP:** distinguish command/job from committed event.
- **LATER / SCALE TRIGGER:** pub/sub/event bus/stream infrastructure only when real multi-consumer/routing/replay workloads appear.
- **AVOID:** adopting AWS messaging products merely because the source compares them; SquiFlow is not currently AWS-hosted.
- **AVOID:** Kafka/event-stream infrastructure for ordinary durable background jobs.

4. compressed request/response payloads;
5. several callers sharing a connection pool to a database.

The visual implicitly shows that each optimization moves cost rather than erasing it: pagination adds cursor/page state, async logging adds buffers, cache adds invalidation, compression adds CPU, pooling adds bounded shared connections.

## E. How it works

Request → bound result size/page → reuse existing DB connection when available → optionally serve safe cached data → compress sufficiently large response → emit telemetry through bounded asynchronous path → response.

## F. Why it matters

These techniques reduce payload size, connection setup overhead, database load and synchronous logging I/O. They improve latency/throughput only when the optimized cost is significant.

## G. Trade-offs and limitations

### SOURCE CAVEAT + EXTERNAL KNOWLEDGE

The article describes pagination as “streaming” result sets; pagination and streaming are different mechanisms. Pagination normally issues bounded page requests, while streaming incrementally transfers one response/sequence.

- pagination can produce unstable results if ordering/cursors are poorly defined;
- async logging can lose telemetry under crash/saturation unless the buffer policy is explicit;
- cache can return stale or cross-tenant data if keys/invalidation are wrong;
- compression saves bandwidth but costs CPU and is wasteful on already-compressed media/small bodies;
- connection pools improve reuse but can saturate the DB or leak session/tenant state if reset semantics are wrong.

## H. Alternatives and comparisons

- offset vs cursor/keyset pagination: simple random page vs stable/efficient traversal under large mutable datasets.
- cache vs direct authoritative read: latency/load improvement vs freshness/complexity.
- async telemetry vs authoritative audit: lossy performance path vs durable security/business record.
- larger pool vs queue/admission: more concurrent DB work vs bounded database protection.

## I. Real implementation considerations

At 10x traffic, cache misses, connection-pool waits and log volume can amplify load. At 100x, stampedes, pool saturation and compression CPU can become the bottleneck. Performance changes must be observed with p95/p99 latency, dependency time, allocations, payload bytes, DB pool wait and cache hit/miss rather than request average alone.

## Implications for the Current Implementation

- **KEEP:** bounded pagination and request/page sizes.
- **KEEP:** bounded asynchronous telemetry, with authoritative audit separate.
- **NEEDS MEASUREMENT:** caching, compression and pool sizes.
- **KEEP:** caches never become authority for payment/stock/credit/current authorization/hard limits.
- **KEEP:** DB pool tests include tenant-context reset/isolation.
- **AVOID:** adding Redis solely because “cache improves API performance.”

# 017 — HTTP/1 -> HTTP/2 -> HTTP/3

## A. Identification

## B. Core concept

### SOURCE

The article presents HTTP evolution from HTTP/1.x over TCP, through HTTP/2 multiplexing/prioritization/header compression over TCP, to HTTP/3 over QUIC/UDP.

## C. Important concepts

- HTTP 0.9/1.0/1.1 timeline;
- persistent connections;
- pipelining;
- headers/status codes;
- HTTP/2 binary framing;
- multiplexed streams;
- stream prioritization;
- HPACK header compression;
- server push;
- TCP transport for HTTP/1.x and HTTP/2;
- QUIC over UDP for HTTP/3.

### EXTERNAL KNOWLEDGE / CAVEATS

The timeline is simplified. HTTP/3 was standardized after the early QUIC adoption period; exact protocol support should be treated as deployment/runtime capability rather than business logic. Server Push is not a reason to design around HTTP/2; modern client support/usage has changed substantially.

## D. Diagram / visual explanation

### SOURCE — PDF page 37

The visual shows a timeline (HTTP 0.9 → HTTP 1 → 1.1 → 2 → 3), an HTTP/1 request/response sequence over a TCP connection, HTTP/2 multiplexed request streams through binary framing, a server-push example, and HTTP/3 carrying HTTP requests/responses over QUIC.

The key architectural boundary is that application-level HTTP semantics can remain stable while transport behavior changes underneath.

## E. How it works

HTTP/1.x serializes/request-pipelines work over TCP connections → HTTP/2 introduces binary framing and multiplexes multiple logical streams over a TCP connection → HTTP/3 maps HTTP semantics onto QUIC over UDP with integrated transport/security behavior.

## F. Why it matters

Protocol evolution can reduce connection overhead and head-of-line effects, improve multiplexing and network behavior, especially on lossy/mobile links. But application correctness should not depend on one negotiated HTTP version unless a feature truly requires it.

## G. Trade-offs and limitations

- HTTP/1.1 is widely compatible but can need more connections/serialization.
- HTTP/2 multiplexes streams but TCP-level packet loss can still affect the connection.
- HTTP/3 improves transport behavior over QUIC but requires compatible clients, edge/proxies, firewall/UDP paths and observability.
- newer transport versions add operational/debug complexity and may fall back depending on network path.

## H. Alternatives and comparisons

Choose protocol support based on client/edge/runtime compatibility and measurements. Do not build separate business APIs solely for HTTP version. gRPC may rely on HTTP/2 semantics in its native form, while normal REST APIs can often negotiate HTTP versions transparently.

## I. Real implementation considerations

Measure handshake/connect latency, throughput, stream concurrency, packet-loss behavior and proxy support. Test fallback. Ensure retries/idempotency remain application-level concerns. For Workstation sync, a long-lived streaming design must test real edge/proxy connection lifetime, not assume HTTP/2 success from localhost.

## Implications for the Current Implementation

- **KEEP:** HTTP/1.1/2/3 negotiation remains infrastructure/runtime detail.
- **KEEP:** SquiFlow command/idempotency/authorization semantics do not depend on one HTTP generation.
- **NEEDS MEASUREMENT:** exact edge/proxy configuration and whether HTTP/3 materially improves current workloads.
- **KEEP:** gRPC POC must verify actual HTTP/2/streaming behavior through the selected edge.
- **AVOID:** “upgrade to HTTP/3” as an application-architecture project without measured transport need.

## E. How it works

A key-value/distributed store maps keys to values → partitions ownership among nodes → replicates data according to topology → uses consistency/conflict mechanisms to reconcile reads/writes → discovers/members nodes → serves operations under the chosen consistency/availability model.

## H. Alternatives and comparisons

Relational DB vs key-value: cross-row constraints/joins/transactions vs simple key access/distribution.

Embedded local store vs distributed KV: offline/local simplicity vs shared multi-node availability.
