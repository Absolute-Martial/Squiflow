# 002 — Docker vs. Kubernetes. Which one should we use?

## A. Identification
- **Archive entry:** `002`
- **PDF pages:** `7-8`
- **Original archive pages:** `14-15`
- **Multi-page:** yes
- **Exact duplicate indexed occurrence:** none
- **Related topics:** `003` IaC, `025/108` virtualization vs containerization, `053/075` Kubernetes, `079` Docker best practices, `040/048/076/082` deployment and CI/CD.

## B. Core concept
### SOURCE
Docker packages and runs applications in isolated containers on a host. Kubernetes orchestrates containerized applications across a cluster and automates placement, scaling, load balancing and desired-state management.

### INFERENCE
The real choice is not “Docker or Kubernetes” as equivalent substitutes. Containerization and orchestration solve different layers of the deployment problem.

## C. Important concepts
### SOURCE
- containers and packaged dependencies;
- isolation at application/container level;
- host operating system;
- Docker as container runtime/platform;
- Kubernetes cluster;
- master/control functionality versus worker hosts;
- multiple hosts/nodes;
- load balancing;
- scaling;
- desired-state management;
- networking/security/storage complexity across hosts.

### EXTERNAL KNOWLEDGE / CAVEATS
- Multiple containers do **not** automatically require Kubernetes. One host can run several containers using simpler service/container tooling.
- Kubernetes normally uses a CRI-compatible runtime rather than requiring Docker Engine itself.
- Kubernetes adds its own control-plane, networking, storage, security, upgrade and observability obligations.

## D. Diagram / visual explanation
### SOURCE — PDF page 7
The left side shows an app and dependencies inside containers above Docker, then OS and hardware, emphasizing a single-host container runtime. The right side shows Kubernetes managing containers across hosts/nodes, emphasizing a cluster-level control boundary. The comparison is about **scope of management**, not a claim that the technologies are mutually exclusive.

## E. How it works
1. Build/package application with dependencies into an image/container.
2. Run container(s) on a host with a container runtime.
3. If cluster orchestration is introduced, declare desired workloads/resources to Kubernetes.
4. Kubernetes schedules workloads to nodes, maintains desired replica state and exposes/network-routes workloads through cluster abstractions.
5. Controllers reconcile actual state toward desired state after failures or scaling changes.

## F. Why it matters
Containerization improves repeatability and isolation of deployments. Orchestration matters when multiple hosts, replicas, failover/reconciliation, rolling deployment and dynamic placement become operational problems.

## G. Trade-offs and limitations
**Docker/containerization advantages:** simple packaging, repeatability, lower overhead than full VMs, local reproducibility.  
**Costs:** image/runtime maintenance, storage/network mapping, patching, registry supply-chain concerns.

**Kubernetes advantages:** declarative reconciliation, scheduling, rolling updates, service discovery, replica management, autoscaling ecosystem.  
**Costs:** control-plane overhead, networking/storage complexity, certificate/RBAC/secrets management, cluster upgrades, more failure modes, steeper operational burden.

**Bad choice:** Kubernetes on a small single-node system when the actual problem is merely “run a few processes/containers reliably.”

## H. Alternatives and comparisons
- **Bare/system services:** best when process count is small and OS-level deployment is simpler.
- **Containers without Kubernetes:** useful for repeatable packaging/isolation on one/few hosts.
- **VMs:** stronger isolation/OS separation at higher resource cost.
- **Kubernetes:** justified when cluster reconciliation/orchestration is a real recurring need.

## I. Real implementation considerations
At 10×/100× load, ask whether the bottleneck is application/DB capacity or deployment placement. Kubernetes does not fix an overloaded DB or bad query. A control-plane outage, node partition, image-pull failure, storage unavailability or bad rollout can break service even if the application code is healthy. Rollback also depends on schema compatibility, not only replica replacement.

## Implications for the Current Implementation
- **KEEP:** SquiFlow does not introduce HTTP/gRPC microservices or Kubernetes merely because multiple executables exist.
- **KEEP:** containerization remains allowed for packaging/isolation.
- **LATER / SCALE TRIGGER:** Kubernetes only after real multi-node placement, replica reconciliation, rollout/failover/service-discovery/scaling pain exceeds simpler deployment automation.
- **NEEDS MEASUREMENT:** actual rack resource cost and operational value of container versus direct-host packaging.
- **AVOID:** treating Kubernetes as a scalability prerequisite before measuring the actual bottleneck.

**New architecture decision required now?** No. Existing trigger-driven Kubernetes policy remains appropriate.

## Critical questions
### Foundation
1. What problem does Docker solve that Kubernetes does not replace?
2. What additional scope does Kubernetes manage beyond one container host?
3. What does desired-state reconciliation mean?
### Critical reasoning
1. Why can an application need multiple containers yet still not need Kubernetes?
2. Why does Kubernetes not automatically make a system scalable?
3. Which operational problem should exist before adding a cluster control plane?
4. Why can a database remain the bottleneck after horizontal application scaling?
### Trade-off
1. Compare systemd/host services, Docker Compose-style deployment and Kubernetes for one rack node.
2. What operational capability justifies Kubernetes' resource/complexity cost?
3. When are VMs preferable to containers?
### Failure / edge case
1. What happens if the Kubernetes control plane is unavailable while existing pods keep running?
2. What happens when a rollout deploys code incompatible with the current database schema?
3. How should storage-dependent workloads behave when a node is replaced?
### Implementation
1. What measurements would tell SquiFlow it has outgrown a single-node deployment?
2. Which deployment state belongs in Git versus backup versus secret storage?
3. How would you test node loss before claiming Kubernetes improves availability?
### System design
1. Design a progression from one SquiFlow rack node to three nodes without adopting Kubernetes prematurely.
2. Compare container orchestration with application-level Worker queue scaling.
### Challenge

# 003 — A Cheatsheet on Infrastructure as Code Landscape

## A. Identification
- **Archive entry:** `003`
- **PDF pages:** `9-10`
- **Original archive pages:** `20-21`
- **Multi-page:** yes
- **Related:** `002`, `037`, `040`, `048`, `076`, `079`, `082`.

## B. Core concept
### SOURCE
Infrastructure can be provisioned/configured from versioned code. The article places containerization, Kubernetes orchestration, IaC tools such as Terraform/CloudFormation/Ansible, and GitOps in one deployment-management landscape.

### INFERENCE
The durable architectural goal is **reproducibility and controlled change**, not adoption of a specific IaC brand.

## C. Important concepts
### SOURCE
- repeatable infrastructure;
- availability/performance/cost benefits;
- containerization;
- orchestration;
- infrastructure definitions as code;
- version control;
- testing/reuse;
- Terraform/CloudFormation;
- Ansible/configuration management;
- GitOps;
- CI/CD-triggered infrastructure/configuration changes.

### EXTERNAL KNOWLEDGE / CAVEATS
- Containerization is packaging/runtime isolation, not identical to IaC.
- Configuration management, resource provisioning and application deployment are distinct concerns even when one tool spans several.
- GitOps adds a reconciliation workflow; it is not automatically necessary for a small deployment.
- State/secrets are not safely solved by “put everything in Git.”

## D. Diagram / visual explanation
### SOURCE — PDF page 9
The infographic has separate panels: containerized apps over Docker/OS/infrastructure; Kubernetes applying desired configurations to worker nodes; an IaC panel where developers push/pull infrastructure code through automation to cloud/on-prem servers; Terraform provisioning cloud resources through provider APIs; Ansible using playbooks/inventories over SSH; and a Git-driven CI/CD/source-of-truth panel. The visual actually shows several **different control loops**, which is more important than the list of tools.

## E. How it works
1. Express infrastructure/deployment intent in version-controlled definitions.
2. Review/test the change.
3. Apply through provisioning/configuration/deployment tooling.
4. Reconcile or verify actual environment state.
5. Record artifacts/configuration versions and recover/rebuild from the same definitions plus protected state/secrets.

## F. Why it matters
IaC reduces undocumented manual drift, improves repeatability, reviewability, disaster rebuild, environment consistency and change traceability.

## G. Trade-offs and limitations
Advantages: reproducibility, code review, automation, easier rebuild, auditable changes.  
Costs: tool/state management, credentials, provider/version drift, destructive-plan risk, secret handling, bootstrap problem, false confidence if restore is untested.

Bad choice: introducing Terraform/Kubernetes/GitOps ceremony when a versioned service definition + script/runbook already fully reproduces the real environment.

## H. Alternatives and comparisons
- **Shell/runbook + system service definitions:** valid minimal IaC/deploy-as-code for a simple host if deterministic and tested.
- **Ansible:** useful for host configuration and repeatable imperative/declarative machine setup.
- **Terraform:** strong when provisioning external infrastructure resources through APIs and state is managed carefully.
- **GitOps:** useful when continuous reconciliation from Git solves drift/scale problems.
- **Kubernetes manifests:** only after Kubernetes itself is justified.

## I. Real implementation considerations
Architect-derived concerns: secrets must live outside ordinary Git; stateful data must not be destroyed by repeat application; DB migrations need compatibility/rollback rules; configuration drift must be detectable; exact runtime versions should be pinned enough for rebuild; disaster recovery must work if original host is gone; infrastructure definitions themselves need backup/access recovery.

## Implications for the Current Implementation
- **KEEP:** paying-customer deployment must be reproducible from version-controlled definitions/runbooks.
- **IMPROVE NOW (Phase 0 requirement already accepted):** make `deploy/` real as soon as implementation starts; do not leave environment creation as tribal shell history.
- **NEEDS MEASUREMENT / OPEN:** exact mechanism—direct host services, containers, Ansible, Terraform or combination.
- **LATER / SCALE TRIGGER:** GitOps/Kubernetes only if reconciliation/orchestration complexity emerges.
- **AVOID:** putting tenant/business settings or secrets into Git merely to call them IaC.

**New architecture decision required now?** No; the exposure strengthens an already-accepted Phase-0/production requirement.

# 004 — A Crash Course on Architectural Scalability

## A. Identification
- **Archive entry:** `004`
- **PDF pages:** `11-12`
- **Original archive pages:** `22-23`
- **Related:** `031/096`, `063`, `080`, `095`, `097`, `119`.

## B. Core concept
### SOURCE
Scalability is the ability to handle increased workload using a repeatable, financially viable strategy. The article names centralized components, high-latency components and tight coupling as bottlenecks, and presents load balancing, caching, event-driven processing and sharding as common techniques.

## C. Important concepts
- finite scalability / cost effectiveness;
- centralized bottleneck / SPOF;
- high-latency work;
- coupling;
- statelessness;
- loose coupling;
- asynchronous processing;
- load balancing;
- caching;
- event-driven processing;
- sharding.

### EXTERNAL KNOWLEDGE / CAVEATS
Statelessness and async processing are not universal requirements. Some domains require authoritative state and synchronous decisions. Sharding can dramatically increase data/operational complexity and should follow measured limits, not precede them.

## D. Diagram / visual explanation
### SOURCE — PDF page 11
The visual places “No system is infinitely scalable” at the center, connects bottlenecks (centralized components, high latency, tight coupling) to scaling techniques, and shows load balancing, caching, event-driven handling and sharding as different responses. It is a menu of techniques rather than a single mandatory architecture.

## E. How it works
1. Measure workload and bottleneck.
2. Classify the limiting resource/path.
3. Choose a scaling technique that targets that constraint.
4. Re-measure because the bottleneck moves.
5. Repeat only while operational/economic cost remains justified.

## F. Why it matters
Scalability planning prevents both overload and premature distributed-system complexity. The most valuable lesson is to tie a technique to a concrete bottleneck.

## G. Trade-offs and limitations
- **Load balancing:** improves horizontal capacity/availability, but requires stateless/shared-state handling and does not fix shared DB bottlenecks.
- **Caching:** lowers latency/load but creates freshness, invalidation, memory and stampede risks.
- **Async/event-driven:** absorbs bursts and decouples work but adds queues, retry, ordering, duplicate and eventual-result semantics.
- **Sharding:** expands data capacity but complicates transactions, queries, rebalancing, keys and operations.

## H. Alternatives and comparisons
Scale **up** before scale **out** when hardware headroom and operational simplicity make it economical. Optimize query/index/algorithm before distributing. Use queues for bursty long-running work; use synchronous processing when the user must know authoritative success now.

## I. Real implementation considerations
At 10× traffic, DB connection pool, query plans, disk I/O, Worker backlog or external dependencies may fail before API CPU. At 100×, tenant skew and reconnect storms matter. Every technique needs capacity metrics, saturation signals, admission/backpressure and a rollback/degradation plan.

## Implications for the Current Implementation
- **KEEP:** SquiFlow defines finite capacity profiles rather than claiming infinite scale.
- **NEEDS MEASUREMENT:** identify first real bottleneck on actual rack/workload.
- **LATER / SCALE TRIGGER:** cache, replicas, sharding, extra nodes, service extraction after evidence.
- **KEEP:** central authoritative DB is allowed until measured capacity/recovery evidence says otherwise.
- **AVOID:** “stateless/event-driven/sharded everywhere” as generic architecture doctrine.

**New architecture decision required now?** No.

## Critical questions
### Foundation
1. What makes a scaling strategy repeatable and cost-effective?
2. Name the three bottleneck classes highlighted by the article.
3. Which four scaling techniques are shown?
### Critical reasoning
1. Why can load balancing fail to improve throughput?
2. Why does a cache often move rather than remove complexity?
3. How can async processing improve resilience while weakening immediacy?
4. Why is a centralized database not automatically bad architecture?
### Trade-off
1. Scale up versus scale out for a small owned rack.
2. Cache versus index/query optimization.
3. Queue versus synchronous request for document generation.
4. Sharding versus a larger single DB node.
### Failure / edge case
1. What happens during a cache stampede?
2. What happens when many offline Workstations reconnect simultaneously?
3. What happens when queue consumers are down for hours?
4. What happens when one tenant dominates a shared resource?
### Implementation
1. Define a capacity envelope for Core API, DB and Worker.
2. Which saturation metrics should trigger the next scaling move?
3. How would you protect OpenFGA/ZITADEL from reconnect storms?
### System design
1. Evolve SquiFlow from 100 to 10,000 concurrent devices without choosing techniques before metrics.

# 005 — Cookies Vs Sessions Vs JWT Vs PASETO

## A. Identification
- **Archive entry:** `005`
- **PDF pages:** `13-14`
- **Original archive pages:** `26-27`
- **Related:** `008`, `010`, `022`, `039`, `043`, `061`, `074`, `086`, `109` and URL `052`.

## B. Core concept
### SOURCE
The article compares server-side session state referenced by a cookie, self-contained JWTs, and PASETO as a token design with stronger cryptographic defaults.

### INFERENCE
These are not perfectly equivalent categories: a cookie is a browser storage/transport mechanism, a server session is a state model, JWT/PASETO are token formats, and authentication protocols/identity providers sit above them.

## C. Important concepts
- authentication (“who are you?”);
- cookies;
- session IDs;
- server-side session store;
- session scalability concern;
- JWT header/payload/signature;
- stateless/self-contained token idea;
- token theft/expiration;
- PASETO versions/purpose/local/public framing visible in the diagram;
- stronger crypto defaults / reduced algorithm-choice footguns.

### EXTERNAL KNOWLEDGE / CAVEATS
- JWT payloads are normally encoded, not encrypted by default.
- Server sessions can scale with shared/durable session infrastructure; they are not inherently unscalable.
- “Stateless JWT” shifts state/freshness/revocation problems rather than eliminating all server-side state.
- PASETO is not automatically compatible with OIDC ecosystems, so adopting it can conflict with a standards-based identity provider strategy.

## D. Diagram / visual explanation
### SOURCE — PDF page 13
The infographic has four panels: authentication categories; cookie/session login and subsequent request flow; JWT structure and bearer-style request flow; and a PASETO structure showing version, purpose and payload plus public/private key concepts. The visual contrasts **where state/trust information lives**.

## E. How it works
**Session:** authenticate → create server session → issue session ID cookie → browser sends cookie → server looks up/validates session.  
**JWT:** authenticate → issuer creates signed token → client sends token → verifier validates signature/claims/expiry.  
**PASETO:** issuer creates token using a constrained version/purpose scheme → verifier/decryptor processes according to the selected purpose and keys.

## F. Why it matters
Session/token design affects revocation, security, scaling, browser exposure, distributed deployments and authorization freshness.

## G. Trade-offs and limitations
- **Server sessions:** strong server-side revocation/control; cost is shared state, session storage, affinity/distribution decisions.
- **JWTs:** portable verification and broad ecosystem; cost is bearer-token theft risk, claim staleness, key/issuer validation, revocation complexity.
- **PASETO:** safer algorithm-selection design; cost is ecosystem/tooling/standard compatibility and still requires key lifecycle, expiry and authorization design.
- **Cookies:** secure when HttpOnly/Secure/SameSite + CSRF defenses are correct; unsafe if misconfigured or used as proof of authorization by themselves.

## H. Alternatives and comparisons
For browser apps, server-managed sessions often provide simpler revocation/control. For APIs/native clients, standards-based OAuth/OIDC access/refresh mechanisms often fit better. Token format should follow the selected identity protocol/provider unless a concrete independent token need exists.

## I. Real implementation considerations
Multi-node Web deployments need a shared/durable session/revocation story or a design that avoids process-local authority. Short token lifetimes reduce stale claims but increase refresh/provider dependency. Stolen bearer tokens remain usable until expiry/revocation controls intervene. Current authorization should not be frozen into long-lived authentication claims.

## Implications for the Current Implementation
- **KEEP:** ZITADEL owns identity/authentication through OIDC/OAuth.
- **KEEP:** Workstation uses system-browser Authorization Code + PKCE `S256`.
- **KEEP:** OpenFGA/current server state remains authorization authority; token/session form does not replace it.
- **NEEDS MEASUREMENT / OPEN:** exact Web cookie/session + Blazor topology in Phase 1.
- **AVOID:** custom JWT or PASETO authentication subsystem alongside ZITADEL.
- **LATER / SCALE TRIGGER:** shared session/revocation infrastructure only if chosen multi-node Web topology requires it.

**New architecture decision required now?** No.

## Critical questions
### Foundation
1. Where does authoritative session state live in a server-session model?
2. What three structural parts does a JWT contain?
3. What security-design goal does PASETO claim to improve?
### Critical reasoning
1. Why is a cookie not the same architectural concept as a JWT?
2. Why does “stateless JWT” not mean “no state exists anywhere”?
3. Why can a valid old token still represent stale authorization?
4. Why can server sessions scale despite the article's simplified warning?
### Trade-off
1. Browser session cookie versus bearer JWT in browser storage.
2. Short-lived token versus long-lived token.
3. PASETO versus OIDC-provider-issued JWT-style tokens for SquiFlow.
### Failure / edge case
1. What happens if ZITADEL is unavailable while a valid Web session exists?
2. What happens after an Owner revokes Staff permission but the Staff still has an unexpired token?
3. How do multi-node Web servers avoid process-local session loss?
4. What happens when a refresh token is stolen?
### Implementation
1. Where should SquiFlow perform OpenFGA checks relative to session/token validation?
2. Which cookie attributes and CSRF controls matter for a server-managed Web session?
3. How should logout differ from permission revocation?
### System design
1. Design authentication/session handling for Web + Workstation + Admin Web using one identity provider but separate authorization scopes.
2. Design safe tenant switching for one user belonging to multiple tenants.
### Challenge
A user is authenticated, has an unexpired identity token, but their tenant membership and OpenFGA permission were revoked while their Workstation was offline. Describe every check needed before accepting the pending command.

## I. Real implementation considerations

# 007 — 10 Essential Components of a Production Web Application

## A. Identification
- **Archive entry:** `007`
- **PDF pages:** `17-18`
- **Original archive pages:** `34-35`
- **Related:** `040`, `046`, `048`, `084`, `098`, `103`, `106`, `110`, `116`, `120`.

## B. Core concept
### SOURCE
The article sketches a typical production Web system: CI/CD, browser/DNS, load balancer/reverse proxy, CDN, Web/API/backend servers, database/cache, Worker/job queue, search, logging/monitoring and alerts.

## C. Important concepts
- CI/CD deployment;
- DNS;
- load balancer/reverse proxy;
- CDN;
- Web app/API/backend separation;
- database;
- distributed cache;
- Worker/job queue;
- full-text search;
- logging/monitoring;
- alerts/incident response.

### EXTERNAL KNOWLEDGE / CAVEATS
Not every production application needs a distributed cache or dedicated search service. Missing from the generic diagram are backup/restore, identity/authorization, tenant isolation, secrets, object storage, security controls, certificate/time health, admission control and private recovery.

## D. Diagram / visual explanation
### SOURCE — PDF page 17
The visual follows user traffic through DNS/edge/load-balancing into Web/backend servers, with side branches to CDN/search/notification-like outputs, database/cache and Workers. CI/CD enters from the developer side; logging/monitoring and alerts sit cross-cutting. It is a topology inventory, not a requirement that every box be separately deployed.

## E. How it works
Developer commit → CI/CD builds/tests/deploys → browser resolves DNS → edge/load balancer routes → Web/API/backend executes → DB/cache/search/Worker dependencies are used as needed → monitoring records behavior → alerts fire on detected problems.

## F. Why it matters
Production reliability depends on supporting systems around business code: routing, deployment, durable storage, background work, visibility and recovery.

## G. Trade-offs and limitations
Each additional component adds capacity and specialization but also credentials, upgrades, backup/recovery, monitoring and failure modes. CDN/cache/search can improve performance but introduce staleness. Worker queues improve responsiveness but require retry/idempotency/backlog operations. Load balancing helps redundancy only if state/dependencies support it.

## H. Alternatives and comparisons
A small system can combine Web/API/app functionality in fewer processes and use DB-backed jobs before adopting a broker, direct DB queries before dedicated search, and no cache before measured need. Separation should follow workload/security/failure boundaries.

## I. Real implementation considerations
Ask what happens when DNS, edge, DB, identity, authorization, object store, Worker or monitoring is down. Track queue age, DB saturation, certificate expiry, backup restore status and noisy-tenant capacity. A monitoring platform is not a substitute for authoritative audit or backups.

## Implications for the Current Implementation

## E. How it works

Step-up authentication is distinct from authorization. Multi-tenant users must map identity to SquiFlow membership and selected TenantContext rather than trusting an IdP org/role claim as business authority.

## B. Core concept

Database performance depends on workload characteristics—read/write/delete mix, item/data size, dataset size, concurrency, consistency, HA and geography—and can be improved through indexing, sharding/partitioning, denormalization, replication and locking techniques.

## C. Important concepts

### EXTERNAL KNOWLEDGE / CAVEATS
- Partitioning and sharding are related but not synonymous; partitioning may remain within one DB instance.
- Replicas can introduce read lag/freshness concerns.
- Denormalization trades write/integrity complexity for read convenience and should not corrupt authoritative invariants.
- Locks are correctness tools first; performance depends on contention scope/duration.
- Connection pooling, query plans/statistics, vacuum/maintenance, storage/WAL/checkpoints and schema design can dominate real performance.

## D. Diagram / visual explanation
### SOURCE — PDF page 21
The infographic groups “what impacts performance” above a set of strategies. It visually compares access patterns and techniques rather than presenting one universal optimizer. Tables/index sketches, sharding/replication and locking illustrations connect workload shape to different interventions.

## E. How it works
1. Characterize workload and consistency requirements.
2. Measure slow/hot queries and resource saturation.
3. Optimize schema/query/index access path.
4. Control concurrency/transaction contention.
5. Add replicas/partitioning/sharding/denormalization only when the specific measured constraint requires them.
6. Re-measure write/storage/maintenance costs introduced by the optimization.

## F. Why it matters
Database latency commonly dominates application latency and concurrency correctness. Poor tuning can cause lock amplification, connection exhaustion, write spikes, disk growth or tenant unfairness.

## G. Trade-offs and limitations
- **Indexes:** fast reads, extra write/storage/maintenance cost.
- **Sharding:** horizontal capacity, high operational/query/transaction complexity.
- **Denormalization:** fewer joins, duplicate/stale data risk and harder writes.
- **Replication:** read availability/scale, lag/failover/consistency complexity.
- **Locking:** protects invariants, can reduce concurrency or deadlock if overused.

## H. Alternatives and comparisons
Optimize query/schema/index before distributed DB changes. Use optimistic concurrency where conflicts are rare; pessimistic locking when an invariant requires serialization around scarce state. Read replicas are for suitable stale/read workloads, never permission/payment/stock authority unless freshness contract allows it.

## I. Real implementation considerations
10× offline reconnects can turn a normally read-heavy app into a bursty write workload. Tenant skew can make average metrics misleading. Connection pools must fit DB memory/process capacity. Query-plan regressions appear only at realistic cardinalities. Backup/migration/maintenance and disk-full behavior must be tested as part of performance operations.

## Implications for the Current Implementation
- **IMPROVE NOW (already Phase-3 gate):** record a real SquiFlow workload profile before selecting/tuning central DB.
- **KEEP:** normalized authoritative schema; no denormalization/EAV/JSON for core invariants merely for UI convenience.
- **NEEDS MEASUREMENT:** indexes, pool sizes, DB adapter and PostgreSQL operational behavior.
- **LATER / SCALE TRIGGER:** replicas/sharding only after measured capacity/freshness need.
- **KEEP:** per-invariant concurrency mechanism, not one global lock/isolation level.
- **AVOID:** using stale projections/replicas as payment/credit/stock/authorization authority.

# 010 — JWT 101: Key to Stateless Authentication

## A. Identification
- **Archive entry:** `010`
- **PDF pages:** `23-24`
- **Original archive pages:** `51-52`
- **Related/duplicates:** related `005`, `008`, `039`, `043`, `074`, `086`, `109`; exact archive↔URL title overlap with URL `052`, which remains separately unprocessed until its own URL page.

## B. Core concept
### SOURCE
A JWT is presented as an open standard for transmitting information between parties. The article explains three sections—header, payload and signature—and symmetric versus asymmetric signing.

## C. Important concepts
- JWT/JWS-style compact token structure;
- header;
- algorithm metadata;
- payload/claims;
- registered/public/private claims;
- signature;
- symmetric secret signing/verification;
- asymmetric private-key signing/public-key verification;
- authentication/authorization use cases.

### EXTERNAL KNOWLEDGE / CAVEATS
- A normal signed JWT is **not encrypted**; header and payload can be decoded by anyone who receives it.
- A signature provides integrity/authenticity relative to the trusted signing key; it does not make every claim semantically trustworthy without issuer/audience/time/protocol validation.
- JWT is a token format, not a complete authentication or authorization architecture.
- Algorithms must be constrained by trusted configuration; do not accept arbitrary algorithm choice from the token.

## D. Diagram / visual explanation
### SOURCE — PDF page 23
The infographic shows header, payload and signature as three connected token sections; a client/server authentication flow; and symmetric versus asymmetric signing. The visual's key distinction is who possesses which signing/verifying key.

## E. How it works
1. Issuer constructs header and claims.
2. Header/payload are encoded.
3. Issuer signs them with configured symmetric secret or private key.
4. Client presents token.
5. Verifier checks signature using the shared secret or public key and validates relevant claims/protocol context.
6. Application then performs its own current authorization/domain checks.

## F. Why it matters
JWTs are common in OAuth/OIDC ecosystems and allow verifiers to validate signed claims without querying the issuer for every request. This can improve decoupling but creates freshness/revocation/key-validation responsibilities.

## G. Trade-offs and limitations
Advantages: interoperable ecosystem, compact signed claims, asymmetric verification distribution.  
Limitations: bearer theft risk, stale claims, revocation complexity, key rotation/JWKS availability, clock skew, audience/issuer mistakes, accidental sensitive data exposure, token-size overhead, confusing authentication with authorization.

## H. Alternatives and comparisons
- Server session: stronger centralized revocation/control, requires session state.
- Opaque reference token: introspection/server lookup trades local verification for central freshness/control.
- PASETO: different safer-default token design but not a reason to abandon OIDC provider interoperability without need.
- JWT within OIDC: accept only as part of the configured trusted provider/protocol, not arbitrary user-signed tokens.

## I. Real implementation considerations
Validate issuer, audience, signature/allowed algorithms, expiry/not-before as applicable, keys and OIDC/OAuth transaction semantics. Cache signing keys carefully with rotation behavior. Never put sensitive secrets in readable claims. Do not use long-lived permission claims as the only authorization truth.

## Implications for the Current Implementation
- **KEEP:** SquiFlow trusts configured ZITADEL OIDC/OAuth identity context, not arbitrary JWTs.
- **KEEP:** stable identity key is `(issuer, subject)`, not email.
- **KEEP:** OpenFGA/current SquiFlow state remains authorization authority.
- **AVOID:** custom JWT issuance/authentication subsystem.
- **IMPROVE NOW when Phase 1 is implemented:** explicit issuer/audience/signature/time/nonce/state validation through standards-compliant middleware and hostile tests.
- **LATER / SCALE TRIGGER:** key-cache/session multi-node behavior only when chosen topology requires it.

**New architecture decision required now?** No.

### Failure / edge case
