# 061 — Tokens vs API Keys

## A. Identification
- **PDF pages:** `123-124`
- **Original archive pages:** `236-237`
- **Related prior material:** `005`, `008`, `010`, `013`, `022`, `039`, `043`, `045`, `060`; later `069`, `074`, `087`, `109` deepen identity/access/API-authentication themes.
- **Classification:** `FIT BY PRINCIPAL / BOUNDARY`; neither token nor API key is a universal replacement for the other.

## B-C. Core concept and important concepts — SOURCE
The source contrasts two simplified authentication/authorization flows.

**Token flow:** end user logs into a frontend; credentials go to an Identity Service; a JWT is returned; the frontend sends it in the `Authorization` header; an API Gateway validates signature, expiry and claims; a valid request reaches a user-authenticated service and database.

**API-key flow:** a third-party developer registers through a Developer Portal; an API key is issued and also stored in a secure key store; the developer application sends the key in a header; the API Gateway asks an API-key-validation service to verify it; valid traffic reaches a public API service and then the database.

Important source concepts are therefore: human/user login, identity service, JWT, developer portal, API key issuance, key store, gateway interception, verifier/validation service, user-authenticated API versus public/developer API, and downstream application/database access.

## D. Diagram / visual explanation
The visual deliberately forks the traffic by **principal type and credential lifecycle**. The green token path begins with an end user and interactive login; the blue API-key path begins with a third-party developer and provisioning portal. Both converge at the API Gateway but use different validation components before being forwarded to different service surfaces. The diagram also makes credential issuance/storage part of the design rather than showing credentials magically appearing at request time.

## E-F. How it works and why it matters
A credential presented to an API is useful only if the receiver can validate who/what it represents, what audience/scope it applies to, whether it is still valid, and what authorization must run afterward. Tokens are especially useful when identity/session/delegation claims and expiry are part of the request context. API keys are useful when an application/developer integration needs a simple provisioned secret/identifier. The two can coexist because they solve different credential-distribution and principal-lifecycle problems.

## G-H. Trade-offs, limitations, alternatives — INFERENCE + EXTERNAL KNOWLEDGE
- A cryptographically valid JWT is not current SquiFlow business authorization. Tenant membership, OpenFGA/resource permission and domain state remain separate.
- An API key should not become a permanent bearer master password. Production design needs key ID/prefix, secret generation, secure-at-rest representation, scope, owner/application binding, expiry or rotation policy, revocation, audit, leak response, rate/admission controls and log redaction.
- Storing raw API-key secrets is often unnecessary; verification can use a strong one-way representation or a secret-management pattern appropriate to the validation design.
- Long-lived bearer API keys have larger theft windows than short-lived tokens. OAuth client credentials, signed requests or mTLS may be better when short-lived machine identity, delegated scopes, proof-of-possession or stronger client authentication is required.
- JWT validation at a gateway can be useful, but backend authorization cannot simply trust that “gateway validated token” if the backend can be reached through another path or if resource authorization depends on current state.
- API keys can identify an integration/client without identifying the end user behind it; if end-user delegation matters, OAuth/OIDC-style tokens are usually a better semantic model.

## Implications for the Current Implementation
- **USED NOW — interactive identity:** SquiFlow uses ZITADEL through OIDC/OAuth for Web/Workstation authentication because standards-based issuer/subject/session/MFA/SSO behavior fits human identity. SquiFlow does not create its own JWT authority merely because JWT appears in the source.
- **USED NOW — authorization:** OpenFGA plus SquiFlow TenantContext/domain validation remains current application permission authority; token claims do not replace it.
- **USED/PLANNED FOR SERVICE ADMINISTRATION:** where Core/Admin needs ZITADEL API access, the existing identity owner doc calls for a dedicated least-privilege service account/client rather than a blanket instance-owner secret.
- **POSITIVE FUTURE FIT — API keys:** if SquiFlow exposes a developer/public integration API where a third-party application needs a simple revocable client credential and there is no end-user delegation requirement, API keys are a legitimate candidate.
- **ALTERNATIVE FIT:** OAuth client credentials or another short-lived machine credential can be better for integrations needing scoped token issuance/rotation/federation; mTLS can be better where possession of a client certificate is part of the trust contract.
- **ADOPTION GATE:** no developer API-key subsystem is added until a concrete external integration needs one. If added, prove scope, storage/verification, rotation, revocation, leak response, per-key rate limits, tenant binding, audit and secret-redaction behavior.
- **UNCHANGED:** clients never receive central DB credentials; credential validation never bypasses backend tenant/resource/business authorization.

## Critical questions
**Foundation**
1. What lifecycle difference separates the token flow from the API-key flow in the source?
2. Why does a gateway need a verifier rather than simply checking that a credential header exists?
3. What is the difference between identifying a developer application and identifying an end user?

**Critical reasoning / trade-offs**
4. Why can a valid JWT still be insufficient to authorize a refund?
5. Why can a long-lived API key be operationally simpler but riskier after leakage?
6. When would OAuth client credentials be a better fit than an API key?

**Failure / edge cases**

**Implementation / system design**

# 062 — 5 Data Structures That Make DB Queries Super Fast

## A. Identification
- **PDF pages:** `125-126`
- **Original archive pages:** `240-241`
- **Related prior material:** `009`, `012`, `036`, `038`, `051`, `054`, `055`, `058`; later `085`, `097`, `113` continue data/query topics.
- **Classification:** `KEEP / NEEDS MEASUREMENT`; index/data structure selection is workload- and provider-specific.

## B-C. Core concept and important concepts — SOURCE
The source describes five structures used for different query patterns:
1. **B-Tree** — balanced ordered tree with keys/data pointers in internal and leaf nodes; supports point and range queries.
2. **B+ Tree** — internal nodes guide search while data pointers live in linked leaves; sequential leaf access helps range queries.
3. **Hash Index** — hashes a key to a bucket; optimized for equality search, not ranges.
4. **Bitmap Index** — bit arrays represent values; bitwise operations support filtering and are described as useful for low-cardinality categorical data.
5. **Inverted Index** — maps each term/value to row/document IDs containing it; supports full-text search.

## D. Diagram / visual explanation
The infographic uses one panel per structure: branching ordered trees for B/B+, a bucket lookup for hash, bit columns for bitmap, and term-to-posting-list relationships for inverted indexing. The visual is valuable because it shows that “index” is not one algorithm: physical shape follows access pattern.

## E-F. How it works and why it matters
An index spends storage and write/maintenance work to create an access path that can avoid scanning all rows. Ordered trees preserve sortable order; hash structures trade ordering for direct equality lookup; bitmap structures exploit compact boolean operations over low-cardinality dimensions; inverted indexes reverse the document→term relation to term→documents. The best structure depends on predicates, sort/range behavior, cardinality, update rate, dataset size and DBMS implementation.

## G-H. Trade-offs, limitations, alternatives — EXTERNAL KNOWLEDGE
- More indexes are not automatically better: each can increase write latency, WAL/log volume, storage, cache pressure, vacuum/maintenance and migration time.
- B-tree versus B+ tree terminology is implementation-specific; many production database “B-tree” indexes are B+-tree-like in leaf behavior.
- PostgreSQL's ordinary B-tree and hash indexes do not map one-for-one to every infographic category. PostgreSQL has no general persistent bitmap-index feature identical to Oracle-style bitmap indexes; the planner can instead use bitmap index/heap scans and combine ordinary indexes.
- PostgreSQL full-text/array/document workloads often use GIN (inverted-index-like behavior), while GiST/BRIN and expression/partial/covering indexes solve other access patterns not shown.
- Hash indexes do not support ordering/range and can be inferior to a good B-tree when one index must support multiple query shapes.
- Inverted indexes are excellent for search but introduce index build/update/storage cost and tokenization/language/query semantics.

## Implications for the Current Implementation
- **CURRENT FIT:** SquiFlow's Phase-3 persistence proof already requires representative queries, actual plans, tenant skew, index benefit and write/WAL/storage cost. This article reinforces that rule.
- **B-tree family:** likely useful for many IDs, tenant-scoped predicates, dates/ranges and ordering in a relational store, but exact index keys/order are determined from real query shapes.
- **Hash:** positive candidate for narrow equality-only workloads only when the selected provider/benchmark shows benefit over its normal B-tree path.
- **Bitmap-style filtering:** positive analytical/filtering concept, but do not assume a persistent bitmap index exists or is best in the selected PostgreSQL topology.
- **Inverted indexing:** positive fit for real full-text/document/search requirements; PostgreSQL native text/GIN or OpenSearch can be evaluated according to search quality, scale, freshness and operations—not because “inverted index is fastest.”
- **UNCHANGED:** indexes are derived performance structures; constraints and authoritative business state remain in the database/domain model.

## Critical questions
1. Why can a B-tree support a range query while a hash index generally cannot?
2. What advantage do linked B+ tree leaves provide?
3. Why do bitmap structures fit low-cardinality filtering better than arbitrary high-cardinality write-heavy data?
4. How does an inverted index reverse the normal document→term relationship?
5. Why can adding an index make reconnect/import throughput worse?
6. What evidence would justify hash over B-tree for one SquiFlow query?
7. Why should the index taxonomy be translated through the selected DBMS rather than copied literally?
8. How would tenant skew affect composite-index selectivity and column order?
9. Which metrics prove an index is beneficial overall rather than only for one benchmarked read?
10. **Challenge:** one query filters `TenantId`, sorts by `CreatedAt`, and searches a customer-name phrase. Explain why one universal index structure may not solve all three dimensions and design the evidence needed for the final access path.

# 063 — How can Cache Systems go wrong?

## A. Identification
- **PDF pages:** `127-128`
- **Original archive pages:** `246-247`
- **Related prior material:** `016`, `019`, `021`, `023`, `054`, `059`; later `080`, `085` deepen cache placement/lifecycle.
- **Classification:** `KEEP CACHE FAILURE CONTRACT`; this article is not itself a reason to add a shared cache.

## B-C. Core concept and important concepts — SOURCE
The source presents four cache failures:
1. **Thunder herd** — many keys expire together and requests fall through to the DB; source suggests expiry jitter and preventing non-core traffic from reaching the DB until cache recovers.
2. **Cache penetration** — requested key exists in neither cache nor DB, causing repeated misses; source suggests caching null/negative results or using a Bloom filter.
3. **Cache breakdown** — a hot key expires and many callers hit the DB; source suggests no expiry for hot keys.
4. **Cache crash** — cache outage sends all requests to the DB; source suggests a circuit breaker or cache cluster.

## D. Diagram / visual explanation
Each panel shows Application → cache → Database and highlights how the failure moves traffic from the fast layer to the authoritative layer. The solutions column shows TTL jitter, negative/Bloom filtering, hot-key retention and circuit-breaker/cluster ideas. The key visual lesson is **miss amplification**: cache failure can make the database fail too.

## E-F. How it works and why it matters
Caching improves the common path by serving derived/reusable data, but its failure path can concentrate requests on slower dependencies. A safe cache design therefore requires not just hit rate but bounded repopulation, negative lookup behavior, cold-start strategy, outage behavior and authoritative fallback policy.

## G-H. Trade-offs, limitations, alternatives — EXTERNAL KNOWLEDGE
- “Never expire hot keys” is unsafe as a universal rule. It can create indefinite staleness; versioned/invalidation-driven refresh or refresh-ahead may be safer.
- Caching null values needs bounded TTL and correct tenant/config/query dimensions; otherwise a newly created record can remain incorrectly “absent.”
- Bloom filters have false positives and need rebuild/update lifecycle; they are only hints, never authority.
- A circuit breaker that blocks both cache and DB can protect the database but creates deliberate service degradation; the affected endpoints and fallback must be explicit.
- Cache clustering improves availability but adds replication/failover/consistency/cost and can still fail due to bad configuration, network partition or shared overload.
- Request coalescing/single-flight, stale-while-revalidate/stale-if-error for safe data, load shedding and admission control are other useful techniques.

## Implications for the Current Implementation
SquiFlow's current API contract already requires a cache proposal to define authority/bypass, safe key dimensions, TTL/invalidation, size/eviction, stampede/miss amplification, negative lookups, cold-start, outage and privacy behavior.
- **CURRENT FIT:** no cache is allowed to become payment, stock, credit, tenant or authorization authority.
- **POSITIVE FIT:** in-process/edge/shared caches can all be useful where measured repetition and a safe freshness contract exist.
- **POSITIVE FIT:** TTL jitter, bounded request coalescing and negative caching can protect PostgreSQL for suitable lookup workloads.
- **LATER:** a Redis/Memcached/shared-cache cluster remains a workload-specific candidate; the existence of cache failure patterns does not prove SquiFlow currently needs one.
- **FAILURE CONTRACT:** cache outage may reduce performance or disable non-critical derived reads, but it must not cause unbounded DB/retry storms or grant access.

## Critical questions
1. How does thundering herd differ from one hot-key breakdown?
2. Why can querying nonexistent IDs become an attack against both cache and DB?
3. What correctness problem can indefinite hot-key caching create?
4. Why is cache clustering not the same as business-data HA?
5. When is negative caching safe and what should invalidate it?
6. How can a circuit breaker protect PostgreSQL while intentionally reducing availability?
7. What is request coalescing and why can it outperform simply increasing cache capacity during a miss storm?
8. Which SquiFlow data can safely serve stale-if-error and which cannot?
9. What metrics reveal miss amplification before the database collapses?
10. **Challenge:** a shared cache restarts after deployment and 10,000 Workstations reconnect. Design the repopulation/admission strategy without turning PostgreSQL into the next failed component.

# 064 — 8 System Design Concepts Explained in 1 Diagram

## A. Identification
- **PDF pages:** `129-130`
- **Original archive pages:** `248-249`
- **Related prior material:** `004`, `007`, `015`, `031`, `041`, `048`, `052`, `053`, `060`; current owner: `docs/requirements/NON_FUNCTIONAL_REQUIREMENTS.md`.
- **Classification:** `KEEP NFR DISCIPLINE`; the eight mechanism pairings are illustrative, not one-to-one guarantees.

## B-C. Core concept and important concepts — SOURCE
The source defines non-functional requirements as system quality attributes and pairs eight with implementation approaches:
1. Availability → load balancers.
2. Latency → CDNs.
3. Scalability → replication.
4. Durability → transaction log.
5. Consistency → eventual consistency.
6. Modularity → loose coupling + high cohesion.
7. Configurability → configuration-as-code.
8. Resiliency → message queues.

## D. Diagram / visual explanation
The visual is an eight-panel matrix. Each panel has a quality label and a small architecture sketch: multiple service instances behind a load balancer, edge/CDN path, replicas, transaction log, asynchronously converging replicas, cohesive modules, version-controlled configuration and producer/queue/consumer buffering. It is best read as a **catalog of relationships**, not proof that one box solves one NFR.

## E-F. How it works and why it matters
NFRs describe behavior under load, failure and real operating conditions. Architecture mechanisms help meet them, but each quality must be translated into a measurable/falsifiable contract: what stays true, what can degrade, what dependency is authoritative, how recovery works and what evidence proves it.

## G-H. Trade-offs, limitations, alternatives — EXTERNAL KNOWLEDGE
- A load balancer improves availability only when multiple independently healthy backends and dependencies exist; it cannot remove a shared DB/rack/identity-provider SPOF.
- A CDN lowers latency mainly for cacheable/edge-servable work; it does not make transactional DB work local.
- Replication can improve read capacity/availability but does not generically scale writes and introduces lag/failover/consistency choices.
- Transaction/WAL logs are a durability mechanism only with durable storage, correct flush/commit policy and recovery; backup/DR are still separate.
- Eventual consistency is **one consistency model**, not “the way to achieve consistency.” Protected invariants may require current/strong authority instead.
- Loose coupling/high cohesion improve modularity but over-abstraction can make systems harder to understand.
- Configurability is broader than configuration-as-code. SquiFlow also needs safe runtime/admin-managed configuration with versioning, authorization and rollback.
- Message queues can isolate bursts and retries, but introduce durable-delivery, duplicate, poison-message, lag and broker-outage semantics.

## Implications for the Current Implementation
- **CURRENT FIT:** SquiFlow's NFR owner document is stronger than the infographic because each material requirement must define normal/failure/edge behavior, authority, consistency, capacity, recovery, compatibility, observability and acceptance evidence.
- **Availability:** keep honest single-node/rack failure limits until redundant dependencies/topology actually exist.
- **Latency/scalability:** optimize measured bottlenecks; CDN, replicas or new nodes are candidates only for the workload they help.
- **Durability:** DB transaction log/WAL, local SQLite durability, object integrity and backup/restore each own different durability scopes.
- **Consistency:** select per invariant; eventual/derived is allowed only with source/freshness/rebuild semantics.
- **Modularity/configurability:** current modular-monolith and managed Admin/configuration approach fits; do not turn “configuration-as-code” into YAML-only product administration.
- **Resiliency:** queues/outbox are useful for durable async effects, while synchronous authoritative operations retain explicit failure/degraded behavior.
- No owner-document change is required; the batch confirms the accepted NFR model.

## Critical questions
1. Why can a load balancer exist while the system still has one availability SPOF?
2. Why does replication not automatically scale writes?
3. What must be true for a transaction log to provide the durability users expect?
4. Why is eventual consistency a model rather than a universal consistency solution?
5. How can loose coupling become over-engineering?
6. What is the difference between configuration-as-code and safe runtime product configuration?
7. Which SquiFlow NFRs are hard invariants versus operational targets?
8. Which metrics would make “low latency” or “resilient” an actual acceptance requirement?
9. **Challenge:** choose one SquiFlow capability and map availability, latency, durability, consistency and recovery without assigning a different infrastructure product to each NFR by default.

# 066 — What is the SOLID Principle?

## A. Identification
- **PDF pages:** `133-134`
- **Original archive pages:** `260-261`
- **Exact later URL-title overlap:** URL `014` remains independently pending.
- **Related prior material:** `028`, `032`, `035`; next `068` Clean Architecture.
- **Classification:** `KEEP PRINCIPLES / AVOID CEREMONY`.

## B-C. Core concept and important concepts — SOURCE
The source defines SOLID as guidelines for code that is easier to understand, modify and extend:
- **SRP:** a class has one reason to change / one well-defined responsibility.
- **OCP:** software entities are open for extension, closed for modification.
- **LSP:** a derived object can replace its base without breaking correctness.
- **ISP:** clients/components should not be forced to depend on interface members they do not use.
- **DIP:** high-level and low-level modules depend on abstractions rather than directly on each other.

## D. Diagram / visual explanation
The visual contrasts red “bad” and green “good” class/interface arrangements. It emphasizes separating unrelated responsibilities, adding behavior by extension, preserving substitutability, splitting broad interfaces and directing dependencies toward abstractions.

## E-F. How it works and why it matters
SOLID is useful when it reduces reasons that unrelated changes break one another and creates replaceable/testable boundaries around genuinely variable dependencies. It is most valuable as design pressure toward cohesion and explicit contracts, not as a requirement to maximize class/interface count.

## G-H. Trade-offs / caveats — EXTERNAL KNOWLEDGE
- SRP means one coherent reason to change, not “one method per class.”
- OCP does not forbid modifying code; excessive plugin abstractions for hypothetical change can be worse than changing simple code safely.
- LSP is behavioral contract compatibility, not merely matching a method signature.
- ISP discourages fat client-facing contracts, but too many microscopic interfaces can create navigation/DI/test overhead.
- DIP says policy should not depend on volatile details; it does **not** mean “create an interface for every concrete class.”
- Composition is often preferable to inheritance when substitutability is difficult to guarantee.

## Implications for the Current Implementation
- **CURRENT FIT:** repository rules already reject `IService`/`IRepository<T>`/one-interface-per-class ceremony while preserving real provider/replacement boundaries such as object/backup storage and identity/authorization adapters.
- **SRP/cohesion:** Guard, Core API, future Admin API and Worker have different security/failure/runtime reasons to change and therefore justify real process/project boundaries where documented.
- **DIP:** domain/application code should depend on SquiFlow semantics rather than provider SDK types; infrastructure provides adapters.
- **ISP:** provider interfaces remain narrow and expose only SquiFlow-needed semantics.
- **OCP:** new provider adapters can extend a real replacement seam, but ordinary modules remain simple/in-process until a real extension boundary exists.
- **LSP:** replacement providers must preserve the SquiFlow contract, including failure/recovery semantics—not merely compile against the same interface.
- No owner change required; this batch confirms the current anti-ceremony abstraction rule.

## Critical questions
1. What does “one reason to change” mean in a domain module?
2. Why is an interface-per-class architecture not automatically DIP?
3. What behavioral property makes LSP harder than matching signatures?
4. When can OCP create speculative complexity?
5. How can a fat provider interface violate ISP?
6. Which current SquiFlow interfaces are justified by a real replacement boundary?
7. Why does a provider adapter need to preserve failure semantics to be substitutable?
8. When does process separation represent SRP/fault isolation rather than over-engineering?
9. **Challenge:** design a storage abstraction that allows provider replacement without exposing provider SDKs or inventing a generic interface hierarchy for every file operation.

# 067 — Common HTTP Status Codes

## A. Identification
- **PDF pages:** `135-136`
- **Original archive pages:** `262-263`
- **Related prior material:** `017`, `018`, `026`, `033`, `044`, `045`, `060`; owner: `docs/api/API_CONTRACT_IDEMPOTENCY_AND_RETRY.md`.
- **Classification:** `KEEP`.

## B-D. SOURCE and visual
The source defines the five classes: `1xx` informational, `2xx` success, `3xx` redirection, `4xx` client error and `5xx` server error. The visual expands this with common examples including `100`, `101`, `200`, `201`, `204`, `301`, `302`, `304`, `400`, `401`, `403`, `404`, `429`, `500`, `501`, `502`, `503`, and `504`.

## E-F. How it works and why it matters
Status codes communicate the HTTP-level outcome category to clients, proxies and tooling. They matter for retry, user behavior, cache/redirect handling and operational diagnosis, but a status alone rarely captures the full SquiFlow business reason. Structured failure codes/problem details provide the semantic layer.

## G-H. Trade-offs / caveats — EXTERNAL KNOWLEDGE
- `401 Unauthorized` is historically named but semantically means acceptable authentication credentials are missing/invalid; authenticated-but-not-permitted is normally `403`.
- `404` can be used intentionally for non-disclosure/enumeration resistance according to endpoint policy.
- `409 Conflict` and `412 Precondition Failed` are distinct: domain/workflow conflict versus failed conditional version/precondition are useful separate contracts.
- `422` can distinguish syntactically valid but semantically invalid content where useful.
- `429` should expose retry timing where meaningful and clients must not immediately hammer again.
- `5xx` is not automatically retryable; deterministic server defects should not become infinite retry storms. `502/503/504` often indicate transient dependency/gateway conditions but still require bounded policy.
- `202 Accepted` is meaningful only when the server has actually accepted durable asynchronous work/status tracking.

## Implications for the Current Implementation
The current API owner already has a stable mapping for malformed requests, authentication, forbidden, nondisclosed/not found, domain conflict, stale precondition, validation, rate limiting, unexpected defects and gateway/dependency failures.
- **KEEP:** HTTP status + SquiFlow failure code/problem details stay consistent.
- **KEEP:** retry classification is based on semantics, not `4xx bad / 5xx retry` slogans.
- **KEEP:** `429` and `Retry-After` integrate with bounded client backoff/admission.
- **KEEP:** `202` is reserved for a durable operation resource.
- **UNCHANGED:** no status code can grant authorization or replace idempotency/concurrency evidence.

## Critical questions
1. Why is `401` different from `403`?
2. When might `404` be safer than revealing a forbidden resource exists?
3. What should distinguish `409` from `412` in SquiFlow?
4. Why is every `500` not a safe retry signal?
5. What contract should accompany `429`?
6. When is `202 Accepted` dishonest?
7. Why do stable application failure codes still matter when HTTP already has status codes?
8. How should a Workstation treat timeout/response loss when the server may have committed?
9. **Challenge:** map malformed payload, expired login, forbidden refund, stale quote version, DB overload and upstream provider timeout to HTTP + SquiFlow failure semantics and retry behavior.

# 068 — How Clean Architecture Works?

## A. Identification
- **PDF page:** `137`
- **Original archive page:** `264`
- **Related prior material:** `028`, `032`, `035`, `066`; current owner: repository/dependency boundaries.
- **Classification:** `KEEP DEPENDENCY DIRECTION / AVOID LITERAL RING CEREMONY`.

## B-C. Core concept and important concepts — SOURCE
The source presents four layers whose dependencies point inward:
1. **Entities** — core business rules/logic, independent of external systems/frameworks.
2. **Use Cases** — application operations that orchestrate entities and interfaces without caring about display/storage detail.
3. **Interface Adapters** — Controllers, Presenters and Gateways translating external formats to/from inner layers.
4. **Frameworks and Drivers** — database, web UI, devices and other external tools on the outside.

## D. Diagram / visual explanation
The concentric-rings visual places enterprise/business rules at the center, application business rules around them, then interface adapters, then frameworks/drivers. Arrows show source-code dependency directed inward even though runtime data/control can flow in and out through adapters. Controller/presenter examples demonstrate how external inputs and outputs cross the boundary.

## E-F. How it works and why it matters
The design protects stable business policy from volatile frameworks/providers. Outer composition creates concrete adapters and injects them through narrow inner contracts. This improves testing and provider replacement when those boundaries are real.

## G-H. Trade-offs / caveats — EXTERNAL KNOWLEDGE
- Clean Architecture is a dependency rule, not a requirement for exactly four projects, one class per ring or a network service per layer.
- Runtime call flow can move outward through an abstraction while source-code dependencies still point inward.
- Domain purity has diminishing returns if every trivial data operation receives multiple forwarding layers.
- Database constraints and provider-specific capabilities are still important; keeping SDK types out of domain code does not mean pretending infrastructure behavior does not exist.
- Cross-cutting security, tenancy, observability and transactions need explicit composition and cannot be “solved” by the rings alone.

## Implications for the Current Implementation
- **CURRENT FIT:** SquiFlow's repository rule already keeps provider SDK types out of domain/business models and creates narrow infrastructure seams only for real replacement/security/fault boundaries.
- **CURRENT FIT:** business modules remain modular-monolith/in-process; Clean Architecture does not justify converting layers into services.
- **CURRENT FIT:** Core API, Workstation, Guard and future Admin/Worker are composition/runtime boundaries justified by platform/fault/security needs, not Clean-Architecture ring count.
- **AVOID:** generic repository/unit-of-work/service-manager forwarding layers solely to mimic a diagram.
- **TESTING:** inner business rules can be tested without live providers; adapter contract/integration tests still prove real DB/ZITADEL/OpenFGA/storage behavior.

# 069 — How Does SSO Work?

## A. Identification
- **PDF pages:** `138-139`
- **Original archive pages:** `268-269`
- **Related prior material:** `008`, `022`, `039`, `043`, `061`; later `074`, `087`, `109`.
- **Classification:** `USED / KEEP` through the selected identity platform; do not build a parallel SSO system.

## B-C. Core concept and important concepts — SOURCE
The source describes SSO as one login used across different systems. A user requests a protected Service Provider (Gmail), is redirected to an Identity Provider (IdP), logs in, receives a secure token while the IdP creates a session, returns the token to Gmail, and Gmail validates it before serving allowed content. When the same user later visits another SSO-integrated Service Provider (Slack), it redirects to the IdP; because the IdP session already exists, login is skipped, a new token is created for Slack, Slack validates it and grants access.

## D. Diagram / visual explanation
The visual shows browser/user, two service providers and an identity provider, with redirects and token exchanges. The important second half is not “reuse the Gmail token”; it is **reuse the IdP session to issue a new token/response for the second SP**.

## E-F. How it works and why it matters
SSO centralizes the authentication ceremony and reduces repeated credential prompts. Each relying application still needs its own client/relying-party registration, response validation, local session and authorization. The IdP session creates convenience but also a larger authentication dependency/blast radius.

## G-H. Trade-offs / caveats — EXTERNAL KNOWLEDGE
- The source is protocol-neutral. Real SSO may use OIDC/OAuth or SAML and must validate issuer, audience/client, signature, expiry and transaction-binding values such as `state`/`nonce` where applicable.
- One IdP login does not mean one bearer token should be replayed to every application; tokens/assertions are audience/client scoped.
- IdP outage can block new authentication/step-up even while some existing application sessions continue according to policy.
- Single logout is not automatic; application session, provider session, refresh capability and back-channel/front-channel logout are separate concerns.
- Central authentication does not centralize SquiFlow tenant/resource authorization.
- Account suspension, tenant membership changes or device revocation may require current SquiFlow checks even if the IdP session remains valid.

## Implications for the Current Implementation
- **USED NOW:** ZITADEL is the selected identity/authentication platform and SquiFlow uses standards-based OIDC for Web/Workstation authentication because this gives centralized identity, MFA/passkey/SSO/federation capability without custom credential logic.
- **CURRENT SSO SEMANTICS:** an authenticated ZITADEL subject can move between SquiFlow relying applications according to configured session/policy, but each application still validates its own flow/session.
- **UNCHANGED AUTHORITY:** SquiFlow derives TenantContext/membership and asks OpenFGA/domain checks after authentication. A ZITADEL organization/claim or successful SSO alone never authorizes business records.
- **STEP-UP:** high-risk operations can require recent/stronger ZITADEL authentication; SSO convenience does not suppress that control.
- **OUTAGE/LOGOUT:** existing owner docs already separate app session, server refresh/session, optional provider logout and recovery behavior.
- No new SSO technology is introduced from this occurrence.

## Critical questions
1. What is reused when the user moves from the first SP to the second: the first app token or the IdP session?
2. Why must Slack still validate its own token/SSO response?
3. Why does SSO not imply shared application authorization?
4. What is the availability blast radius of one central IdP?
5. Why is global logout harder than login?
6. What should happen if TenantMembership is suspended while the IdP session remains valid?
7. When should SquiFlow require step-up even though SSO already authenticated the user?
8. How do custom tenant domains remain routing/branding concerns rather than identity authority?
9. **Challenge:** design an SSO flow for tenant Web and Platform Admin where the user has one identity provider account but Platform Admin requires stronger authorization and step-up without making Core API the Admin backend.

# 070 — Best Practices in API Design

## A. Identification
- **PDF pages:** `140-141`
- **Original archive pages:** `270-271`
- **Related prior material:** `006`, `013`, `016`, `026`, `033`, `044`, `059`, `060`, `061`, `067`; later `077`, `088`, `097`, `101`, `109`, `111`, `115`, `118`.
- **Classification:** `KEEP`; current API owner already implements a stricter semantic contract.

## B-C. Core concept and important concepts — SOURCE
The source lists eight practices:
1. clear, consistent collection-oriented naming;
2. idempotency / safe retries;
3. pagination, including offset and cursor strategies;
4. sorting and filtering through query strings;
5. clear cross-resource references and avoiding excessively long query strings;
6. rate limiting;
7. versioning/backward compatibility;
8. authentication/authorization using appropriate mechanisms such as API keys, JWT and OAuth2.

## D. Diagram / visual explanation
The infographic gives one row per practice. It contrasts unclear versus clear resource names, duplicate request outcomes, unbounded versus paged datasets, visible filters/sorts, readable resource relationships, rate-limited callers, URL/query version examples and request headers/security boundaries. It presents API quality as a **contract system**, not only endpoint naming.

## E-F. How it works and why it matters
A predictable API constrains request/response shape, retries, collection size, caller behavior, compatibility and security. These rules reduce accidental client breakage and resource exhaustion, and let clients distinguish transient failure from semantic rejection.

## G-H. Trade-offs, limitations, alternatives — EXTERNAL KNOWLEDGE
- “APIs should be idempotent” is too broad if read literally. Safe methods naturally avoid business mutation; retryable mutating commands need **semantic idempotency**, often via a stable operation key/receipt. POST is not inherently idempotent.
- Pure noun/CRUD naming is not always clearest for business transitions. Task/action subresources such as approval/refund/publication can express intent better.
- Offset pagination is simple but can become expensive/inconsistent on large changing datasets; cursor/keyset pagination can be better when stable ordering exists.
- Sorting/filtering needs an allow-list, bounded complexity and tenant/authorization scope before pagination; arbitrary fields can become query/DoS surfaces.
- Cross-resource references should avoid uncontrolled deep expansion/N+1; REST aggregate endpoints or GraphQL are alternatives when real read composition needs exist.
- Rate limiting is separate from authorization and must include `Retry-After`/fairness/backpressure semantics where appropriate.
- Versioning is a lifecycle with inventory, compatibility and retirement—not merely placing `/v1` in a URL.
- Security also includes TLS, input/payload bounds, resource authorization, secret handling, SSRF/injection protection and safe errors.

## Implications for the Current Implementation
The existing `API_CONTRACT_IDEMPOTENCY_AND_RETRY.md` already covers the source's eight items and adds SquiFlow-specific correctness:
- stable semantic idempotency keys and atomic receipt/effect where possible;
- expected-version/ETag concurrency;
- server-enforced pagination and filter/sort limits;
- version compatibility for Workstations that skip releases;
- tenant/resource/field authorization;
- rate/admission and bounded retries;
- long-running `202 + operation resource` semantics;
- structured Problem Details/failure codes;
- payload/resource/dependency limits and observability.

**Technology fit remains per boundary:** task-oriented HTTP fits explicit business commands/resources; GraphQL remains a positive candidate for complex read composition; gRPC remains a candidate for earned streaming/high-frequency process boundaries; durable async remains the path for long/after-commit work. API keys/tokens/OIDC are chosen by principal/credential requirement rather than a universal security mechanism.

No material owner-document change is required from entry `070`; it validates the current contract and supplies another review checklist.

## Critical questions
1. Why is POST not automatically retry-safe even if the source says APIs should be idempotent?
2. When is a task/action endpoint clearer than a pure CRUD resource update?
3. How can offset pagination return duplicates/misses while data changes?
4. Why must filtering/sorting be bounded and authorization-scoped?
5. How do cross-resource references create N+1 or unbounded expansion risk?
6. Why is rate limiting not authorization?
7. What must an API version-retirement plan know before removing an old contract?
8. Why do API keys/JWT/OAuth2 solve different credential/use-case problems?
9. Which parts of a long-running operation belong in HTTP response semantics versus durable Worker state?
10. **Challenge:** design a `SubmitQuotation` endpoint contract covering naming, idempotency, stale-version handling, authorization, async consequences, errors, rate limits and old-Workstation compatibility.
