# 091 — Cross-Site Scripting (XSS) Attacks

## A. Identification
- **Archive entry:** 091
- **PDF pages:** 180-181
- **Original archive pages:** 347-348
- **Multi-page:** yes
- **Visual-heavy page inspected:** 180
- **Duplicate:** no

## B. Core concept

**SOURCE:** XSS allows attacker-controlled script/code to execute in a victim's browser in the security context of a web application. The article separates **Reflected XSS**, **Stored XSS**, and **DOM-based XSS**. It highlights session hijacking, cookie theft and browser manipulation as consequences.

**INFERENCE:** The common root is not merely “bad input”; it is **untrusted data crossing into an executable browser context without context-appropriate output handling**.

**EXTERNAL KNOWLEDGE / CAVEAT:** Input validation is useful but cannot replace context-aware output encoding. HTML text, HTML attributes, URL values, JavaScript, CSS and DOM APIs have different safe sinks/encoding rules. `HttpOnly` cookies reduce one theft path but do not make XSS harmless: injected script may still act as the user, read rendered sensitive data, invoke same-origin APIs, alter UI or exfiltrate non-HttpOnly data.

## C. Important concepts
- reflected payloads usually arrive in a request and are returned unsafely in the response;
- stored payloads persist in application-controlled storage and execute for later viewers;
- DOM-based XSS can arise entirely from browser-side source-to-sink flows;
- framework auto-encoding is a strong default only while code does not bypass it with raw HTML/dangerous sinks;
- sanitization is needed only when intentionally supporting a constrained rich-content language; sanitization and encoding solve different problems;
- CSP is defense-in-depth, not permission to render unsafe HTML;
- tenant/customer/supplier names, notes, document/template fields, SVG/HTML-like uploads and URLs are all potentially hostile content;
- stored XSS is particularly dangerous in multi-tenant/admin software because one stored payload can target privileged later viewers;
- custom-domain/session boundaries matter because browser origin/cookie scope changes the blast radius.

## D. Diagram / visual explanation

The page-180 visual shows three attack paths corresponding to reflected, stored and DOM/client-side execution. The important architectural reading is the **source → unsafe sink → victim browser execution** path, not the particular UI shown. The second page is text-only continuation emphasizing DOM-based XSS.

## E. How it works step-by-step

### Reflected
1. attacker constructs a URL/request carrying payload data;
2. victim follows the link/request;
3. server reflects the value into an HTML/JS context unsafely;
4. browser parses it as executable content;
5. script runs under the application's origin.

### Stored
1. attacker submits content accepted by the application;
2. content is persisted;
3. another user/admin opens a page containing it;
4. application renders stored data into an unsafe context;
5. browser executes it.

### DOM-based
1. browser code reads attacker-controllable data such as URL/location/message/storage;
2. client code sends that value into an unsafe DOM/HTML/script sink;
3. browser interprets it as executable markup/script;
4. server-side validation may never observe the dangerous final composition.

## F. Why it matters

SquiFlow will handle customer/supplier/business text, configurable forms/templates, file names, previews and potentially custom domains. A stored payload that reaches an Owner or Platform Admin surface could become a cross-account or control-plane incident even if the underlying database tenant filter is correct.

## G. Trade-offs / limitations

- blanket rejection of punctuation/HTML-like text can damage legitimate business data and still miss context-specific attacks;
- sanitizing arbitrary rich HTML is significantly harder than never allowing rich HTML;
- very strict CSP can conflict with frameworks/plugins and needs real browser testing;
- CSP, WAF and scanners cannot prove application output contexts are safe;
- encoding at input can create double-encoding/canonicalization bugs; prefer preserving data semantics and encoding at the output context unless a field is explicitly sanitized into a canonical rich-content representation.

## H. Alternatives / comparisons

This is not `validation vs encoding vs sanitization vs CSP` as a winner/loser choice. They solve different layers:

```text
structure/business validation
    -> reject invalid business input
framework/context output encoding
    -> default browser-execution defense
allow-list sanitizer
    -> only for intentionally supported rich content
CSP / response headers
    -> defense-in-depth / blast-radius reduction
HttpOnly/Secure/SameSite
    -> session/cookie hardening, not XSS elimination
```

## I. Real implementation considerations

### Implications for the Current Implementation

**What SquiFlow is currently doing/documenting:** `APPLICATION_SECURITY_BASELINE.md` already requires framework output encoding, prohibits raw HTML for convenience, requires a narrow sanitizer if rich content is genuinely needed, calls for CSP/response headers, and explicitly covers stored/reflected/client-side XSS. `VERIFICATION_STRATEGY.md` requires tests through the real rendering/session/template paths.

**Why:** SquiFlow has many user-controlled text/file/template surfaces and privileged Web/Admin viewers. The required property is “untrusted business content never becomes executable browser authority.”

**Implementation evidence:** the repository is still pre-Phase-0/documentation-first; there is no committed Web implementation to inspect. Therefore this is an **accepted security requirement, not yet verified control**.

**KEEP:** framework encoding by default; explicit rich-content decision; CSP as defense-in-depth; separation of Tenant Web/Admin session scopes.

**IMPROVE NOW (when Web implementation begins):** inventory every raw-HTML/markup/JS interop/template render sink; make unsafe rendering rare and reviewable; add stored/reflected/DOM hostile tests before declaring the relevant slice complete.

**NEEDS MEASUREMENT / TEST EVIDENCE:** CSP compatibility and false-positive/feature impact must be exercised in the chosen Blazor/browser topology.

**AVOID:** generic “sanitize all input” middleware, browser storage of reusable credentials, or relying on `HttpOnly`/WAF/scanner as proof XSS is solved.

# 092 — Batch vs Stream Processing

## A. Identification
- **Archive entry:** 092
- **PDF pages:** 182-183
- **Original archive pages:** 351-352
- **Multi-page:** yes
- **Visual-heavy page inspected:** 182
- **Duplicate:** no

## B. Core concept

**SOURCE:** Batch processing collects data in chunks and processes it at scheduled intervals; stream processing processes events continuously for low-latency outputs. The source summarizes batch as high-volume/historical accuracy and stream as low-latency/real-time action. The visual uses example stacks such as S3/Snowflake/HDFS + Spark/MapReduce for batch and Kafka + Flink/Spark Streaming for streams.

**INFERENCE:** The important decision axis is **latency/freshness + state/reprocessing model + operational cost**, not the logo/tool list.

**EXTERNAL KNOWLEDGE / CAVEAT:** Batch does not inherently own “accuracy,” and stream processing does not inherently sacrifice correctness. Streaming systems can use event time, watermarks, replay, checkpoints and exactly-once-within-scope techniques; batch can be very frequent/micro-batched. “Real-time” also needs a defined latency bound rather than a label.

## C. Important concepts
- accumulation window and scheduled trigger;
- continuous ingestion and continuous evaluation;
- event time vs processing time;
- replay/backfill/reprocessing;
- late/out-of-order data;
- stateful stream operators/checkpoints;
- bounded batch chunking/backpressure;
- latency versus operational complexity;
- source-of-truth versus derived analytics;
- durable jobs versus event streams versus live UI signals.

## D. Diagram / visual explanation

The page-182 infographic is a side-by-side pipeline: sources → storage/chunks → scheduled batch processor → delayed analytics output, versus sources → continuous stream ingestion/buffering → stream processor → low-latency analytics/alerts. The tools are examples, not architecture requirements.

## E. How it works step-by-step

### Batch
1. collect durable input over a defined range/window;
2. identify a batch/occurrence identity;
3. process bounded chunks;
4. write results/checkpoints;
5. retry/restart from durable state when needed;
6. publish completed output/reconciliation evidence.

### Stream
1. ingest ordered/partitioned events into durable or transient transport;
2. assign event identity/partition/time semantics;
3. continuously consume and update derived state;
4. handle duplicates, late/out-of-order events and restarts;
5. checkpoint/commit progress;
6. expose freshness/lag and recover/replay when required.

## F. Why it matters

SquiFlow will have scheduled reports/reconciliation/maintenance/imports and durable Worker work. It may later need near-real-time operational dashboards or analytics. Treating every background task as a stream—or every live requirement as a nightly batch—would both be wrong.

## G. Trade-offs / limitations

- streaming adds partitioning, ordering, checkpoints, state recovery, replay, lag and operational burden;
- batch introduces result staleness and potentially large burst resource use;
- micro-batching can blur the distinction;
- a low-latency live UI signal does not automatically require a stream-processing platform;
- neither model replaces authoritative transaction semantics for payments/stock/permissions.

## H. Alternatives / comparisons

```text
one durable task with an execution owner
    -> queue/job/Worker
scheduled/rebuild/reconciliation over a bounded set
    -> batch
many retained facts + independent consumers + replay/low-latency derived state
    -> stream processing candidate
live UI wake-up/notification only
    -> SignalR/WebSocket-style signal + durable state fetch
```

These can coexist.

## I. Real implementation considerations

### Implications for the Current Implementation

**What SquiFlow is doing/documenting:** scheduled and batch/volume-triggered Worker work is explicitly supported; first Worker may use a simple durable DB-backed job/schedule mechanism. Kafka/event-stream infrastructure is not baseline but remains a candidate when durable replay/history/independent offsets/throughput justify it.

**Why:** known first workloads—document generation, reconciliation, scheduled jobs, bounded imports—have clear work ownership and do not yet demonstrate a continuous replayable analytics-stream requirement.

**KEEP:** durable occurrence identity for scheduled work, bounded chunking, resumability, job states, source/version identity for derived outputs.

**LATER / SCALE TRIGGER:** streaming engine/log when a concrete low-latency derived-data workload requires replay, independent consumer positions and sustained event volume.

**AVOID:** using “real-time” as a reason to move payment/stock authority into a stream; treating SignalR as durable stream truth.

### Critical interrogation
- Which current SquiFlow workload actually needs results in seconds rather than minutes/hours?
- Is the workload a business command, one durable job, a batch rebuild, a live notification, or a true event stream?
- What happens to late/offline Workstation events relative to event-time semantics?
- Can a nightly/restartable batch satisfy the requirement more cheaply?
- If streaming is adopted, who owns replay, schema evolution, consumer lag, backfill and state recovery?

**Critical reasoning**

2. Why does a live dashboard not automatically require Kafka/Flink?
3. Which SquiFlow Worker workloads are jobs rather than streams?
4. How would long-offline Workstation data affect a streaming projection?

**Trade-off**

**Failure / edge case**

# 093 — What are Modular Monoliths?

## A. Identification
- **Archive entry:** 093
- **PDF pages:** 184-185
- **Original archive pages:** 353-354
- **Multi-page:** yes
- **Visual-heavy page inspected:** 184
- **Duplicate:** no

## B. Core concept

**SOURCE:** A modular monolith divides one application/deployment unit into modules with well-defined boundaries and cohesive functionality. The article contrasts a traditional monolith, modular monolith and microservices and says modular monoliths combine monolithic simplicity with microservice flexibility.

**INFERENCE:** The useful property is **enforced internal ownership/boundaries without paying a network/distributed-systems tax for every module**.

**EXTERNAL KNOWLEDGE / CAVEAT:** “Modules are independent” is too strong if interpreted literally: modules share process/deployment and may share infrastructure. “Microservices are more scalable” is also not universal; scaling benefit exists when independent scaling/deployment/fault/ownership boundaries are real. A badly coupled modular monolith can be merely a monolith with folders.

## C. Important concepts
- bounded module ownership;
- cohesive domain capabilities;
- explicit in-process interfaces/contracts;
- dependency direction;
- data ownership despite shared database infrastructure;
- same-process transactions when the invariant is truly shared;
- avoiding direct table/ORM bypass across module rules;
- extractability without pretending extraction already exists;
- shared deployment/release compatibility;
- module-level tests and architecture dependency tests.

## D. Diagram / visual explanation

Page 184 shows one outer modular-monolith deployment containing multiple colored modules, contrasted below with monolith and microservices. The key is not the boxes themselves but the boundary rule: modules remain in one deployment while communicating through deliberate interfaces rather than uncontrolled cross-module coupling.

## E. How it works step-by-step
1. identify domain/business capability boundaries from real invariants and language;
2. group behavior/data ownership coherently;
3. define allowed module interfaces and dependency direction;
4. keep calls in-process where no real process boundary exists;
5. enforce ownership in code/tests even if one DB is shared;
6. deploy as one or a small number of runtime hosts;
7. measure where independent scaling/deploy/fault/security needs actually emerge;
8. extract only the capability that earns a service boundary.

## F. Why it matters

SquiFlow explicitly targets a modular-monolith business core while still having genuine process boundaries such as Guard/Workstation and Core API/Admin API/future Worker. That is a nuanced fit: **modular monolith does not mean one process for everything**, and separate runtime hosts do not mean microservices.

## G. Trade-offs / limitations

- one deployment can couple release cadence;
- one process crash can affect all in-process modules in that host;
- shared DB makes accidental ownership violations easy;
- independent scaling is limited until extraction/host separation;
- boundaries require architecture tests/review or they decay;
- premature module abstraction can create ceremony without domain value.

## H. Alternatives / comparisons

This is not `monolith vs modular monolith vs microservices = choose one forever`.

```text
same-process business capability with shared transaction needs
    -> modular monolith module
real security/fault/process/recovery boundary
    -> separate executable/host
independent scaling/deploy/data ownership need proven
    -> extracted service candidate
```

SquiFlow can therefore remain a modular monolith while using multiple executable hosts.

## I. Real implementation considerations

### Implications for the Current Implementation

**What SquiFlow is doing/documenting:** modules are intended to remain modular-monolith code and communicate in-process; `Core API`, `Admin API` and future `Worker` are runtime hosts and may share the central database while respecting module ownership. Guard/Workstation are separate processes for actual supervision/fault reasons.

**Why:** small-team operation, owned-rack constraints, transactional business invariants and local-first complexity make unnecessary service calls particularly expensive. In-process calls preserve simple debugging/transactions while explicit modules preserve maintainability and future extraction options.

**Implementation evidence:** repository structure is still pre-Phase-0; module boundaries are **planned, not yet demonstrated in source code**.

**KEEP:** modular-monolith business core; no HTTP/gRPC between same-process modules; architecture dependency tests.

**IMPROVE NOW when scaffolding starts:** define the first modules from implemented vertical slices and business invariants, not from a catalog. Add tests that prevent provider/framework and cross-module data ownership leaks.

**LATER / SCALE TRIGGER:** extraction only when independent deployment/scaling/fault/security/ownership evidence repeats strongly enough.

**AVOID:** “service per module,” shared-table free-for-all, or an internal event bus that hides required synchronous business ownership.

### Critical interrogation
- Why is each proposed module a real business boundary rather than a folder or CRUD entity?
- What invariant/transaction crosses the boundary, if any?
- Which module owns each table/aggregate even if the DB is shared?
- What evidence would justify extracting one module into a service?
- If extracted, how would data ownership, idempotency, versioning and failure semantics change?

# 094 — Process vs Thread

## A. Identification
- **Archive entry:** 094
- **PDF page:** 186
- **Original archive page:** 355
- **Multi-page:** no
- **Visual-heavy page inspected:** 186
- **Duplicate:** no

## B. Core concept

**SOURCE:** Processes have separate memory spaces and are generally heavier to create/switch; threads exist within a process and share memory, making communication cheaper.

**INFERENCE:** The architecture-relevant distinction is **fault/address-space/security/deployment isolation versus cheaper same-process concurrency**.

**EXTERNAL KNOWLEDGE / CAVEAT:** Threads are not an application architecture boundary by themselves, and modern .NET async work does not map one-to-one to dedicated threads. Process isolation is stronger but not absolute; processes can still share files/sockets/shared memory and common dependencies.

## C. Important concepts
- address-space isolation;
- shared-memory races;
- process startup/deployment lifecycle;
- IPC versus in-memory call cost;
- crash blast radius;
- security privileges/credentials per process;
- OS scheduling/context switches;
- async tasks/thread pool versus explicit threads;
- resource limits and supervision.

## D. Diagram / visual explanation

The page shows programs becoming processes, and processes containing threads, plus a comparison table. The useful SquiFlow reading is that threads share one process's failure/address-space boundary; a separate process is justified only when that stronger boundary solves a real problem.

## E. How it works step-by-step
1. OS creates a process with its own virtual address space/resources;
2. process hosts one or more execution threads;
3. threads share process memory/resources and therefore require synchronization around mutable state;
4. process-to-process interaction requires IPC/network/file mechanisms;
5. process failure terminates its threads, while another process can continue and supervise/recover it.

## F. Why it matters

SquiFlow deliberately uses process boundaries where they have concrete value: Guard must supervise Workstation from outside; Core/Admin separation protects security/availability; Worker can isolate long-running durable work. Ordinary modules do not gain value from process separation just because processes appear in an architecture diagram.

## G. Trade-offs / limitations
- process isolation adds memory, startup, IPC, deployment/version and observability cost;
- threads/tasks are cheaper but share memory and crash/resource blast radius;
- more threads do not guarantee throughput and can increase contention/context switching;
- process boundaries still share downstream SPOFs such as DB/network/provider.

## H. Alternatives / comparisons

```text
in-process synchronous/async call
    -> cheapest when no isolation need
bounded task/thread-pool concurrency
    -> same-process parallel/overlapped work
separate process
    -> fault/security/supervision/deployment isolation
separate service/node
    -> only when network/deployment/data ownership requirement is real
```

## I. Real implementation considerations

### Implications for the Current Implementation

**What/where/why:** Guard ↔ Workstation is a real two-process boundary because a process cannot reliably supervise its own crash/hang. Core API ↔ Admin API are separate process/security/availability surfaces. Future Worker is separate to own durable long-running work. Business modules stay in-process because they do not currently need IPC/distributed failure semantics.

**KEEP:** the process-boundary criteria in `REPOSITORY_STRUCTURE.md`.

**NEEDS MEASUREMENT:** Worker concurrency and document/image parallelism on actual low-end hardware.

**AVOID:** dedicated threads for every request/job; process-per-module; interpreting async I/O as “spawn a thread.”

### Critical interrogation
- What failure should survive this process crashing?
- What secret/privilege should be impossible to access from the other process?
- Is IPC/versioning/recovery worth the isolation?
- Could bounded in-process concurrency solve the same problem?
- What shared DB/provider failure still defeats both processes?

### Questions — answers intentionally withheld

**Foundation**
1. What memory/resources do threads share?
2. Why is process IPC generally more expensive than in-process communication?

**Critical reasoning**
1. Why must Guard be a separate process?
2. Why does a separate Admin API not automatically mean microservices?
3. Why is `.NET async` not equivalent to “one thread per operation”?

**Trade-off**
1. When is stronger isolation worth higher memory/IPC cost?
2. When can many threads reduce throughput?

**Failure / edge case**

2. What if a Worker process dies after an external effect but before marking a job complete?

**Implementation**

# 095 — Latency vs. Throughput

## A. Identification
- **Archive entry:** 095
- **PDF pages:** 187-188
- **Original archive pages:** 358-359
- **Multi-page:** yes
- **Visual-heavy page inspected:** 187
- **Duplicate:** no

## B. Core concept

**SOURCE:** Latency is delay/responsiveness for an individual request/packet; throughput is the amount of data/work successfully delivered per unit time. The source lists server processing, queuing, propagation, transmission and last-mile delay as latency contributors.

**INFERENCE:** Systems need both **per-operation responsiveness** and **sustainable capacity**, and optimizing one can worsen the other.

**EXTERNAL KNOWLEDGE / CAVEAT:** Latency should be treated as a distribution (for example median/tails), not a single average. As utilization approaches saturation, queueing often drives tail latency sharply upward. Bandwidth is a link capacity; achieved application throughput also depends on protocol, concurrency, payloads, CPU, DB/provider limits and errors/retries.

## C. Important concepts
- end-to-end latency decomposition;
- queue wait versus service time;
- p50/p95/p99/tail behavior;
- throughput in requests/s, jobs/s, bytes/s, records/s etc.;
- saturation and backpressure;
- concurrency/parallelism versus throughput;
- throughput under error/retry load;
- per-tenant fairness;
- backlog age as a latency metric for asynchronous work;
- local Workstation perceived latency versus remote sync throughput.

## D. Diagram / visual explanation

Page 187 visually contrasts one request's path/timing with many items flowing through a pipe. It reinforces that a system can have high capacity but poor per-request response time, or low latency at tiny load but collapse under higher throughput.

## E. How it works step-by-step
1. define a user/business journey and its latency start/end boundaries;
2. decompose network, queue, application, DB and provider time;
3. measure latency distribution under representative concurrency;
4. increase offered load and observe achieved throughput;
5. find saturation point and first constrained resource;
6. apply backpressure/admission before unbounded queue growth;
7. choose changes that improve the relevant metric without violating correctness/fairness.

## F. Why it matters

SquiFlow has very different performance shapes: local Workstation actions should feel responsive offline; sync needs backlog-drain throughput after long disconnection; Web/API needs bounded interactive latency; Worker needs oldest-item/job-duration targets; object backup/restore needs byte throughput. One global “fast” number would hide the real requirement.

## G. Trade-offs / limitations
- batching can improve throughput while increasing per-item latency;
- more concurrency can improve throughput until it saturates DB/CPU/network and then worsen latency;
- aggressive caching can lower latency but adds freshness/invalidation cost;
- strict serial consistency can protect invariants while limiting throughput;
- low average latency can hide terrible tail behavior;
- maximizing throughput can starve small interactive work without priority/fairness.

## H. Alternatives / comparisons

Latency and throughput are **not competitors to choose between**. SquiFlow should specify the relevant measure per capability and use backpressure/fairness where objectives conflict.

## I. Real implementation considerations

### Implications for the Current Implementation

`NON_FUNCTIONAL_REQUIREMENTS.md` already requires measurement-driven targets instead of invented p95/p99 promises. It names API latency distributions, DB pool saturation, sync backlog age/drain time, Worker oldest-item age, provider latency, document/image resource use, object-transfer throughput and recovery time.

**What/why:** interactive commands need bounded latency because humans wait; sync/restore/background work often care more about sustainable throughput/backlog age; both remain bounded by actual rack/provider capacity.

**KEEP:** no guessed numeric SLOs before representative measurements; measure on actual deployment class.

**IMPROVE NOW when implementation begins:** define a metric/unit/start-end boundary for every important performance target before optimizing.

**NEEDS MEASUREMENT:** actual percentiles, saturation points, concurrency budgets and throughput envelopes.

**AVOID:** maximizing request/s without queue age/error/fairness, or reporting only averages.

### Critical interrogation
- Which exact SquiFlow journey is “slow,” and from whose clock/perspective?
- Is the problem service time, queue wait, network, DB, provider, lock, GC or client rendering?
- What throughput must be sustained after a reconnect storm without destroying interactive latency?
- Which tenant/workload gets deferred first under pressure?
- What measurement would prove the current single-node profile insufficient?

### Questions — answers intentionally withheld

## Knowledge gained / refined
1. **Security controls must be proven at the actual rendering/query boundary.** XSS and SQL-style security requirements in docs are not implementation evidence.
2. **Processing models are workload semantics, not technology brands.** Batch, durable jobs, live signals and stream processing can coexist.
3. **The modular monolith is a positive SquiFlow fit for current business modules because it preserves in-process transactions/debugging while keeping boundaries extractable; it is not a universal rejection of services.**
4. **Process boundaries need explicit fault/security/supervision reasons.** Guard/Workstation and Core/Admin qualify for different reasons; business modules do not automatically qualify.
5. **Latency and throughput are separate requirement families.** Interactive latency, sync-drain throughput, Worker backlog age and object-transfer throughput need different measurements.
6. **Concept/server/network catalogs are inventory prompts, not deployment shopping lists.** Responsibilities can co-locate and still remain logically separate.
7. **Slow-API remediation must follow evidence.** Several attractive source fixes can make SquiFlow worse if the actual bottleneck is elsewhere.
8. **Network/time/edge failures are production behavior.** They remain non-authoritative infrastructure dependencies with explicit recovery/testing.
