# 101 — How to Design Good APIs

## A. Identification
- **Archive entry:** 101
- **PDF pages:** 198-199
- **Original archive pages:** 380-381
- **Multi-page:** yes
- **Visual-heavy page inspected:** 198
- **Duplicate:** no; exact-title overlap with future URL occurrence `020`, which remains independently pending.

## B. Core concept

**SOURCE:** The article says good APIs are predictable, secure, scalable and consistent. It highlights idempotency, versioning, noun-based resource names, security and pagination. The visual shows HTTP-method idempotency, idempotency-key storage in Redis, URI/query-parameter versioning, noun resource routes, bearer/JWT authentication and offset/limit pagination.

**INFERENCE:** The useful design principle is not a fixed REST checklist; it is **making externally visible contracts explicit enough that clients can retry, evolve, authorize, paginate and recover predictably**.

**EXTERNAL KNOWLEDGE / CAVEAT:** Several source statements need qualification:
- HTTP idempotency is about the **intended effect on server state**, not guaranteed byte-for-byte identical responses. A second `DELETE` can legitimately return a different status while the method remains idempotent.
- `POST` and `PATCH` are not defined as inherently idempotent by HTTP semantics, but an application operation can deliberately make them semantically idempotent.
- an idempotency key in Redis is not automatically safe for a business effect; atomicity, retention, intent comparison and recovery matter. If the authoritative mutation and receipt are in one database, committing them together is often stronger.
- authentication is not authorization. A valid JWT/bearer token does not establish tenant/resource/domain permission.
- noun-based resource naming is useful for ordinary resources, but explicit semantic commands such as `ApproveQuote` or `RefundPayment` can be clearer than pretending all business actions are CRUD.
- offset pagination can drift under concurrent inserts/deletes; cursor/keyset approaches can be better for stable traversal depending on the query.

## C. Important concepts
- semantic operation identity versus transport request identity;
- caller-generated idempotency key;
- same-key/same-intent versus same-key/different-intent;
- idempotency receipt/result retention;
- response-loss ambiguity;
- HTTP method semantics versus business command semantics;
- API compatibility/version lifecycle;
- old Workstation/client support windows;
- resource routes versus task/action routes;
- authentication, TenantContext, resource authorization and business-state validation as separate layers;
- request/response field allow-lists;
- bounded page size and result cost;
- offset/cursor/keyset pagination trade-offs;
- stable failure/Problem Details codes;
- rate/admission/resource budgets;
- concurrency/preconditions/expected versions;
- long-running operation status resources;
- API audience/ownership: tenant Web, Workstation sync, integrations, tenant admin, platform admin;
- protocol choice separated from API/business semantics.

## D. Diagram / visual explanation

Page 198 places one example HTTP request at the center and connects it to five panels: idempotency, versioning, noun-based resources, security/JWT and pagination. The visual is useful as a contract checklist, but it silently collapses several independent concerns. In SquiFlow, bearer validation is only the beginning of request authority, and idempotency storage is part of the correctness boundary rather than an interchangeable cache detail.

## E. How it works step-by-step

For a material SquiFlow command, the stronger flow is:

```text
client expresses explicit business intent
→ authenticate actor/session
→ resolve authoritative TenantContext
→ validate request schema/field allow-list/bounds
→ resolve semantic idempotency identity
→ load tenant-scoped resource where applicable
→ OpenFGA / application authorization
→ domain/workflow/current-state validation
→ expected-version/concurrency check
→ authoritative transaction
     business mutation
     + idempotency receipt/result
     + outbox where applicable
→ safe result / stable failure code
→ duplicate retry returns same semantic outcome
```

For large reads:

```text
bounded query/filter/sort allow-list
→ authorization/tenant scope
→ stable ordering
→ bounded page/cursor
→ explicit next-page contract
```

## F. Why it matters

Workstations can lose responses and skip releases; tenant data is pooled; financial/stock/permission actions cannot duplicate; Web/Admin clients have different audiences; future GraphQL/gRPC may coexist with HTTP. Therefore API design is a correctness and compatibility problem, not only route aesthetics.

## G. Trade-offs / limitations

- durable idempotency receipts consume storage and need retention policy;
- stricter compatibility/versioning slows destructive cleanup but protects older clients;
- cursor pagination can be more complex than offset pagination;
- task-oriented commands can be clearer for domain intent but less “pure REST”;
- fine resource/field authorization adds server work but is mandatory where sensitivity requires it;
- global maximum consistency/authorization freshness can add latency, so risk-specific freshness may be appropriate;
- version proliferation without retirement policy becomes permanent support debt.

## H. Alternatives / comparisons

This article must **not** become “REST wins.” Different SquiFlow surfaces can deliberately use different interfaces:

```text
ordinary resources / explicit business commands
    → REST/task-oriented HTTP can fit well

complex nested/client-selected Web/Admin reads
    → GraphQL remains a positive candidate if real UI composition pain proves it useful

high-frequency typed streaming RPC / Workstation sync
    → gRPC remains a preferred candidate when Phase-3 evidence justifies it

live UI wake-up
    → SignalR/WebSocket-style signaling

long-running consequence
    → durable operation + Worker/outbox
```

The invariant layers—tenant authority, authorization, idempotency, domain rules, compatibility and bounds—remain regardless of interface style.

## I. Real implementation considerations

### Implications for the Current Implementation

**What SquiFlow is doing/documenting:** `MASTER_IMPLEMENTATION_PLAN.md` and `CORE_API_AND_WORKER.md` define REST/task-oriented HTTP as the ordinary baseline without claiming REST purity, semantic idempotency for retryable mutations, task-oriented material commands, explicit API audiences, version compatibility, stable errors, bounded pagination, rate/admission and layered ZITADEL → TenantContext → OpenFGA → domain validation. GraphQL and gRPC remain surface-specific candidates.

**Why:** this gives explicit business intent and retry/error semantics for commands while preserving freedom to use better read/transport mechanisms at other boundaries.

**Implementation evidence:** repository state is still pre-Phase-0; endpoint metadata, idempotency persistence, pagination behavior and compatibility tests are requirements, not yet runtime evidence.

**KEEP:** explicit command semantics, semantic idempotency, layered authorization, bounded reads, compatibility ownership.

**IMPROVE NOW when API scaffolding begins:** executable endpoint audience/auth/resource-limit classification; stable failure-code registry; idempotency same-key/different-intent tests; pagination ordering/continuation tests.

**NEEDS MEASUREMENT:** GraphQL read-composition benefit, gRPC sync transport benefit, actual page sizes/latency/cost budgets.

**AVOID:** storing authoritative idempotency only in a disposable cache by default; forcing every business action into CRUD; “token valid = authorized”; unbounded list endpoints.

# 102 — Types of Virtualization

## A. Identification
- **Archive entry:** 102
- **PDF pages:** 200-201
- **Original archive pages:** 390-391
- **Multi-page:** yes
- **Visual-heavy page inspected:** 200
- **Duplicate:** no

## B. Core concept

**SOURCE:** The article shows four deployment/isolation forms: traditional/bare metal, VM-based virtualization, containerization, and containers on VMs. It says VMs have complete guest operating systems behind a hypervisor, containers share a host kernel, and containers-on-VMs combine hardware-level and lightweight application isolation.

**INFERENCE:** These are **different isolation/packaging layers that can be composed**, not a linear maturity ladder.

**EXTERNAL KNOWLEDGE / CAVEAT:**
- the bare-metal panel says there is “no isolation between processes”; operating systems do provide process/address-space/permission isolation even without hypervisor/container isolation.
- “containers start in milliseconds” and “resource usage is dramatically lower” are workload/image/platform-dependent generalizations.
- “containers on VMs is what actually runs in production cloud environments” is too universal; production can use bare metal, VMs, containers on bare metal, serverless, managed platforms, dedicated hosts and other combinations.
- a container filesystem is not inherently durable; writable-layer semantics differ from persistent storage.

## C. Important concepts
- physical host ownership;
- OS process isolation;
- hypervisor/guest OS isolation;
- kernel-sharing container isolation;
- image packaging/reproducibility;
- startup/patch/boot overhead;
- host/guest compatibility;
- resource quotas/cgroups/job objects depending platform;
- storage/network isolation;
- snapshot/recovery semantics;
- kernel/host vulnerability blast radius;
- licensing/Windows/Linux compatibility;
- nested/container-on-VM composition;
- actual small-rack CPU/RAM overhead.

## D. Diagram / visual explanation

Page 200 uses four quadrants: apps on one OS/physical server; multiple guest OS VMs over a hypervisor; multiple containers over one host OS/container engine; and containers grouped inside VMs. The strongest visual lesson is that **VMs and containers solve different layers and can coexist**.

## E. How it works step-by-step

### Bare metal
hardware → host OS → processes/services.

### VM
hardware → hypervisor → guest OS per VM → app/processes.

### Containers
hardware → host OS/kernel → container runtime → isolated process/filesystem/network namespaces/cgroups or platform equivalents.

### Containers on VMs
hardware → hypervisor → guest OS/VM → container runtime → containers.

## F. Why it matters

SquiFlow targets lower-spec owned rack hardware and has explicit runtime boundaries but no accepted container/VM packaging decision. The deployment form affects RAM overhead, reproducibility, recovery, OS compatibility, secrets, network exposure and operator burden.

## G. Trade-offs / limitations

- bare metal minimizes virtualization overhead but can make host replacement/config drift harder if automation is weak;
- VMs provide stronger OS/kernel separation and useful snapshot/rollback capabilities but consume additional RAM/storage and require guest patching;
- containers improve repeatable packaging/density but share host kernel and introduce image/runtime/storage/network lifecycle concerns;
- containers-on-VMs add both layers' benefits **and** both layers' operations;
- snapshots are not backups and cannot substitute for application-consistent restore evidence.

## H. Alternatives / comparisons

No winner is selected. A valid SquiFlow deployment can use:

```text
bare-metal services
    → simplest if reproducibility/recovery is proven
VMs
    → stronger OS isolation / host consolidation if resource budget allows
containers
    → packaging/reproducibility/isolation if they materially simplify operations
containers on VMs
    → if both OS isolation and container packaging are valuable
```

## I. Real implementation considerations

### Implications for the Current Implementation

**What SquiFlow is doing/documenting:** deployment/IaC mechanism is OPEN. Containerization is allowed if it improves packaging/isolation/reproducibility; Kubernetes is not implied. Production qualification must rebuild on clean/replacement infrastructure and measure actual hardware resource use.

**Why:** the first concern is recoverable, reproducible service operation on small owned hardware—not selecting a fashionable packaging layer.

**KEEP:** packaging choice remains evidence-driven; same verified artifact; secrets outside artifact; health/shutdown/resource bounds.

**NEEDS MEASUREMENT:** VM/container overhead, startup/recovery time, disk/RAM usage and operational simplicity on actual rack hardware.

**LATER / SURFACE TRIGGER:** VMs if OS/security/fault isolation or multi-OS requirements justify them; containers if packaging/deploy consistency justifies them; both if both requirements are real.

**AVOID:** assuming containers imply Kubernetes or that VM/container snapshots replace backup/restore.

### Critical interrogation
- What deployment failure/recovery problem are we trying to solve with a VM or container?
- How much RAM/CPU/disk does the extra layer consume on the actual rack?
- Does a VM give a security/fault boundary we genuinely need between Core/Admin/Worker/DB?
- Does container packaging materially reduce drift compared with native service definitions?
- How is persistent DB/object state protected independently of VM/container lifecycle?
- What evidence would make bare-metal service deployment insufficient?

## D. Diagram / visual explanation

Page 202 is a three-column product matrix. Each row places one Cloudflare, AWS and Azure product under a shared capability label. The visual should **not** be read as “all products in a row are interchangeable” or “choose one provider for every row.” SquiFlow can deliberately mix an edge provider, identity provider, object store and owned compute if those boundaries have clear contracts.

## E. How it works step-by-step

A sound SquiFlow provider decision should be:
1. identify one exact capability (for example public edge, paid object store, off-site backup, managed DB, compute hosting);
2. state authority/data/recovery requirements;
3. inspect current provider/owned-rack mechanism and why it exists;
4. compare current provider capabilities/limits/pricing/privacy/support from official sources;
5. prototype the critical path and failure/recovery behavior;
6. preserve migration/export strategy where replacement is expected;
7. choose per capability—not from a brand-level “winner.”

## F. Why it matters

SquiFlow already mixes owned rack compute with external providers. It therefore benefits more from **clear provider boundaries** than from forcing everything onto one cloud brand.

## G. Trade-offs / limitations

- single-provider consolidation can simplify billing/IAM/networking but increases platform coupling and migration blast radius;
- multi-provider architecture can improve fit/resilience but increases credentials, observability, networking and support complexity;
- edge compute can reduce latency but creates distributed state/version/debugging concerns;
- managed services reduce operator burden but add quotas/cost/provider outage dependency;
- self-hosting preserves control but shifts patching/availability/backup burden to the small team.

## H. Alternatives / comparisons

Cloudflare, AWS and Azure are not a single winner/loser decision. Potential SquiFlow fits can differ:

```text
public custom-domain edge / DNS / CDN / DDoS/WAF capability
    → Cloudflare or another edge provider could be evaluated

future paid object/backup storage
    → AWS/Azure/other S3-compatible or object providers could be evaluated behind existing seams

future cloud compute / managed DB
    → AWS/Azure/other providers become candidates only if deployment requirements move off the owned rack

current business compute
    → owned rack remains the present deployment assumption
```

**What SquiFlow is doing/documenting:** owned-rack compute is current; Hugging Face object storage and Kaggle backup are bootstrap providers behind `IObjectStore`/`IBackupTarget`; ZITADEL/OpenFGA and managed observability are separate external providers; migration to paid object/backup providers is planned at first paying customer or earlier if constraints demand it.

**Why:** provider mixing is already intentional where it reduces cost/bootstrapping burden while narrow interfaces protect known replacement boundaries.

**KEEP:** capability-specific provider selection; no all-in-one cloud migration from a comparison graphic.

**NEEDS PRIMARY-SOURCE REVIEW / POC:** any future Cloudflare/AWS/Azure decision, including limits, data residency, egress, SLA, API semantics and restore/export behavior.

**LATER / REQUIREMENT TRIGGER:** managed edge or cloud compute when public exposure, HA, regional reach, operations, privacy or capacity requirements prove it worthwhile.

**AVOID:** generic provider abstraction over every dependency before a real replacement boundary; moving to one cloud only for architectural neatness.

- Are we solving cost, availability, edge latency, DDoS, storage capacity, operations, compliance or global reach?

# 105 — HTTP vs. HTTPS

## A. Identification
- **Archive entry:** 105
- **PDF pages:** 205-206
- **Original archive pages:** 395-396
- **Multi-page:** yes
- **Visual-heavy page inspected:** 205
- **Duplicate:** no

## B. Core concept

**SOURCE:** HTTP is described as plaintext over a TCP connection. HTTPS adds TLS: TCP handshake, certificate validation, asymmetric key exchange, then symmetric encryption for application data. The source says HTTPS protects passwords/tokens/forms from network interception.

**INFERENCE:** The durable architecture lesson is **external application traffic requires authenticated, encrypted transport; transport security does not replace application authorization.**

**EXTERNAL KNOWLEDGE / CAVEAT:** The handshake explanation is a historical/simplified RSA-style model and is not a general description of modern TLS 1.3. # 107 — Things Every Developer Should Know: Concurrency is NOT parallelism

## B. Core concept

**SOURCE:** Concurrency is “dealing with lots of things at once,” primarily a program-structure/composition concept; parallelism is “doing lots of things at once,” simultaneous execution on multiple processing units. The source says concurrency is valuable for I/O/high-latency work and parallelism for CPU-heavy work such as image processing/data analysis.

**INFERENCE:** The architectural question is **how many operations may be in flight safely** versus **how much CPU work should execute simultaneously**.

**EXTERNAL KNOWLEDGE / CAVEAT:** Concurrency is not limited to threads or “independently executing processes”; async state machines/event loops/tasks can provide concurrency. Parallelism can use CPU cores, SIMD/GPU/accelerators or multiple machines. More parallelism can reduce throughput under memory/cache/IO contention, and more I/O concurrency can overload downstream pools/providers.

- parallel image/document work;
- reconnect storms.

## D. Diagram / visual explanation

Page 209 shows four timelines: not concurrent/not parallel; concurrent not parallel via interleaving; not concurrent but parallel; concurrent and parallel. This is a useful reminder that concurrency and parallelism are independent axes.

## E. How it works step-by-step
1. identify work classes and shared resources;
2. define correctness for overlapping operations;
3. set bounded concurrency per resource/work class;
4. use async I/O while waiting where appropriate;
5. use parallel compute only when CPU work is measured bottleneck;
6. observe DB pool/locks, provider quotas, CPU/RAM and queue age;

## G. Trade-offs / limitations

- CPU parallelism can increase peak RAM and disk/temp pressure;
- serializing one aggregate may be necessary while global serialization destroys throughput;
- too-low concurrency increases backlog age;
- cancellation does not undo already committed/external effects.

## H. Alternatives / comparisons

Concurrency and parallelism are complementary. SquiFlow may use high async concurrency for bounded network waits while using low CPU parallelism for heavy rendering, and narrow serialization for one stock/payment invariant.

## I. Real implementation considerations

**KEEP:** bounded concurrency/backpressure, real DB correctness, separate CPU/IO budgets.

**NEEDS MEASUREMENT:** actual Worker concurrency, sync batch/in-flight limits, document/image parallelism, DB pool size.

**AVOID:** one thread per request/job; unlimited `Task.WhenAll`; global serialization; increasing concurrency before measuring contention.

3. allow required public edge traffic only to intended entry points;
4. keep DB/provider-management/private recovery paths private/restricted;
5. apply host-level rules to limit blast radius if network-edge policy is bypassed/misconfigured;
6. log/monitor meaningful denied/changed rules without unbounded noise;
7. test IPv4/IPv6/direct-backend paths;
8. keep an authenticated recovery path that does not require disabling security controls.

## F. Why it matters

SquiFlow runs on owned rack hardware and will expose a small set of public application/identity-related paths while keeping DB and infrastructure control private. Network filtering can reduce attack surface before requests reach ASP.NET, but the product remains secure only if backend authority checks also work.

## G. Trade-offs / limitations

- strict rules reduce exposure but can break provider callbacks, updates, identity flows or recovery if dependencies are not inventoried;
- complex per-host rules create configuration drift;
- broad “temporary” incident rules can become permanent holes;
- egress restrictions improve containment but complicate dynamic SaaS/provider endpoints;
- firewall logs can be noisy and can leak metadata if exported carelessly;
- firewall availability/configuration can itself become a SPOF.

## H. Alternatives / comparisons

Network firewall, host firewall, reverse proxy/WAF, VPN/private network and application authorization are **complementary layers**, not substitutes:

```text
network/host firewall
    → reachable network flows
reverse proxy/WAF
    → application-edge protocol/request controls
TLS
    → transport confidentiality/integrity/authentication
ZITADEL/OpenFGA/TenantContext/domain rules
    → application identity and business authorization
```

## I. Real implementation considerations

### Implications for the Current Implementation

**What SquiFlow is doing/documenting:** owner docs already require TLS, explicit public edge/private recovery, server-side SSRF controls, least privilege, and no direct database/client authority. Exact rack machine count/network/uplink/power and physical network topology remain deployment facts. A specific firewall product/rule set is not selected.

**Why:** the architecture needs minimal exposure and recoverable private operations without pretending network filtering is business authorization.

**KEEP:** firewall/network policy as defense in depth and non-authoritative.

**IMPROVE NOW before production qualification:** create an explicit ingress/egress service/port inventory, verify only intended public ports are reachable, test direct-backend bypass, IPv6 exposure and private recovery access. This is a security/operations requirement, not a new product selection.

## Knowledge gained / refined
1. **Good API design is broader than REST styling.** Semantic idempotency, tenant/resource authorization, compatibility, concurrency, failure codes and bounded resource cost are first-class SquiFlow API requirements.
2. **Interface styles can coexist.** REST/task HTTP, GraphQL, gRPC, live signaling and durable async each fit different surfaces; none wins globally from a comparison.
3. **VMs, containers and bare-metal services are deployment tools, not maturity levels.** Packaging remains evidence-driven on the actual rack.
4. **Cloud-provider comparisons are capability snapshots, not provider-selection authority.** SquiFlow can intentionally use a hybrid/multi-provider architecture where boundaries are clear.
5. **The current .NET/Avalonia/Blazor/ASP.NET foundation remains accepted because no source or current requirement demonstrates a better replacement need.** A popularity diagram is not evidence to reopen it.
6. **Modern HTTPS/TLS must be described accurately enough not to create a custom-crypto or obsolete handshake design.** External traffic remains TLS-protected while application authority stays separate.
7. **Forward and reverse proxies are different control directions and may coexist.** Current need is inbound edge; egress proxy is a conditional future mechanism.
8. **Concurrency and parallelism need separate budgets.** I/O concurrency, DB/provider capacity and CPU-heavy parallelism are different constraints.
9. **Authentication mechanism selection follows principal/lifecycle.** Human OIDC, Web sessions, native PKCE, machine API keys/client credentials/mTLS can coexist; authentication never replaces OpenFGA/domain authority.
10. **Firewalling is exposure control, not permission control.** The concrete near-term gap is deployment port/egress policy evidence, not selecting a firewall product.
