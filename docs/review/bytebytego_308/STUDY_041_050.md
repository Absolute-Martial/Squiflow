# 041 — The System Design Topic Map

## Identification
- **PDF pages:** `83-84`
- **Original archive pages:** `162-163`
- **Classification:** `KEEP` as a completeness map; `AVOID` treating every node as required infrastructure.

## SOURCE
The article says system design is a game of trade-offs and organizes topics into six areas:
1. **Application Layer** — availability/scalability/reliability and other NFRs, OOP, DDD, monoliths, microservices, modular monoliths, clean architecture, API design.
2. **Network & Communication** — protocols, service integration, messaging, real-time communication, event-driven architecture.
3. **Data Layer** — schema design, indexing, SQL vs NoSQL, transactions, database types, replication, sharding, leader election and distributed-database consistency.
4. **Scalability & Reliability** — horizontal scaling, statelessness, autoscaling, sharding, caching, load balancing, rate limiting and fault-tolerance concepts.
5. **Security & Observability** — OAuth 2, JWT, PASETO, sessions, cookies, RBAC/ABAC, security threats, monitoring, tracing and logging.
6. **Infrastructure & Deployments** — CI/CD, containerization/orchestration, serverless, IaC and disaster recovery.

The visual additionally names CAP/PACELC, HTTP/HTTPS, WebSockets, gRPC, AMQP, API gateways, service mesh, service discovery, long polling, SSE, vector clocks, MITM/XSS/CSRF/SQL injection, Terraform/CloudFormation/Ansible, Docker and Kubernetes.

## Diagram / visual
The infographic is a hub-and-branch knowledge map. It is useful because it makes cross-layer dependencies visible: for example, API design touches networking/security; distributed databases touch consistency and reliability; infrastructure choices touch deployment/recovery.

Its weakness is that leaf nodes appear visually equivalent even though some are universal concerns (failure, security, recovery) while others are optional techniques (service mesh, Kubernetes, sharding, serverless).

## INFERENCE
The map is best used as an architectural review checklist: ask whether each concern applies, then choose the simplest mechanism that satisfies the real invariant/failure mode. It is not a maturity model.

## EXTERNAL KNOWLEDGE / architect caveats
Important dimensions not made explicit enough for SquiFlow include:
- semantic idempotency and unknown outcomes;
- compatibility/schema/protocol evolution;
- multi-tenancy and data-isolation boundaries;
- authoritative versus derived state;
- concurrency/locking/expected-version behavior;
- backpressure, queue age and overload degradation;
- backup restore, RPO/RTO and replacement-environment recovery;
- privacy/retention/data lifecycle;
- cost/provider lock-in and operational ownership;
- external side effects and reconciliation;
- testing/verification of hostile and partial-failure paths.

## Implications for the Current Implementation
- **KEEP:** SquiFlow already separates application, transport, data, identity/authorization, deployment and operations concerns.
- **KEEP:** modular monolith remains the baseline; microservices/service discovery/service mesh are not implied by the map.
- **KEEP:** HTTP, gRPC, queues, pub/sub and streams are selected by boundary semantics rather than fashion.
- **KEEP:** scaling begins with measurement and capacity envelopes, not automatic sharding/caching/autoscaling.
- **KEEP:** ZITADEL, OpenFGA, tenant isolation and application-domain rules remain separate authority layers.
- **KEEP:** disaster recovery includes rebuild/restore, not just redundant runtime nodes.
- No new owner-document change is required; the missing dimensions above are already represented in current SquiFlow requirements/review gates.

# 042 — How Transformers Architecture Works?

## Identification
- **PDF pages:** `85-86`
- **Original archive pages:** `164-165`
- **Classification:** `NOT APPLICABLE` to the current SquiFlow baseline; useful technical literacy only.

## SOURCE
The article presents a canonical Transformer with encoder and decoder. Its steps are:
- input embedding;
- positional encoding;
- encoder multi-head attention, add/normalize and feed-forward processing repeated through layers;
- decoder output embedding and positional encoding;
- masked multi-head attention so future tokens are hidden;
- encoder-decoder attention;
- decoder feed-forward processing;
- linear layer;
- softmax probabilities;
- next-word selection and generated human-readable output.

It says Transformer architecture is foundational to popular LLMs including GPT, Gemini, Claude, DeepSeek and Llama.

## Diagram / visual
The visual shows two vertical stacks: an encoder stack fed by input tokens and a decoder stack fed by previous output tokens, with an attention connection from encoder output into the decoder. It is the classic encoder-decoder teaching diagram.

## INFERENCE
The article's main transferable lesson is that a model architecture is a pipeline of representations and repeated transformations, and that attention controls context interaction rather than storing ordinary application truth.

## EXTERNAL KNOWLEDGE / caveats
- The diagram is a canonical **encoder-decoder Transformer**, not the exact architecture of every named modern LLM. Many GPT/Llama-style generative LLMs are decoder-only Transformer variants; other models use different mixtures/architectural changes.
- “Choose the highest probability word” oversimplifies generation; decoding may use temperature, top-k/top-p sampling, beam-like strategies, penalties and other controls.
- Tokenization occurs before embeddings and is omitted from the simplified flow.
- Attention does not mean the model literally “understands” words in a human sense; that wording is pedagogical.

## Implications for the Current Implementation
- **AVOID:** adding an LLM/model-serving subsystem merely because AI appears in the archive.
- **KEEP:** current SquiFlow document/rule/business correctness does not depend on probabilistic model output.
- **LATER:** if a concrete OCR/extraction/classification/assistant requirement appears, it must define data privacy, provider boundary, prompt/input limits, hallucination/error handling, cost, offline behavior, auditability and human confirmation before architecture is selected.
- **KEEP:** deterministic bounded SquiFlow rules/workflows must not be silently replaced with probabilistic model decisions for payment, stock, permission or financial authority.

## Critical questions
1. What problem does masked attention solve in an autoregressive decoder?
2. Why is positional information needed in the simplified Transformer description?
3. Why is the shown architecture not an exact diagram of every modern LLM named in the article?
4. Which SquiFlow decisions must remain deterministic even if AI features are added later?
5. What tenant/privacy boundary would an external model provider create?
6. What should happen when model output is plausible but wrong?
7. Which usage/cost limits would become application state if model calls are metered?
8. How would offline Workstation behavior interact with a cloud-only AI feature?
9. **Challenge:** design a future AI-assisted document-extraction feature without allowing model output to become authoritative financial data automatically.

# 043 — JWT Simply Explained

## Identification
- **PDF pages:** `87-88`
- **Original archive pages:** `166-167`
- **Semantic overlap:** entries `005`, `008`, `010`, `039`; independently reviewed occurrence.
- **Classification:** `KEEP` as token-format literacy; `AVOID` a custom SquiFlow JWT subsystem.

## SOURCE
JWT is presented as an open standard for securely transmitting information and as widely used for authentication/authorization. It has:
1. **Header** — JSON describing signing algorithm.
2. **Payload** — claims/user data, including registered/public/private claims.
3. **Signature** — created from encoded header/payload plus key/algorithm.

The article distinguishes:
- **symmetric signatures** — same secret signs and verifies;
- **asymmetric signatures** — private key signs, public key verifies.

The visual also shows a login/token flow and the three-part JWT shape.

## INFERENCE
A signed token can carry issuer-provided claims across a network boundary without the receiver querying the issuer for every claim, provided the receiver correctly validates the token and trusts the issuer/key policy.

## EXTERNAL KNOWLEDGE / caveats
- JWT payloads are normally encoded, not encrypted. Signature protects integrity/authenticity, not confidentiality.
- “JWT is secure” is conditional on algorithm allow-listing, issuer/audience validation, expiry/not-before handling, key rotation, token type, storage, TLS and revocation/session policy.
- The algorithm named by an untrusted token must not be accepted without server-side policy.
- Token validity does not prove current SquiFlow membership/resource authorization.

## Implications for the Current Implementation
- **KEEP:** ZITADEL/OIDC remains the identity/token issuer and validation authority.
- **KEEP:** SquiFlow uses trusted provider/session validation, then current TenantContext/membership, OpenFGA and domain checks.
- **AVOID:** custom JWT issuance, custom PASETO layer, or role/permission truth embedded permanently in application tokens.
- **KEEP:** platform Admin authorization remains separate from tenant authority even if both identities originate from ZITADEL.
- No new owner-document change required.

## Critical questions
1. What security property does a signature provide that Base64 encoding does not?
2. When is asymmetric signing operationally preferable to a shared verification secret?
3. Why must a verifier validate issuer and audience in addition to signature?
4. How does key rotation affect long-lived tokens?
5. Why is a valid token insufficient to authorize `RefundPayment`?
6. Where should tenant membership be checked if the JWT still contains an old tenant claim?
7. How would token theft differ from token tampering?
8. **Challenge:** a token remains cryptographically valid after an employee is removed from a tenant. Design the request authorization chain that prevents continued access.

# 045 — How does HTTPS work?

## Identification
- **PDF pages:** `91-92`
- **Original archive pages:** `176-177`
- **Classification:** `KEEP` TLS/HTTPS requirement; `SOURCE NEEDS QUALIFICATION` for modern handshake details.

## SOURCE
The article describes HTTPS as HTTP protected by TLS. Its simplified flow is:
1. establish TCP;
2. client hello/server hello negotiate TLS version and cipher suites; server sends certificate; client validates it;
3. client generates a session key, encrypts it with server public key, and server decrypts it with private key;
4. both sides then use symmetric encryption for bidirectional application data.

It says symmetric cryptography is used because asymmetric crypto is expensive and states that asymmetric encryption “goes only one way.”

## Diagram / visual
The diagram explicitly separates handshake negotiation, certificate/public-key validation, session-key establishment and the later encrypted data channel.

## INFERENCE
The enduring architectural lesson is correct: HTTPS combines authenticated key establishment with efficient symmetric protection for application traffic, and certificate validation is essential to trust the server identity.

## EXTERNAL KNOWLEDGE / important corrections
- The exact Step 3 is outdated for modern TLS. TLS 1.3 normally derives shared traffic secrets using ephemeral key exchange (for example ECDHE); the client does not simply generate one session key and RSA-encrypt it with the certificate public key.
- Modern TLS provides confidentiality **and integrity/authentication**; describing intercepted traffic as merely “binary code” is imprecise.
- “Asymmetric encryption goes only one way” is incorrect. The real reasons symmetric cryptography is used for bulk data are performance/efficiency and the negotiated authenticated-key design.
- HTTP/3 uses QUIC/UDP rather than first creating an ordinary TCP connection, while TLS 1.3 is integrated into QUIC.
- TLS configuration, certificate renewal, protocol versions and cipher policy should be delegated to maintained platform/runtime/edge implementations, not hand-built.

## Implications for the Current Implementation
- **KEEP:** production Web/Core API/Admin API/Workstation external communication uses HTTPS/TLS; OIDC/OAuth also uses HTTPS.
- **KEEP:** no insecure HTTP fallback for authentication, API or sync just because TLS/certificate validation fails.
- **KEEP:** SquiFlow does not implement custom cryptography/TLS.
- **Implementation hardening to verify later:** certificate renewal/expiry monitoring, trusted-proxy termination, secure protocol configuration, HSTS/browser policy where appropriate, and fail-closed behavior.
- **NEEDS MEASUREMENT:** TLS performance overhead is workload/connection-reuse/hardware dependent; generic percentages are not accepted as a SquiFlow capacity number.
- No topology decision changes.

## Critical questions
1. Which properties does TLS add beyond hiding plaintext?
2. Why is certificate validation part of HTTPS security rather than a cosmetic browser check?
3. Why is the source's “client encrypts session key with public key” not a general description of modern TLS 1.3?
4. Why are symmetric keys used for bulk traffic?
5. What should SquiFlow do when certificate validation fails?
6. How does TLS termination at a reverse proxy change the trust boundary to the backend?
7. What breaks when server clock/certificate renewal is wrong?
8. How would HTTP/3 change the source's TCP-first diagram without changing SquiFlow business semantics?
9. **Challenge:** design a certificate-expiry failure drill for Core API and Admin API that does not encourage an insecure emergency downgrade.

# 049 — What is Event Sourcing? How is it different from normal CRUD design?

## Identification
- **PDF pages:** `99-100`
- **Original archive pages:** `186-187`
- **Classification:** `AVOID / REJECT AS BASELINE`; `LATER` only for a domain that truly needs event-log authority and replay-derived state.

## SOURCE
The article compares:
- **Normal CRUD:** current order state is inserted/updated in the database.
- **Event sourcing:** state-changing events such as `NewOrderEvent` and `ModifyOrderEvent` are sequenced and appended to an event store; `OrderView` is rebuilt from events. The event store is described as the source of truth and an append-only log. Incremental event numbers are used to guarantee order. If the view is down, it can be rebuilt from the event store.

The example uses event IDs 321 and 322 for create/quantity change.

## Diagram / visual
The CRUD side shows Order Service mutating an Order Table. The Event Sourcing side shows Order Service appending events to Event Store, a sequencer, and a derived Order View built from those events.

## INFERENCE
Event sourcing changes the authoritative persistence model: the event history, not the latest row image, is the canonical record from which current state is derived. This can provide rich history/replay but pushes complexity into event design, projection lifecycle and compatibility.

## EXTERNAL KNOWLEDGE / caveats
- Event sourcing does not automatically make a system deterministic. Replay is reliable only when event semantics, code/versioning, external dependencies, timestamps/randomness and side effects are controlled.
- A single globally increasing sequence is not always required; ordering is usually defined at the scope whose invariant needs it, often per aggregate/stream/partition.
- Event schema evolution is a durable compatibility problem because old events may exist forever.
- Projection lag, rebuild duration, duplicate/out-of-order delivery and snapshot strategy become explicit operational concerns.
- External side effects cannot simply be replayed during state rebuild; they need separate effect/outbox/idempotency semantics.
- Privacy/erasure requirements can conflict with immutable append-only event retention and require careful design.

## Implications for the Current Implementation
- **AVOID:** full Event Sourcing as SquiFlow's core persistence model.
- **KEEP:** normalized current relational authority + explicit immutable audit/history/versioned issued documents/corrections where business history matters.
- **KEEP:** transactional outbox is not Event Sourcing; it records durable after-commit delivery intent, not the sole source of aggregate truth.
- **KEEP:** Workstation local outbox/sync history is not Event Sourcing; current local/server business state remains explicitly modeled.
- **LATER / SCALE/DOMAIN TRIGGER:** reconsider only if one domain genuinely needs replay-as-authority, temporal reconstruction and immutable event semantics enough to justify permanent event-version/projection/rebuild operations.
- Financial corrections and issued-document history currently do not by themselves justify event sourcing; explicit immutable business records are simpler.

## Critical questions
1. What changes when the event log rather than the current row becomes the source of truth?
2. Why is an outbox not automatically event sourcing?
3. Which ordering scope actually matters for an order aggregate?
4. How do you evolve an event type that has already been stored for years?
5. What happens if projection rebuild takes hours?
6. Why must external payment/printing effects not be replayed during view rebuild?
7. How can deletion/privacy obligations conflict with immutable event logs?
8. When would snapshots be introduced and what remains authoritative?
9. Which SquiFlow history requirements are already satisfied without event sourcing?
10. **Challenge:** a team proposes Event Sourcing only because it wants an audit trail. Design the simpler alternative and state what capability would still be missing.

# 050 — How Data Lake Architecture Works?

## Identification
- **PDF pages:** `101-102`
- **Original archive pages:** `188-189`
- **Classification:** `AVOID / REJECT AS BASELINE`; possible future analytics architecture only after a real workload.

## SOURCE
A data lake is described as centralized storage for large volumes of structured, semi-structured and unstructured data in raw form. The flow is:
1. sources such as S3, Excel, databases, videos, images, sensors and PDFs;
2. ingestion via real-time streaming or batch/scheduled jobs;
3. raw data store before transformation;
4. batch or real-time processing to clean/transform/prepare;
5. processed data store;
6. consumption through dashboards, AI models, data warehouse, real-time alerts and reporting.

## Diagram / visual
The visual is a layered pipeline: heterogeneous data sources → ingestion → raw storage → batch/stream processing → transformed/processed storage → several analytical/AI/reporting consumers.

## INFERENCE
The data lake separates **collection/storage of source data** from **later processing and consumption** so multiple analytical use cases can reuse data without forcing one relational serving schema.

## EXTERNAL KNOWLEDGE / architect caveats
A production data lake also needs governance that the simplified picture does not show:
- data catalog/schema discovery and lineage;
- access control and tenant/privacy boundaries;
- retention/legal deletion;
- encryption/key ownership;
- data quality and duplicate handling;
- partitioning/file formats and small-file management;
- late/out-of-order streaming data;
- backfill/reprocessing versioning;
- cost/capacity lifecycle policies;
- prevention of raw-lake data from silently becoming transactional authority.

Without governance, a “lake” can become an untrusted data swamp.

## Implications for the Current Implementation
- **AVOID:** no generic data lake, Spark/Flink/Kafka/warehouse pipeline in the current SquiFlow baseline.
- **KEEP:** authoritative operational data remains the transactional relational system; object storage holds business files, not a shadow analytics authority.
- **KEEP:** private Kaggle is an encrypted opaque **backup target**, not a data lake or analytics dataset.
- **LATER:** if cross-tenant/product analytics eventually needs large derived datasets, create an explicitly derived/exported analytical path with tenant isolation, privacy, lineage, freshness and rebuild contracts.
- **KEEP:** reports should begin against safe bounded operational/derived read models; “we need reports” does not imply a lake.
- No new owner-document change required.
