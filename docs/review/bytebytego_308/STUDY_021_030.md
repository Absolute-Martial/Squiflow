## 021 — How to load your websites at lightning speed

**PDF pages:** `45-46`  
**Original archive pages:** `91-92`  
**Classification:** `KEEP` + `NEEDS MEASUREMENT`

### SOURCE

The article gives eight frontend-performance techniques:

1. compression to reduce bytes transferred;
2. selective rendering/windowing so only visible elements are rendered;
3. modular architecture with code splitting to divide a large application bundle into smaller bundles;
4. priority-based loading so essential and above-the-fold resources load first;
5. pre-loading resources before they are requested;
6. tree shaking/dead-code removal to remove unused JavaScript from the final bundle;
7. pre-fetching resources likely to be needed soon;
8. dynamic imports so code is loaded in response to user actions rather than all at startup.

### VISUAL INSPECTION

PDF page `45` contains a frontend-performance infographic organized around the same optimization families. The visual reinforces that the techniques operate at different stages: transferred bytes, render work, bundle composition, loading order, and predictive loading. It is not a single recommendation to enable every optimization simultaneously.

### INFERENCE

The common mechanism is reducing work on the initial critical path: send fewer bytes, parse/execute less code, render less UI, and delay nonessential work.

### EXTERNAL KNOWLEDGE / CAVEAT

Preload and prefetch are not free. Incorrect hints can waste bandwidth, contend with actually critical resources, increase mobile-data consumption, or retain unnecessary data. Compression also consumes CPU and should be selected by content type/size rather than enabled blindly. Code splitting can create too many small network/module requests or awkward loading waterfalls if boundaries are poorly chosen.

Frontend caching/prefetching must not become a new source of current business authority. Browser performance and offline business synchronization are separate concerns.

### Connection to previous articles

- Extends `016` API performance from backend request handling to the browser/render critical path.
- Connects to `007` production Web architecture: CDN/edge delivery may help static assets, but the article does not justify a new CDN product.
- Connects to `017` HTTP evolution: faster transport does not remove the need to reduce payload/render work.

### Implications for the Current Implementation

Current SquiFlow direction already keeps Web online-only for business operations and treats caching/compression as evidence-driven. Keep that separation.

For implemented Web surfaces, measure bundle/page weight, initial/interactive load, rendering cost for large lists/tables, unnecessary component initialization, payload sizes, and network waterfalls before adding complexity. Windowing is especially relevant if administrative grids, product lists, audit views, or other large collections actually show render pressure.

Do not convert prefetch/browser caches into a hidden offline business replica. Tenant-sensitive or authorization-sensitive responses need explicit cacheability rules.

No owner-document architecture change is required from this article.

## 022 — What is SSO (Single Sign-On)?

**PDF pages:** `47-48`  
**Original archive pages:** `93-94`  
**Classification:** `KEEP`

### SOURCE

The source defines SSO as one identity/login being usable across multiple systems. Its example flow is:

- an unauthenticated user reaches Gmail and is redirected to an SSO authentication server/login page;
- the authentication server validates credentials, creates a global session, and creates a token;
- Gmail validates the token with the authentication server and grants access;
- the user then visits YouTube;
- YouTube redirects for authentication, but the authentication server finds the user already logged in and returns authentication without requiring credentials again;
- YouTube validates and grants access.

### VISUAL INSPECTION

PDF page `47` shows two service-provider flows sharing one SSO authentication server. The important visual property is that the applications do not share their local application state directly; they rely on the central identity/session relationship.

### INFERENCE

SSO centralizes the authentication ceremony and session relationship, but each application still has to decide what that authenticated identity may do.

### EXTERNAL KNOWLEDGE / CAVEAT

The source uses a simplified generic token-validation flow. Real SSO protocols differ: an application may validate a signed token locally, perform introspection, exchange an authorization code, maintain its own application session, or use another standards-defined flow. “SSO” is a user/login property, not one wire protocol.

Identity mapping must be stable. Email alone is usually not a safe immutable account key. Logout, session revocation, IdP outage, account disablement, redirect/callback validation, step-up authentication, and token lifetime all need explicit behavior.

### Connection to previous articles

- Deepens `008`, which distinguished SSO from sessions, tokens, JWT, and OAuth 2.0.
- Connects to `005`/`010`: token format does not by itself define current application authorization.
- Connects to `013`: SSO is one security layer, not the full security model.

### Implications for the Current Implementation

SquiFlow already selects ZITADEL for identity/authentication/SSO capability. Keep the current separation:

```text
ZITADEL identity / session / MFA / SSO
        ↓
stable external subject mapping
        ↓
SquiFlow membership + TenantContext
        ↓
OpenFGA authorization
        ↓
domain/workflow/concurrency/state rules
```

A successful ZITADEL login must not create tenant or platform authority by itself. Platform Admin step-up authentication is also separate from the OpenFGA/platform action authorization that follows it.

No new SSO service or custom token system is justified.

**Trade-offs**

## 023 — Redis VS Memcached

**PDF page:** `49`  
**Original archive page:** `97`  
**Classification:** `AVOID` as a baseline dependency + `LATER / SCALE TRIGGER` + `NEEDS MEASUREMENT`

### SOURCE

The source's visual compares Memcached and Redis. It presents Memcached as a simpler key/value cache with plain string values and LRU eviction, while Redis provides richer data structures such as strings, bitmaps/bit fields, hashes, lists, sets, sorted sets, geospatial indexes, HyperLogLogs, and streams.

The visual also associates Redis with atomic operations/transactions, RDB/AOF persistence, publish-subscribe, geospatial support, server-side Lua scripting, multiple eviction policies, and leader/follower replication. It contrasts Memcached as multi-threaded and Redis as using a single thread for key read/write operations.

The text gives Redis examples using hashes, sorted sets, and bitmaps for counters/comments, sorted/deduplicated users, behavior-history filtering, and large boolean datasets.

### VISUAL INSPECTION

The page is primarily a comparison table plus the Redis data-structure key. The table itself is a feature inventory, not a workload decision framework.

### INFERENCE

Redis can be used for more than caching because its data structures and durability/messaging features support broader patterns. That capability is also precisely why selecting “Redis” can accidentally broaden infrastructure scope far beyond the original cache requirement.

### EXTERNAL KNOWLEDGE / CAVEAT

Feature matrices like this are version/configuration sensitive and simplify important implementation details. Threading models, persistence guarantees, replication/failover behavior, transactions, cluster behavior, and eviction semantics must be verified against the exact product/version/configuration if selected.

A persistent Redis configuration still does not automatically make Redis an appropriate source of authoritative SquiFlow payment, stock, credit, tenant, permission, or accounting truth.

### Connection to previous articles

- Extends `019` key-value comparison from distributed-store dimensions to two in-memory cache products.
- Connects to `016` performance: cache is one optimization, not a default.
- Connects to `011` because HyperLogLog appears again, now as a Redis data structure.

### Implications for the Current Implementation

Current SquiFlow cache policy is already stronger than “choose Redis vs Memcached.” No cache product is mandatory. A future cache must define:

- authoritative source and bypass path;
- tenant/permission/config/version-safe keying;
- freshness/TTL/invalidation;
- memory/entry bounds and eviction;
- cold start and repopulation load;
- stampede/miss amplification controls;
- outage behavior;
- privacy/diagnostic treatment.

On the initial low-resource deployment, a bounded in-process cache may be preferable if a measured hot path needs one. A shared Redis/Memcached service is earned only by an actual cross-process/shared-cache workload and operational proof.

No owner-document change is required; current docs already explicitly say neither Redis nor Memcached is baseline.

## 025 — Virtualization vs Containerization

**PDF pages:** `52-53`  
**Original archive pages:** `112-113`  
**Duplicate group:** `ARCH-DUP-03` — occurrence `108` remains independently unprocessed  
**Classification:** `KEEP` + `NEEDS MEASUREMENT`

### SOURCE

The source distinguishes:

- **bare metal:** applications run directly on the OS, high performance but less flexibility;
- **virtualized:** a hypervisor creates VMs, each with its own guest OS; stronger isolation but greater resource overhead;
- **containerized:** a container engine runs containers sharing the host OS; presented as lightweight/efficient and faster/more scalable than VMs;
- **containers on VMs:** combines VM isolation/flexibility with container packaging and is described as common in hybrid cloud environments.

### VISUAL INSPECTION

PDF page `52` diagrams all four deployment forms as layers from hardware upward. The key visual distinction is where the separate operating system boundary exists: per VM versus shared host OS for containers.

### INFERENCE

Virtualization and containerization solve overlapping but different isolation/packaging problems. They can be composed rather than treated as mutually exclusive choices.

### EXTERNAL KNOWLEDGE / CAVEAT

“Containers are faster and more scalable than VMs” is too broad as a universal rule. Startup/resource overhead is often lower, but workload performance, isolation, density, security, kernel compatibility, storage/network path, noisy-neighbor behavior, and operational tooling determine the real result.

A container is not itself HA, persistent storage, orchestration, backup, or zero downtime.

### Connection to previous articles

- Deepens `002` Docker vs Kubernetes: containerization is the packaging/isolation layer; Kubernetes is one possible multi-host orchestrator.
- Connects to `003`: containerization is not the same thing as IaC.
- Occurrence `108` must be reviewed again when reached even if content is related or identical.

### Implications for the Current Implementation

Keep SquiFlow deployment-independent. The application should not know whether its host is bare metal, a VM, or a container.

Containerization remains allowed when it improves repeatability/isolation; Kubernetes remains non-baseline until actual multi-node reconciliation/placement/rollout pain exists. On low-resource hardware, compare process/container/VM overhead and recovery characteristics rather than assuming one abstraction is free.

Durable PostgreSQL storage and durable customer objects cannot accidentally become container-local disposable files.

**Trade-offs**

**Failure / edge cases**

**Implementation**

## 027 — Must-Know Network Protocol Dependencies

**PDF pages:** `56-57`

### SOURCE

The source maps protocol dependencies/categories:

- TCP/UDP supporting many higher-level protocols, with SCTP/DCCP for specialized cases;
- examples of TCP-based protocols including HTTP, SSH, BGP, RDP, IMAP, SMTP, POP;

### VISUAL INSPECTION

### INFERENCE

### EXTERNAL KNOWLEDGE / CAVEAT

The diagram necessarily simplifies protocol reality. HTTP can run over different transport generations; HTTP/3 uses QUIC over UDP, so “HTTP is TCP-based” is not universally true. QUIC is not a universal replacement for TCP+TLS for every protocol. MCP is an application protocol and belongs at a different conceptual layer than TCP/UDP/IP.

DNS can use both UDP and TCP depending on query/response/transport requirements. TLS protects transit but does not establish SquiFlow tenant/business authorization.

### Connection to previous articles

- Extends `017` HTTP/1/2/3 transport evolution and `018` URL/DNS routing concerns.
- Connects to `013`: network protection complements application authentication/authorization.
- Connects to `001`: gRPC's network behavior is one protocol stack instance, not universal transport truth.

### Implications for the Current Implementation

Current SquiFlow decisions already say:

- external app traffic uses HTTPS/TLS;
- ZITADEL uses OIDC/OAuth over HTTPS;
- HTTP version is runtime/edge detail;
- DNS/hostnames route but never establish TenantContext;
- time synchronization matters operationally for TLS/tokens/leases/schedules/diagnostics;
- SSH/private access is operations-only;
- raw TCP/UDP/MQTT/etc. require a concrete workload before adoption.

Use dependency-aware health/telemetry: distinguish DNS resolution, connect timeout, TLS/certificate, authentication, authorization, downstream timeout, and application failures where practical. No new network protocol is required.

### Connection to previous articles

- Connects to `014` architecture learning: patterns are vocabulary/evidence, not architecture authority.
- Connects to the current SquiFlow anti-overengineering rule: required behavior is kept, speculative layers are not.
- Later pattern occurrences (`032`, `081`, URL `060`) must be reviewed independently for new framing/anti-patterns.

### Implications for the Current Implementation

Use patterns only when they remove a real problem. Good SquiFlow examples may include:

- narrow **Adapter** seams for selected providers;
- **Strategy**-like policy selection where multiple real algorithms/providers exist (not listed in this article, so do not attribute Strategy to the source);
- middleware/decorator-style cross-cutting behavior when ASP.NET Core already provides the mechanism;
- **Facade** only when it creates a real stable boundary rather than hiding an unbounded god service.

Do not manufacture generic repository/unit-of-work/one-interface-per-class, factories for every constructor, or observer/event layers for ordinary in-process calls. Current decisions already reject abstraction for its own sake.

## 030 — What do version numbers mean?

**PDF pages:** `62-63`  
**Original archive pages:** `128-129`  
**Classification:** `KEEP`

### SOURCE

The article explains Semantic Versioning using `MAJOR.MINOR.PATCH`:

- increment MAJOR for incompatible API changes;
- increment MINOR for backward-compatible functionality;
- increment PATCH for backward-compatible bug fixes.

Its workflow starts at `0.1.0`, shows a first stable `1.0.0`, then examples of patch/minor/major increments. It also shows pre-release labels such as `alpha`, `beta`, `rc.1` and build metadata.

### VISUAL INSPECTION

PDF page `62` visually maps the three version positions to change meaning and shows a sequence from initial development to stable and later releases. The visual reinforces release communication, not compatibility enforcement by itself.

### INFERENCE

A version number is metadata communicating intended compatibility/change scope. The number itself cannot make two independently deployed components compatible.

### EXTERNAL KNOWLEDGE / CAVEAT

SemVer's “public API” needs a defined scope. SquiFlow has several independently evolving durable/public contracts: product release, HTTP API, Workstation sync protocol, local/central schema, durable jobs/messages, rule/workflow/form snapshots, configuration, and possibly provider contracts. They do not need to share one version number or compatibility window.

A `0.x` product label is not permission to silently corrupt or break customer data. A MAJOR bump also does not make an unsafe database migration acceptable. Migration/reader-writer overlap, deprecation, rollback/roll-forward, and pending offline work still need explicit compatibility rules.

### Connection to previous articles

- Deepens the versioning node introduced in `006` API roadmap.
- Connects directly to SquiFlow's skipped-Workstation compatibility requirements and `001` gRPC contract evolution.
- URL occurrence `045` later has the same title and remains independently unprocessed.

### Implications for the Current Implementation

SquiFlow already uses baseline version `v0.0.15` and explicitly separates product/documentation versioning from API/schema/sync compatibility. Current API docs require an explicit compatibility/retirement contract because Workstations can skip releases, and schema evolution uses expand-migrate-switch-contract before destructive contraction.

Keep that. Do not equate a product SemVer bump with permission to break stored/pending data, durable messages, or older Workstations.

Potential future refinement is to document exactly what counts as SquiFlow's “public API” for product SemVer and which independent contract versions are embedded/negotiated. That can close when the first real cross-version Phase-3 slice exists; no new owner-document decision is required now.

### Critical questions — do not reveal answers yet

**Foundation**
1. What change classes do MAJOR, MINOR, and PATCH communicate under SemVer?
2. What are pre-release labels and build metadata trying to communicate that the three numeric positions do not?

**Critical reasoning**
3. Why does a product MAJOR bump not make an incompatible database migration automatically safe?
4. Why should API version, sync protocol version, schema migration version, and product release version be allowed to differ?
5. What exactly is SquiFlow's “public API” for SemVer purposes, and which internal changes should not force a MAJOR release?
6. Why is `0.x` still required to preserve explicitly supported Workstation/data compatibility?

**Trade-offs**
7. What cost comes from supporting too many old API/sync versions simultaneously?
8. What risk comes from retiring versions too aggressively when Workstations can remain offline for long periods?

**Failure / edge cases**

**System-design interview**
