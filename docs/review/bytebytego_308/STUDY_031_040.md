# 031 — Top 20 System Design Concepts You Should Know

## Identification
- **PDF pages:** `64-65`
- **Original archive pages:** `134-135`
- **Duplicate group:** `ARCH-DUP-04`; occurrence `096` remains independently reviewable later.
- **Classification:** `KEEP` as a completeness prompt; `AVOID` turning the list into an implementation backlog.

## SOURCE
The visual lists twenty concepts: load balancing, caching, database sharding, replication, CAP theorem, consistent hashing, message queues, rate limiting, API gateway, microservices, service discovery, CDNs, database indexing, partitioning, eventual consistency, WebSockets, scalability, fault tolerance, monitoring, and authentication/authorization. The article gives a one-line description of each and asks what other concepts should be added.

## Diagram / visual
The page is a 4×5 grid of concept cards. The design intentionally places infrastructure, data, reliability, communication, security, and observability ideas at the same abstraction level. That is useful for breadth, but it can also imply that every system needs every card.

## INFERENCE
The strongest value is coverage awareness: a designer should know these mechanisms and be able to recognize the problem each addresses. The list is not a dependency graph and does not show prerequisites, failure semantics, operational cost, or when a technique is unnecessary.

## EXTERNAL KNOWLEDGE / caveats
- CAP is simplified. Under a network partition, a distributed system must choose how to trade availability against consistency for the affected operation; partition tolerance is not usually an optional property for a system that must continue operating across a real partition.
- “Caching stores frequently accessed data in memory” is narrower than real caching, which can exist in browsers, edge/CDN nodes, processes, disks, reverse proxies, and distributed stores.
- “Eventual consistency guarantees consistency over time” is too broad without convergence assumptions, conflict rules, delivery/retry behavior, and an authoritative source.
- Database sharding and partitioning overlap conceptually; physical distribution, ownership, routing, and cross-partition operations are the important distinctions.
- Microservices, service discovery, sharding, replicas, and distributed caches are not maturity badges.

## Implications for the Current Implementation
- **KEEP:** SquiFlow already treats these as selectable mechanisms rather than required layers.
- **KEEP:** modular monolith first; microservices/service discovery are deferred until real independently deployed boundaries exist.
- **KEEP:** caching, replicas, partitioning, sharding, and extra nodes are scale triggers after workload evidence.
- **KEEP:** queue/outbox use is for durable work whose semantics require it, not because “message queue” is on a checklist.
- **KEEP:** OpenTelemetry monitoring, ZITADEL authentication, OpenFGA authorization, rate/admission limits, and explicit tenant isolation are already independent concerns.
- **Architect-derived missing concepts important to SquiFlow:** semantic idempotency, concurrency control, tenant isolation, schema/protocol evolution, recovery/RPO/RTO, backpressure/admission, authoritative-vs-derived state, disaster restore, and ambiguity after partial external effects. These omissions do not require a new decision because they are already represented in the owner documents.

## Critical questions
**Foundation**

2. Why are sharding, partitioning, replication, and caching different even though all can distribute data?
3. What problem does service discovery solve only after services are independently addressable?

**Critical reasoning / trade-offs**
4. Why can adding a cache increase failure complexity even while reducing latency?
5. Why is “use microservices for scalability” an incomplete argument?
6. When can replication improve availability but make freshness or write coordination harder?
7. Why can a rate limiter protect infrastructure while still allowing an authorized request to be denied temporarily?
8. Which of the twenty concepts would you intentionally not deploy on a single-node SquiFlow rack and why?

**Failure / edge cases**
9. What happens when the cache is healthy but contains stale authorization data?
10. What happens when a shard is unavailable while other shards are healthy?
11. How should a client behave when rate limiting occurs during a retryable mutation?

**Implementation / system design**

13. Which metrics would prove that database sharding is justified rather than better indexing/query design?
14. How would you prove a new CDN/cache cannot cross tenant boundaries?

**Challenge**

# 032 — 9 OOP Design Patterns You Must Know

## Identification
- **PDF pages:** `66-67`
- **Original archive pages:** `139-140`
- **Classification:** `KEEP` as vocabulary; `AVOID` pattern-driven object graphs.

## SOURCE
The article groups nine patterns into three categories:
- **Creational:** Factory, Singleton, Builder.
- **Structural:** Adapter, Decorator, Proxy.
- **Behavioral:** Strategy, Observer, Command.

It describes each in one sentence and asks which patterns the reader has used.

## Diagram / visual
The infographic visually organizes the patterns by family and illustrates object/class relationships. The category split is the main teaching device: creation, composition, and behavior/interaction.

## INFERENCE
Patterns are reusable names for recurring design shapes. Their value is communication and local problem solving, not proving architectural sophistication.

## EXTERNAL KNOWLEDGE / caveats
- A Singleton is one instance **within its defined runtime/container scope**; it does not create one global instance across multiple processes or nodes.
- Global mutable singleton state can create hidden coupling, test interference, concurrency bugs, and accidental in-memory authority.
- Observer-style in-process notification does not provide durable messaging, replay, delivery guarantees, or cross-process consistency.
- Command objects can clarify intent, but “Command pattern” does not automatically imply CQRS, a message broker, or event sourcing.
- Factories/builders are useful when construction is genuinely variable/complex; they can become forwarding ceremony when object creation is simple.

## Implications for the Current Implementation
- **KEEP:** Strategy/adapter patterns fit real SquiFlow seams such as provider selection or replaceable transport/storage behavior when variation is concrete.
- **KEEP:** command-shaped application operations remain useful for semantic transitions such as approve/refund/publish.
- **AVOID:** generic one-interface-per-class factories, service-locator/singleton globals, manager-handler chains, and observer buses created only to match pattern names.
- **KEEP:** durable cross-process work still uses DB/outbox/Worker semantics; an in-process Observer is not a reliability mechanism.
- No new owner-document change is required.

## Critical questions
1. Why is a pattern name less important than the coupling/problem it removes?
2. When does a Factory improve design, and when is direct construction clearer?
3. Why is a Singleton especially dangerous if it stores tenant, permission, or business state?
4. How is an in-process Observer different from a durable event/message path?
5. Why does using a Command object not require separate read/write databases?
6. When is Decorator preferable to inheritance for cross-cutting behavior?
7. How would you test that a Proxy does not accidentally bypass authorization or change retry semantics?
8. Which SquiFlow provider boundary is a legitimate Strategy/Adapter candidate?
9. Design a document-renderer abstraction using the minimum useful pattern vocabulary.
10. **Challenge:** a team uses Factory + Singleton + Observer + Command for every operation. What signals tell you the pattern system has become more complex than the business problem?

# 033 — A Cheatsheet on REST API Design Best Practices

## Identification
- **PDF pages:** `68-69`
- **Original archive pages:** `143-144`
- **Exact URL overlap later:** URL `064` remains a separate ledger occurrence.
- **Classification:** `KEEP`, with important retry/idempotency qualifications.

## SOURCE
The article recommends:
1. resource-oriented paths and appropriate HTTP verbs;
2. API versioning;
3. standard error codes;
4. idempotent APIs for safe retries, especially POST operations;
5. idempotency keys for side-effect deduplication;
6. pagination, including offset, cursor, and keyset strategies;
7. authentication, authorization, and HTTPS.

The visual additionally shows versioning examples, HTTP status families, noun-based resources, an idempotency-key storage example, a method/idempotence table, offset pagination, and JWT structure.

## INFERENCE
The article combines interface consistency, retry safety, bounded collection access, and security. These are separate contracts that happen to meet at the API boundary.

## EXTERNAL KNOWLEDGE / caveats
- Not every endpoint or HTTP method is inherently idempotent. A POST can be made safely retryable only when the application defines semantic identity/deduplication for the intended operation.
- “Repeated requests produce the same result” is an oversimplification: idempotency primarily protects the **semantic effect**; the literal response bytes or transient metadata need not be identical.
- PUT/DELETE being idempotent at HTTP-semantics level does not automatically make a buggy backend implementation retry-safe.
- Offset pagination is simple but can drift under concurrent inserts/deletes and can become expensive at deep offsets; cursor/keyset behavior also requires stable ordering and contract design.
- Authentication does not replace per-resource authorization, tenant isolation, input/field authorization, or domain validation.

## Implications for the Current Implementation
- **KEEP:** REST/task-oriented HTTP remains the v0.0.15 application baseline without strict REST purity.
- **KEEP:** semantic action subresources are valid for approvals/refunds/publications where generic CRUD would obscure intent.
- **KEEP:** caller-provided semantic idempotency keys for retryable mutations.
- **KEEP:** explicit version compatibility because Workstations can skip releases.
- **KEEP:** stable SquiFlow Problem Details/error classification and bounded pagination.
- **KEEP:** ZITADEL authentication → TenantContext → OpenFGA/resource authorization → domain/concurrency checks.
- **AVOID:** treating the visual’s method table as sufficient proof of application retry safety.

## Critical questions
1. Why can a POST be retry-safe even though POST is not inherently idempotent?
2. What exactly must an idempotency key identify: an HTTP request or an intended business operation?
3. When is cursor/keyset pagination safer than offset pagination?
4. Why can resource-oriented naming coexist with semantic action endpoints?
5. What should happen if the server commits a mutation but the HTTP response is lost?
6. How should old Workstations be rejected when they no longer satisfy the supported protocol window?
7. What tenant/permission dimensions must be included before any API response can be cached?
8. Design a retry-safe `RefundPayment` API including conflict, dependency, authorization, and duplicate behavior.
9. **Challenge:** two requests use the same idempotency key but different payloads. What must the server do and why?

# 036 — The 4 Types of SQL Joins

## Identification
- **PDF pages:** `74-75`
- **Original archive pages:** `151-152`
- **Classification:** `KEEP` as relational-query foundation.

## SOURCE
The article defines:
- **INNER JOIN:** matching rows only;
- **LEFT JOIN:** all left rows plus right matches, with right-side NULLs for non-matches;
- **RIGHT JOIN:** all right rows plus left matches, with left-side NULLs for non-matches;
- **FULL OUTER JOIN:** all rows from both sides, filling missing matches with NULL.

The visual uses colored row/value diagrams to show which rows survive each join.

## INFERENCE
Join type is part of business meaning. Choosing the wrong join can silently omit entities or create NULL-bearing optional relationships.

## EXTERNAL KNOWLEDGE / caveats
- Correctness is only the first concern; join order, indexes, cardinality estimates, data skew, selected columns, filters, and row multiplication determine performance.
- One-to-many joins can multiply rows and accidentally double-count totals if aggregates are applied at the wrong level.
- NULL introduced by outer joins must not be confused with actual stored NULL meaning.

## Implications for the Current Implementation
- **KEEP:** normalized relational modeling remains the authoritative default for core invariants.
- **KEEP:** Phase-3 query-plan tests must include real joins at representative tenant/data cardinalities.
- **KEEP:** financial/report totals must test one-to-many joins for duplication rather than relying on visually plausible SQL.
- **AVOID:** denormalizing solely to avoid learning/optimizing joins before a measured bottleneck exists.

## Critical questions
1. Which join would preserve customers that currently have no orders?
2. How can an outer join change the meaning of NULL in the result?
3. Why can a syntactically correct join double-count invoice totals?
4. What indexes might help a hot tenant-scoped join, and what write cost do they add?
5. How would you test a report query against missing relationships and one-to-many expansion?
6. **Challenge:** a query is logically correct but slow only for one very large tenant. Which earlier concepts should you investigate before denormalizing?

# 039 — Explaining JSON Web Token (JWT) with simple terms

## Identification
- **PDF pages:** `79-80`
- **Original archive pages:** `156-157`
- **Semantic overlap:** entries `005`, `008`, `010`; this occurrence is still independently covered.
- **Classification:** `KEEP` as a conceptual explanation; `AVOID` custom SquiFlow JWT authority.

## SOURCE
The article uses a box analogy. A JWT contains a header, payload, and signature. The header describes token type/security, the payload contains information, and the signature is described as a seal created with a secret so tampering can be detected. The server reads the header/payload and checks the signature. It asks when JWT should be used for authentication and what other authentication methods exist.

## Diagram / visual
The hand-drawn infographic shows JWT structure, an illustrative message-to-token flow, “working,” and signing/verification. It is intentionally beginner-friendly rather than protocol-complete.

## INFERENCE
The article’s main idea is integrity of claims carried in a compact token: the receiver can validate whether the signed content was altered, assuming it trusts the issuer/key and validation rules.

## EXTERNAL KNOWLEDGE / caveats
- A signature is not encryption. Standard JWT header/payload data is generally readable by whoever possesses the token unless a separate encryption mechanism is used.
- JWTs may use symmetric or asymmetric signing; “only the sender knows the secret” describes only some algorithms/configurations.
- Signature validity alone is insufficient: issuer, audience, expiry/not-before, key selection/rotation, token type, algorithm policy, replay/session/revocation semantics, and application authorization matter.
- A JWT is a token format, not a complete authentication architecture and not a current-authorization database.

## Implications for the Current Implementation
- **KEEP:** ZITADEL/OIDC owns authentication/token issuance/validation semantics.
- **KEEP:** SquiFlow does not create a second JWT/PASETO/password subsystem.
- **KEEP:** current OpenFGA/resource authorization and TenantContext are checked independently of token validity.
- **KEEP:** old/offline permission snapshots or claims never become server capability tokens.
- No new decision required.

## Critical questions
1. What security property does a JWT signature provide that a plain JSON payload does not?
2. Why should sensitive secrets not be placed in a normal JWT payload merely because it is signed?
3. What is the difference between proving “this token came from a trusted issuer” and “this user may refund this payment now”?
4. How do key rotation and token lifetime interact?
5. What happens when a user’s OpenFGA permission is revoked while a previously issued token remains cryptographically valid?
6. Why might server-managed Web sessions still be preferable for SquiFlow Web even if the identity provider uses JWTs internally?
7. **Challenge:** design the validation chain for a Workstation request carrying a valid OIDC access token but stale tenant membership.

# 040 — How to Deploy Services

## Identification
- **PDF pages:** `81-82`
- **Original archive pages:** `160-161`
- **Classification:** `KEEP / STRENGTHEN release reasoning`; progressive strategies remain topology-triggered.

## SOURCE
The article says deployment/upgrades are risky and compares four approaches:

1. **Multi-Service Deployment:** upgrade multiple services simultaneously; easy to implement, but dependency testing/management and safe rollback are difficult.
2. **Blue-Green Deployment:** maintain two identical production-quality environments, test the newer one, then switch traffic; rollback is simple but duplicated environments can be expensive.
3. **Canary Deployment:** gradually expose the new version to subsets of users; described as cheaper than blue-green and rollback-friendly, but operationally more complicated because the canary must be monitored while traffic migrates.
4. **A/B Test:** run different versions simultaneously for different user subsets/experiments; described as a cheap way to test features in production, with a need for careful exposure control.

The diagram shows simultaneous service-version upgrades, blue/green environment switching, percentage-based canary expansion, and split version percentages for A/B testing.

## INFERENCE
The techniques trade infrastructure duplication, blast radius, rollback speed, observability needs, compatibility requirements, and operational complexity. Deployment strategy is inseparable from data/schema compatibility.

## EXTERNAL KNOWLEDGE / caveats
- Canary deployments can still have a staging environment; “no staging environment” is not inherent to canary.
- Whether canary is cheaper than blue-green depends on topology, routing, observability, and operational cost.
- A/B testing is primarily an experimentation/exposure technique; it can use deployment mechanisms but should not be confused with rollback-safe release engineering.
- Rollback of application binaries may be easy while database/data migrations are not safely reversible. Expand-migrate-switch-contract and roll-forward are often safer.
- Multi-service release risk depends heavily on contract compatibility; coordinated deployment should not be used to hide incompatible service contracts.

## Implications for the Current Implementation
Current GitLab owner docs already say:
- the first paying-customer release promotes one verified immutable artifact;
- configuration/secrets stay outside the artifact;
- migrations/capacity/dependencies are preflighted;
- health plus an authorized smoke journey is evaluated;
- rollback/roll-forward/maintenance behavior is explicit;
- a single rack node does not claim zero downtime;
- blue-green/canary/progressive delivery requires spare topology, routing, compatible contracts/schema, telemetry, and recovery evidence.

Therefore:
- **KEEP:** honest maintenance-window/in-place deployment may be safer initially.
- **KEEP:** blue-green/canary remain open strategies only after topology earns them.
- **KEEP:** Core API/Admin API/Worker compatibility must not require unsafe all-at-once synchronized releases.
- **KEEP:** schema evolution is expand-migrate-switch-contract where destructive contraction would break old Workstations or durable work.
- **Architect-derived deployment question:** feature flags can separate code deployment from feature exposure, but they need ownership, expiry/removal, authorization, migration compatibility, and failure behavior; they are not automatically required now.
- No new user approval is needed from this occurrence because the accepted release policy already captures the material finding.

## Critical questions
**Foundation / reasoning**
1. What resource cost does blue-green add in exchange for fast traffic rollback?
2. Why does canary require strong observability rather than merely a traffic splitter?
3. Why is A/B experimentation not the same objective as canary risk reduction?
4. Why can an application rollback still fail if the database schema has already been destructively migrated?

**Failure / edge cases**
5. What happens if the new version writes data the old version cannot read during a canary?
6. What should happen if health checks pass but the authorized smoke journey fails?
7. How do you stop a rollout when only one tenant/workload class is failing?
8. How should queued durable work behave while Worker versions overlap?

**Implementation / system design**
9. Design the safest first-production release for one active SquiFlow rack node with no spare production node.
10. What additional infrastructure/evidence would justify moving that deployment to blue-green?
11. How would you roll out a schema change when Workstations can remain offline across releases?
12. Which metrics and error budgets would you watch during a canary?

**Challenge**
13. A canary shows normal CPU/error rate, but new-version orders occasionally create duplicate downstream payments after client timeouts. Why is deployment telemetry alone insufficient, and which earlier correctness mechanisms must stop the rollout?

8. Deployment safety depends on schema/contract compatibility and recovery, not only traffic-routing strategy.

## Highest-value SquiFlow implications confirmed
- Keep the modular monolith and single-node-first profile until measured boundaries/scale demand more.
- Keep semantic idempotency and explicit compatibility as first-class API/sync requirements.
- Keep real query-plan/cardinality tests rather than index guesses.
- Keep ZITADEL authentication separate from OpenFGA authorization and TenantContext.
- Keep release artifact/migration/health/smoke/rollback-or-roll-forward gates; do not claim blue-green/canary without topology.
- Keep cloud/provider decisions behind narrow capability boundaries and real workload/economic evidence.

## Premature optimizations / patterns to avoid
- microservices/service discovery because they appear on a system-design list;
- sharding/replication/distributed caches before measured need;
- global mutable Singleton state;
- observer/event-bus abstractions used as fake durability;
- REST purity that obscures domain commands;
- AWS/cloud service adoption by catalog matching;
- denormalization before real join/query-plan evidence;
- multi-cloud portability work without a requirement;
- custom JWT authority around ZITADEL;
- canary/blue-green claims on a topology that cannot actually support them.
