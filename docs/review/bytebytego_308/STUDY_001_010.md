## B. Core concept

### SOURCE

The article introduces RPC as communication between services on different servers while presenting an invocation style that can resemble a local function call. Its example places an Order Service and Payment Service on separate servers and shows the Order Service acting as the gRPC client. The client-side path encodes data into a binary form, passes it through the gRPC runtime and transport, sends it over HTTP/2, and the Payment Service reverses that path before invoking the server application. The result follows the reverse direction back to the caller.

### INFERENCE

The central architectural idea is not merely “binary is fast.” It is that an application-level method call crosses a real network boundary through generated/defined contracts, serialization, a runtime and a transport stack. Once the call becomes remote, network-failure semantics exist even if the programming model looks local.

## C. Important concepts

### SOURCE

The article introduces or visibly relies on all of the following:

1. **RPC / Remote Procedure Call** — invoking behavior in a different service/process.
2. **Local call versus remote call** — the top diagram contrasts a same-process function call with an Order Service calling a Payment Service on another server.
3. **gRPC client and gRPC server roles** — Order Service is the caller; Payment Service is the receiver.
4. **Client application layer** — business/application code initiates the RPC.
5. **Client stub** — the diagram labels the client-side RPC abstraction as a client stub.
6. **Encoding / decoding layer** — request and response are serialized/deserialized around the RPC runtime.
7. **Binary encoding / ProtoBuf** — the visual contrasts JSON with a compact binary representation and labels the binary format as ProtoBuf.
8. **gRPC runtime** — sits between encoding/decoding and transport.
9. **Transport layer** — carries encoded messages across the network.
10. **HTTP/2** — shown as the network transport in step 5.
11. **Server decode and local invocation** — the server receives, decodes and invokes its application method.
12. **Response serialization** — the result is encoded and transmitted back through the same layered path.
13. **REST/JSON at an upstream boundary** — the example begins with a REST call from a client into the Order Service, then converts that interaction into gRPC for the downstream Payment Service call.
14. **Performance claim** — the text says gRPC is “said to be 5X faster than JSON” because of binary encoding and network optimizations.

### EXTERNAL KNOWLEDGE / CAVEATS

- The REST/JSON step is **not intrinsic to gRPC**. It is one example of an edge/client API using HTTP/JSON while an internal service boundary uses gRPC.
- The statement that gRPC is “5X faster than JSON” is a workload-dependent secondary-source claim, not a universal engineering constant. End-to-end time can be dominated by database work, business logic, external providers, queueing, TLS, network distance or contention rather than serialization.
- A generated client stub is code/proxy behavior; the request **message** is serialized. Saying “the stub is encoded” is a useful simplification in the article but is not the most precise description of the implementation.
- Modern gRPC normally uses Protocol Buffers by default, but gRPC's architectural value also includes generated contracts, streaming forms, deadlines/cancellation and runtime semantics; binary size alone is not the whole decision.

The most important visual boundary is the network line between the two transport layers. Everything above it can make the call feel function-like, but that dashed boundary is where latency, timeout, disconnection, retry and partial-failure concerns enter the design.

## E. How it works

### SOURCE — article sequence

1. The external client sends a REST request whose body is usually JSON in the example.
2. The Order Service receives the request.
3. The Order Service initiates an RPC toward Payment Service through its client-side stub/encoding path.
4. The request is encoded into binary data and handed to the lower transport stack.
5. The message crosses the network via HTTP/2.
6. Payment Service receives the network data.
7. The server-side stack decodes it.
8. The server application/local method is invoked.
9. The server application produces a result.
10. The result is encoded.
11. The encoded response is sent through the transport.
12. Order Service receives the response.
13. The response is decoded.
14. The result is returned to the calling client application.

### EXTERNAL KNOWLEDGE — operationally complete version

A production design also needs to account for contract/schema compatibility, connection establishment/reuse, authentication metadata, request deadlines, cancellation, message-size limits, flow control, retry ownership, idempotency for retryable mutations, tracing/correlation and what happens when the caller times out after the server has already committed an effect.

## F. Why it matters

### SOURCE

The article's motivation is efficient communication between remote services while preserving a call-oriented developer model. It emphasizes binary encoding and HTTP/2 as performance-oriented characteristics.

### EXTERNAL KNOWLEDGE

Engineers commonly consider gRPC when they need one or more of:

- strongly generated contracts across processes;
- high-frequency synchronous service calls;
- compact structured payloads;
- client-streaming, server-streaming or bidirectional streaming;
- a consistent RPC runtime with deadlines/cancellation and metadata.

Its value is greatest when those properties solve a measured problem. It is much less valuable when the real work is local/in-process or when a durable asynchronous workflow is semantically more appropriate.

## G. Trade-offs and limitations

### Advantages

- **Compact payloads:** Protocol Buffers are commonly smaller than equivalent verbose JSON payloads.
- **Generated contracts:** typed client/server code can reduce hand-written request plumbing and catch some compatibility mistakes earlier.
- **Streaming:** gRPC supports interaction patterns beyond one request / one response.
- **Connection reuse / multiplexing:** HTTP/2 can efficiently carry many logical RPCs over connections.
- **Clear service contracts:** useful when independently versioned processes genuinely need a stable RPC boundary.

### Disadvantages / operational costs

- **Remote-call fallacy:** a remote call can look like a local method but has fundamentally different latency and failure semantics.
- **Browser friction:** ordinary browsers do not expose every native gRPC capability directly; gRPC-Web, transcoding or a separate browser-facing HTTP API may be needed.
- **Binary debugging:** payloads are less immediately inspectable than JSON without schema-aware tooling.
- **Contract evolution discipline:** `.proto` field numbers, reserved fields, backward/forward compatibility and generated-client rollout become an explicit responsibility.
- **Infrastructure compatibility:** proxies, load balancers and edges must correctly support the HTTP/2/streaming behavior the application depends on.
- **Long-lived connection behavior:** reconnects, keepalives, backpressure and connection churn can become operational concerns.
- **Retry danger:** automatic or layered retries can duplicate a mutation unless semantic idempotency is designed independently.
- **Timeout ambiguity:** the caller can give up after the server has already performed the operation.
- **Tighter synchronous coupling:** the caller often inherits downstream latency and availability unless the workflow is restructured.
- **Generated-code/toolchain overhead:** schema compiler/runtime/version dependencies become part of build and release compatibility.

### Bad-choice situations

- Two modules run in the same process and can use a normal in-process call.
- The operation is naturally a durable after-commit consequence that should be queued rather than synchronously chained.
- Browser/external integration simplicity matters more than RPC efficiency.
- Payload/serialization is not a meaningful bottleneck.
- The team cannot yet operate the added schema, streaming, proxy and observability surface reliably.

## H. Alternatives and comparisons

### In-process call vs gRPC

Choose **in-process** when both capabilities share the same runtime and failure boundary. It avoids serialization, network latency, transport failures and distributed versioning. Choose **gRPC** only after there is a real process/network boundary.

### REST/HTTP + JSON vs gRPC

Choose **REST/task-oriented HTTP** when browser/external compatibility, debuggability, standard HTTP semantics and simplicity dominate. Consider **gRPC** when generated contracts, streaming, binary efficiency or sustained high-frequency RPC provide measurable value.

### Durable asynchronous work vs gRPC

Use **durable async** for long-running work or consequences that should survive caller disconnects and be retried/reconciled independently. Use **synchronous gRPC/HTTP** when the caller genuinely needs an answer before it can proceed.

### Message broker/event flow vs gRPC

A message/job/event path changes the interaction semantics: the sender is not simply waiting for a remote procedure result. Do not replace a durable asynchronous ownership model with gRPC merely to reduce components, and do not introduce a broker for a simple bounded synchronous request that needs an immediate answer.

## I. Real implementation considerations

### 10× / 100× traffic

- Measure whether serialization/network framing is actually a significant part of latency/CPU before attributing scaling problems to JSON.
- Long-lived HTTP/2 connections can help, but server concurrency, DB pools, downstream provider limits, per-tenant fairness and flow control can become the real bottlenecks first.
- Large reconnect bursts can turn efficient individual RPCs into an overload event if admission control and backpressure are absent.

### Partial network failure

- A connection can break after the server receives the request but before the client receives the response.
- The client must not infer “failed” means “nothing happened.”
- Retry ownership and semantic idempotency must be explicit for mutations.

### State

- gRPC itself is a transport/RPC mechanism; it does not decide where authoritative business state lives.
- Streaming connection state must not become the only copy of durable business progress.

### Dependency unavailable

- A synchronous caller needs a bounded deadline and explicit failure behavior.
- Infinite waits or retry storms are unacceptable.
- Where temporary unavailability should not block the user-facing operation, the architecture may need a durable async boundary instead of another synchronous retry layer.

### Observability

- Propagate trace/correlation context across RPCs.
- Measure RPC latency percentiles, error/status classes, deadline exceeded/cancellation, payload sizes, connection churn and downstream contribution.
- Binary payloads require schema-aware diagnostics rather than assuming packet/body inspection will be as convenient as JSON.

### Deployment / rollback

- Client and server versions can coexist during rollout; `.proto` changes must preserve the supported overlap window.
- Old Workstations may remain offline across multiple server releases, making compatibility significantly harder than a same-day server rollout.
- Edge/proxy changes must be tested with real HTTP/2/streaming behavior before production dependency is assumed.

## Implications for the Current Implementation

### Current SquiFlow position checked against the GitLab branch

The current accepted direction on `docs/bytebytego-308-exhaustive-study` inherits the approved transport work from `docs/grpc-preferred-transport-policy`:

- ordinary modules in the modular monolith communicate **in-process**;
- gRPC is a **preferred candidate, not a decided universal transport**, at real process/service boundaries;
- Workstation synchronization correctness remains transport-independent;
- Phase 3 may compare ordinary HTTP against gRPC for the first sync transport;
- Admin API and Core API remain independent normal runtime planes and do not gain a direct dependency merely because gRPC exists;
- durable async work remains preferred for long-running/after-commit consequences.

### Classification

**KEEP** — In-process communication between ordinary modules. Article 001 gives no reason to turn local module calls into RPC.

**KEEP** — Transport-independent Workstation sync correctness. Authentication, TenantContext, OpenFGA authorization, idempotency, expected-version/conflict handling, durable local outbox and authoritative central transaction are not solved by gRPC.

**NEEDS MEASUREMENT** — Workstation sync transport. gRPC should win only if representative Phase-3 measurements show material value from streaming, generated contracts, binary efficiency or sustained high-frequency RPC compared with the simpler HTTP baseline.

**LATER / SCALE TRIGGER** — Independently deployed synchronous services. If a real extracted service appears and requires high-rate synchronous communication, gRPC becomes an early candidate; it is not a reason to extract the service.

**AVOID** — Admin API → Core API gRPC as default architecture. That would weaken the deliberately independent control-plane/data-plane runtime boundary.

**AVOID** — Treating the article's “5X faster” statement as a SquiFlow performance assumption.

### Bottlenecks / failure cases to preserve in the design

- reconnect storms from many Workstations;
- response loss after central commit;
- old Workstation versus new server contract skew;
- authorization change while the device is offline;
- network interruption during streaming;
- large attachments starving small semantic sync operations;
- downstream ZITADEL/OpenFGA/DB latency dominating transport time;
- proxy/edge HTTP/2 behavior that differs from local development.

### Does Article 001 require a new architecture decision now?

**No.** The already-approved gRPC transport-selection policy captures the material architectural conclusion from this exposure. This exhaustive pass adds stronger traceability and failure-mode reasoning, but it does not justify changing an owner document again at this point.

A future Phase-3 POC should explicitly test streaming interruption/reconnect, backpressure/flow control, message/batch limits and end-to-end business latency in addition to serialization benchmarks; those are implementation-test details under the existing decision rather than a new technology commitment.
