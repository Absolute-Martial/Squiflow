# 051 — How SQL Query Executes In A Database?

## Identification
- **PDF pages:** `103-104`
- **Original archive pages:** `202-203`
- **Classification:** `KEEP`; `NEEDS MEASUREMENT` for provider-specific planning/execution behavior.

## SOURCE
The article presents four main stages:
1. **Transport Subsystem** receives the query, manages the client connection and performs authentication/authorization checks.
2. **Query Processor** contains a Query Parser and Query Optimizer. The parser breaks the query into clauses, checks syntax and creates a parse tree. The optimizer is described as checking semantic issues such as table existence and finding the most efficient execution approach. Its output is the execution plan.
3. **Execution Engine** coordinates the plan steps, calls the Storage Engine and combines results.
4. **Storage Engine** performs low-level reads/writes through components including a transaction manager, lock manager, buffer manager and recovery manager.

The visual uses a `SELECT name, age FROM users WHERE city = 'San Francisco'` example and shows an execution-plan box containing an index seek, column lookup and qualifying-row return.

## Diagram / visual
The figure makes a useful separation between:
- connection/session ingress;
- parse/plan work;
- execution coordination;
- storage/transaction/locking/buffer/recovery responsibilities.

It also shows that the same SQL text can be transformed into lower-level physical operations such as an index seek rather than being executed clause-by-clause literally.

## INFERENCE
The key architectural lesson is that query latency is produced by several layers. A slow query can come from parsing/planning, bad statistics/cardinality estimates, an inefficient physical plan, lock waits, buffer/cache misses, disk I/O, transaction contention, temp spill, or resource saturation. Therefore “rewrite the SQL” is only one possible response.

## EXTERNAL KNOWLEDGE / caveats
- Real DBMS component boundaries vary. PostgreSQL, SQL Server, MySQL/InnoDB and others do not all expose a subsystem literally named “Transport Subsystem” or split semantic analysis exactly as the source describes.
- Table/column binding and semantic validation are often separate from cost-based optimization; the article compresses those phases for teaching.
- The chosen execution plan is driven by statistics, cost models, indexes, parameter values, memory, parallelism and provider-specific rules.
- Authentication/authorization at the DB connection layer is not a substitute for application authentication, tenant context, OpenFGA/resource authorization or domain rules.
- Locking semantics differ under MVCC/isolation models; “lock manager” should not be interpreted as every read taking an exclusive-style lock.
- Recovery also involves durable logging/WAL/redo/undo or equivalent provider mechanisms that are not shown in detail.
- Plan caching/parameter-sensitive planning can make the same query text behave differently under different parameter distributions.

## Implications for the Current Implementation
- **KEEP:** Phase 3 must prove real query plans and representative cardinalities, not infer performance from SQL text.
- **KEEP:** if PostgreSQL is selected, qualification still includes connection/backend-process cost, WAL/checkpoints, autovacuum, temp/sort spill, archive/log/disk growth and crash/restart behavior.
- **KEEP:** tenant authorization happens at the application boundary; database roles/RLS are defense in depth rather than the sole authority path.
- **KEEP:** expected-version concurrency and database constraints protect application invariants independently of query-planner internals.
- **Architect-derived implementation question:** hot-query testing should include plan stability under tenant skew and reconnect/import bursts, not only average datasets.
- No material owner-document change is required; these requirements are already represented in the current persistence/verification gates.

## Critical questions
**Foundation**
1. What is the difference between parsing SQL and choosing an execution plan?
2. Why can the same SQL text use different physical plans on different datasets?
3. What responsibility does the buffer manager conceptually own?

**Critical reasoning / trade-offs**
4. Why can an index seek be worse than a sequential scan for some queries?
5. How can stale statistics lead to an inefficient plan?
6. Why should application authorization not be delegated entirely to the DB connection account?
7. How can one large tenant create a bad plan even when an average tenant performs well?

**Failure / edge cases**
8. What symptoms would distinguish lock contention from disk I/O pressure?
9. What can happen when a query spills to temporary disk because memory is insufficient?
10. How can plan caching make a query fast for one parameter and slow for another?

**Implementation / system design**
11. Design a Phase-3 hot-query test that includes tenant skew, realistic indexes and execution-plan evidence.
12. Which telemetry should correlate API latency with DB plan/lock/pool evidence?
13. How would you decide whether to add an index, rewrite a query or change a data-access pattern?

**Challenge**

# 052 — How RabbitMQ Works?

## Identification
- **PDF pages:** `105-106`
- **Original archive pages:** `206-207`
- **Classification:** `LATER / SCALE TRIGGER`; `AVOID` preselecting RabbitMQ as the Worker baseline.

## SOURCE
The article describes RabbitMQ as a message broker for asynchronous communication. Its flow is:
1. a producer sends a message to the RabbitMQ broker;
2. the broker routes through an exchange;
3. bindings connect exchanges to queues using routing/binding rules;
4. **Direct** exchange uses exact routing-key matches;
5. **Topic** exchange uses patterns;
6. **Fanout** exchange broadcasts to all bound queues;
7. a consumer pulls messages from a queue and processes them, possibly passing results to other systems.

The visual shows Producer → RabbitMQ Broker → Exchange → Direct/Topic/Fanout routing → Queues → Consumer.

## Diagram / visual
The most valuable visual idea is that producers generally publish to an **exchange/routing layer**, not directly to a specific consumer. Routing and durable work ownership are separate concepts.

## INFERENCE
RabbitMQ becomes useful when the system genuinely needs broker-managed durable asynchronous delivery, competing consumers or routing/fan-out semantics that are operationally worth a separate broker. Choosing a broker also creates new correctness responsibilities around publish confirmation, redelivery, acknowledgement, retry and poison-message handling.

## EXTERNAL KNOWLEDGE / caveats
The source omits several production-critical semantics:
- producer confirms / publish outcome ambiguity;
- durable queues/exchanges and persistent messages;
- consumer acknowledgements and the point at which acknowledgement is safe;
- redelivery and duplicate processing;
- prefetch and consumer backpressure;
- dead-lettering/poison-message policy;
- retries/delays and retry storms;
- exclusive/auto-delete/transient resources;
- headers exchange and default exchange behavior;
- ordering scope with multiple consumers/requeues;
- cluster/quorum/availability choices;
- disk/memory alarms and broker resource saturation.

RabbitMQ does not automatically provide application-level exactly-once effects. If a consumer commits business state and loses the acknowledgement, redelivery can occur; the consumer/effect therefore still needs semantic idempotency/reconciliation.

## Implications for the Current Implementation
- **FIT / positive future candidate:** RabbitMQ is attractive if SquiFlow develops real broker-managed routing, competing-consumer, independent-queue-lifecycle, or multi-destination delivery needs that exceed the simple DB-backed job/outbox mechanism.
- **CURRENT FIT:** Phase 6 still starts from the simplest durable Worker/job mechanism because the first concrete workload has not yet proven it needs a broker.
- **COMPLEMENTARY:** RabbitMQ may coexist with the transactional outbox; the outbox can own reliable publication from the authoritative DB transaction while RabbitMQ owns broker delivery/routing afterward.
- **OTHER FIT:** Kafka/event-stream infrastructure may be better than RabbitMQ if the future requirement is replayable high-throughput history with independent consumer offsets rather than work-queue/routing semantics.
- **If adopted later, required gate:** publisher confirms/uncertain publish handling, consumer ack-after-safe-effect, bounded prefetch/concurrency, idempotent/reconcilable consumers, poison/dead-letter policy, duplicate/redelivery tests, broker outage behavior, and drain/recovery runbooks.
- **UNCHANGED:** payments, stock, permissions and protected transitions remain owned by authoritative transactions; broker delivery never replaces semantic idempotency or domain authority.

## Critical questions
1. What is the difference between an exchange and a queue?
2. When would Direct, Topic and Fanout routing produce materially different system behavior?
3. Why can a consumer receive the same message more than once?
4. At what point is it safe for a consumer to acknowledge a message?
5. Why does broker persistence not remove the need for idempotent business effects?
6. How can high prefetch improve throughput while increasing recovery/blast radius?
7. What should happen to a poison message that repeatedly fails?
8. How should a producer reason about an uncertain publish result after a network timeout?
9. When is multiple-outbox delivery simpler than introducing RabbitMQ fanout?
10. What metrics would prove a DB-backed job mechanism is no longer sufficient?
11. Design a durable SquiFlow document-generation Worker flow using RabbitMQ without losing business truth when broker or consumer crashes.
12. **Challenge:** the consumer commits a supplier-payment consequence, crashes before ACK, and receives the message again. Which invariants prevent duplicate financial effects?

# 053 — A Cheatsheet on Kubernetes

## Identification
- **PDF pages:** `107-108`
- **Original archive pages:** `210-211`
- **Classification:** `AVOID / REJECT AS BASELINE`; `LATER / SCALE TRIGGER` only after a real orchestration problem.

## SOURCE
The article describes Kubernetes as an open-source container orchestration platform. Developers create manifests describing desired application instances/resources/configuration. The visual/article covers:
- **control plane** components: API Server, etcd, Controller Manager, Scheduler;
- **worker nodes** with Kubelet, container runtime, kube-proxy and Pods;
- common resources: Pods, Deployments, Services, Volumes/Persistent Volumes;
- request flow: submit desired state → API Server → Scheduler assigns node → Kubelet starts Pod → Pod runs;
- Horizontal Pod Autoscaler scaling replicas using observed CPU, memory or custom metrics.

The source says the control plane is deployed on the “master node.”

## Diagram / visual
The infographic has five sections: developer view, cluster architecture, key resources, request flow and HPA. It is useful because it emphasizes desired-state orchestration rather than “run Docker commands on many machines.”

## INFERENCE
Kubernetes solves a recurring operations problem: maintain desired workload state across a cluster, place workloads, expose them stably and reconcile failures/scale changes. That value appears only when there is enough multi-node/process orchestration pressure to justify the platform itself.

## EXTERNAL KNOWLEDGE / caveats
- “Master node” is older/simplified terminology; production control planes can be multi-node/highly available and are conceptually distinct from one master machine.
- Kube-proxy is not the only possible service-network implementation; some environments use alternative dataplanes.
- A PersistentVolume is durable relative to Pod replacement only according to the storage class/reclaim/backend contract. It is not a backup and does not automatically survive every cluster/storage failure.
- HPA only scales what the metric/resource model allows and can amplify downstream pressure if database/provider capacity is the real bottleneck.
- Kubernetes does not create application-level HA by itself. Databases, identity providers, durable queues, object stores, schemas, rollout compatibility and stateful dependencies must still tolerate failure.
- Running Kubernetes on a small single physical node adds control-plane/runtime resource cost without creating true physical failover.

## Implications for the Current Implementation
- **FIT / positive future candidate:** Kubernetes is strong when SquiFlow develops a real multi-node desired-state problem: recurring scheduling/placement, replica reconciliation, service discovery, rolling rollout, automatic replacement/failover, or autoscaling that simpler operations can no longer own reliably.
- **CURRENT FIT:** the present lower-spec owned-rack/small-process topology does not yet have that orchestration problem, so simpler host/container deployment remains better matched today.
- **COMPLEMENTARY:** containerization and Kubernetes are not mutually exclusive; containers can be used before Kubernetes and later become Kubernetes workloads if the orchestration trigger appears.
- **ADOPTION EVIDENCE:** compare operational burden/resource cost against simpler host service/Compose/VM automation on real hardware; prove stateful DB/object/identity recovery independently.
- **UNCHANGED:** Kubernetes would not itself create backup, database HA, schema compatibility, business idempotency, or tenant authorization.

1. What problem does the Kubernetes control plane solve that Docker alone does not?
2. Why is a Deployment different from a Pod?
3. What stable abstraction does a Service provide when Pods are replaced?
4. Why is a PersistentVolume not a backup?
5. How can HPA make a database bottleneck worse?
6. What does a single-node Kubernetes cluster fail to provide during physical node loss?
7. Which SquiFlow trigger would justify service discovery becoming an actual problem?

# 054 — 6 Data Structures to Save Storage

## Identification
- **PDF pages:** `109-110`
- **Original archive pages:** `212-213`
- **Classification:** `LATER / NEEDS MEASUREMENT`; `AVOID` approximate structures for authoritative business/security decisions.

## SOURCE
The six structures/algorithms are:
1. **Bloom Filter** — probabilistic set-membership test.
2. **HyperLogLog** — approximate unique-element counting with low memory.
3. **Cuckoo Filter** — space-efficient membership structure supporting deletion.
4. **MinHash** — compressed signatures for estimating set similarity.
5. **SkipList** — layered linked-list structure for fast search/insert/delete.
6. **Count-Min Sketch** — approximate item-frequency estimation in streams.

The visual calls them structures that “save database storage” and gives a simplified mini-diagram for each.

## INFERENCE
The common theme is trading exactness, representation cost or structural overhead for better memory/storage/lookup characteristics under a particular workload. However, the list mixes probabilistic sketches/filters with an ordered index structure (SkipList), so “save storage” is not one uniform property.

## EXTERNAL KNOWLEDGE / caveats
- Bloom filters have false positives; standard Bloom filters are usually designed to avoid false negatives while their construction/state assumptions remain valid.
- HyperLogLog and Count-Min Sketch provide approximations with error bounds/probabilistic behavior; they cannot replace exact authoritative counts when correctness requires exactness.
- Cuckoo-filter advantages depend on load factor, fingerprint size, implementation and workload; “better lookup performance” is not universal.
- MinHash estimates set similarity and is useful for similarity/dedup search, not exact membership or exact equality.
- SkipLists generally trade additional pointer/index structure for logarithmic expected operations; calling them a storage-saving structure is context-dependent.
- These are implementation mechanisms, not product data-model decisions.

## Implications for the Current Implementation
- **FIT:** Bloom/Cuckoo filters can be useful as negative-membership/lookup hints where false positives are harmless because the authoritative store is still checked.
- **FIT:** HyperLogLog/Count-Min can be valuable for approximate operational analytics/telemetry where exact values are explicitly unnecessary.
- **FIT:** MinHash can be useful for a future similarity/deduplication search workload.
- **CURRENT BOUNDARY:** payment totals, stock quantity, credit balance, authorization, tenant membership, durable quotas, or any exact invariant must continue to use exact authoritative state.
- **CURRENT IMPLEMENTATION:** database-native indexes/data structures remain preferable before custom application structures because no measured SquiFlow workload yet requires these mechanisms.

## Critical questions
1. Which structures in the list are approximate and what kind of error do they allow?
2. Why can a Bloom-filter false positive be safe for a cache-avoidance hint but unsafe for authorization?
3. Why is HyperLogLog unsuitable for exact invoice-count enforcement?
4. What workload is MinHash designed for?
5. Why is SkipList conceptually different from the probabilistic sketches in the same infographic?
6. Which SquiFlow metrics could tolerate approximation and which absolutely cannot?
7. How would you verify that a Bloom-filter optimization never suppresses an authoritative DB check when it matters?
8. **Challenge:** propose one SquiFlow workload where an approximate structure might eventually be valuable, and define the correctness boundary that prevents it from becoming authority.

# 055 — 5 Database Normal Forms Every Developer Should Know

## Identification
- **PDF pages:** `111-112`
- **Original archive pages:** `214-215`
- **Classification:** `KEEP` normalized authority; `LATER` denormalization only as derived/read optimization.

## SOURCE
The article says normalization reduces redundancy and enforces integrity through dependency-driven forms:
1. **1NF** — remove repeating groups and use atomic values.
2. **2NF** — remove partial dependency; non-key attributes depend on the full primary key.
3. **3NF** — eliminate transitive dependency; non-key columns depend on primary keys.
4. **BCNF** — strengthen 3NF by requiring determinants to be candidate keys/uniquely identify rows.
5. **4NF** — avoid mixing independent multi-valued one-to-many relationships in one table.

The visual walks through simplified order/customer/course/employee-skill examples.

## Diagram / visual
The strongest visual lesson is decomposition: one table containing several independent facts is split into tables where each fact has a clearer owner/key dependency.

## INFERENCE
Normalization is primarily about preserving fact identity and avoiding update/insert/delete anomalies. It is not a rule that every query should join the maximum number of tiny tables, nor does it prohibit derived read models.

## EXTERNAL KNOWLEDGE / caveats
- “Atomic value” in 1NF depends on the relational/domain interpretation; it does not mean every concept must be split into arbitrary primitive columns.
- 2NF matters primarily when a candidate key is composite; with a single-column key, partial dependency on part of the key cannot occur.
- The source phrase “non-key columns depend only on primary keys” is a simplification of functional-dependency rules; candidate keys and determinants matter.
- BCNF and 3NF differ in edge cases with overlapping candidate keys/functional dependencies.
- Normalization level should be guided by invariants and update anomalies; performance denormalization is a separate decision with freshness/rebuild cost.

## Implications for the Current Implementation
- **CURRENT FIT:** normalized authoritative SquiFlow relational data is appropriate for real business identities, relationships and constraints because correctness/update integrity matter.
- **COMPLEMENTARY FIT:** denormalized/materialized read structures are also valid when a measured query/read workload benefits; they must declare source, freshness, update/rebuild and tenant/authorization contracts.
- **CURRENT FIT:** bounded dynamic forms/custom attributes may use structured/versioned extensibility, while core invariants remain typed/owned rather than hidden in arbitrary blobs.
- **UNCHANGED:** normalization does not eliminate indexes, query plans, projections, caches, or transactional concurrency design; those mechanisms can coexist.

## Critical questions
1. What anomaly does normalization try to prevent?
2. When does 2NF add no new constraint beyond 1NF for a table with a single-column key?
3. How is a transitive dependency different from a partial dependency?
4. Why can BCNF be stricter than 3NF?
5. What problem does 4NF address that ordinary foreign-key decomposition may miss?
6. Why should normalized authority not be confused with “never denormalize anything”?
7. How can JSON/EAV hide business invariants that should be relational constraints?
8. What must a denormalized read model declare before SquiFlow treats it as safe?
9. **Challenge:** design an authoritative order/customer/product schema and then identify one report projection that could be denormalized without becoming source of truth.

# 056 — How CQRS Works?

## Identification
- **PDF pages:** `113-114`
- **Original archive pages:** `218-219`
- **Classification:** `KEEP` command/query responsibility separation; `AVOID` assuming separate databases/event sourcing are required.

## SOURCE
The article defines CQRS as separating write Commands and read Queries for scalability/maintainability. Its illustrated flow is:
1. client sends a Command to a Command Handler;
2. handler validates/executes through the Domain Model;
3. changes are saved to a Write Database and may also be saved to an Event Store; emitted events update a Read Model asynchronously;
4. projections are stored in a Read Database, described as eventually consistent with the Write Database;
5. queries go to a Query Handler;
6. Query Handler reads precomputed projections from the Read Database and returns results without hitting the write model/database.

## Diagram / visual
The visual presents a **full deployment form of CQRS**: separate command and query paths, separate write/read databases, an event-update path and optional event store.

## INFERENCE
The deeper idea is responsibility separation: mutation handling and read shaping have different constraints and can evolve independently. The source diagram shows one common scaled-out implementation, not the minimum definition.

## EXTERNAL KNOWLEDGE / caveats
- CQRS does **not** require separate databases, separate services, a message broker or Event Sourcing. It can exist as command/query separation inside one modular monolith and one transactional store.
- Event Sourcing and CQRS are related but independent patterns.
- A read model need not always be asynchronously/eventually consistent; implementation can choose synchronous derivation when appropriate.
- Separate read stores introduce projection lag, rebuild, duplicate/out-of-order handling and operational availability concerns.
- Authorization is a first-class issue: a fast precomputed read model cannot be allowed to serve stale or cross-tenant permission-sensitive data.
- Queries are expected not to create business mutations, but ordinary technical effects such as telemetry/cache population may still occur; the semantic contract is “no business state change.”

## Implications for the Current Implementation
- **USED NOW:** SquiFlow already benefits from command/query responsibility separation inside the modular monolith; this gives explicit mutation intent and tailored reads without requiring distributed topology.
- **FIT FOR FUTURE READ PRESSURE:** separate read models/stores/services and asynchronous projections can become valuable when reporting/search/dashboard workload materially benefits from independent scaling or denormalized projections.
- **COMPLEMENTARY:** CQRS may be combined with Event Sourcing in a domain that needs both, but neither requires the other.
- **CURRENT FIT:** one authoritative relational DB remains simpler for the current core because there is no proven need for dual-store projection lag/rebuild operations.
- **UNCHANGED:** any future read model still needs tenant/resource authorization, freshness evidence, duplicate/out-of-order handling and rebuild behavior.

## Critical questions
1. What is the minimum useful meaning of CQRS?
2. Why does command/query separation not require two databases?
3. How is CQRS different from Event Sourcing?
4. What new failure mode appears when the read model is asynchronously projected?
5. How should a client know whether a projection is stale enough to matter?
6. Why can a precomputed read DB be dangerous for permission-sensitive data?
7. Which SquiFlow operations are obvious Commands and which are Queries?
8. When would a separate read model be justified for reporting/search?
9. How would you rebuild a read model without replaying external payment/printing effects?
10. **Challenge:** design `ApproveQuote` and `GetQuoteSummary` using command/query separation inside one modular monolith and one DB; then explain what evidence would justify splitting the read path later.

# 058 — Database Index Types Every Developer Should Know

## Identification
- **PDF pages:** `117-118`
- **Original archive pages:** `226-227`
- **Classification:** `KEEP`; provider-specific semantics must be verified rather than copied literally.

## SOURCE
The article defines a database index as a derived structure mapping column values to row locations and presents:
1. **Primary Index** — said to be automatically created with a primary key and to be dense or sparse; dense has an entry for every row while sparse has entries for some rows.
2. **Clustered Index** — determines physical row order; only one can exist because rows can only have one physical order; useful for range scans and I/O efficiency.
3. **Secondary/Non-clustered Index** — separate structure containing indexed columns plus pointers/keys used to find underlying rows; does not determine physical row storage.

The visual shows dense vs sparse primary indexing, a clustered physical-order example, and a secondary index resolving toward primary/data blocks.

## INFERENCE
The useful concept is that indexes are **derived access paths**, not copies of business truth. Different index organizations trade read efficiency against storage, write amplification, maintenance and physical locality.

## EXTERNAL KNOWLEDGE / important caveats
Index terminology is highly DBMS-specific:
- A primary-key constraint commonly creates a unique index, but whether that index controls physical clustering depends on the engine.
- PostgreSQL does not maintain a SQL-Server/InnoDB-style permanently clustered table order from its primary key; `CLUSTER` is a separate operation and later writes can disturb that order.
- InnoDB commonly clusters table data around the primary key; SQL Server has its own clustered/nonclustered semantics.
- “Sparse index is preferred in most scenarios” is too broad; sparse indexing only applies naturally to certain storage organizations and workload assumptions.
- Modern providers also expose composite, unique, partial/filtered, covering/include, expression/function, hash, GiST/GIN/BRIN and other index types/structures.
- More indexes increase write/WAL/storage/vacuum/maintenance/migration cost and can worsen cache pressure.

## Implications for the Current Implementation
- **KEEP:** index design is provider/workload-specific and closes through actual execution plans.
- **KEEP:** primary/unique indexes are driven by real identities/invariants; performance indexes are driven by measured hot queries.
- **KEEP:** tenant-scoped query patterns must be reflected in index ordering/selectivity where the chosen DB benefits from it.
- **AVOID:** assuming “primary key = physically clustered” before the provider is selected/proven.
- **KEEP:** measure index write/WAL/storage/migration cost during reconnect/import bursts, not only read latency.
- **LATER:** partial/covering/specialized indexes may be excellent after actual Phase-3 query shapes are known.
- No new owner-document change required.

## Critical questions
1. Why is an index derived rather than authoritative business state?
2. What is the practical difference between clustered and secondary access paths?
3. Why does “primary key” not imply the same physical storage behavior across all DBMSs?
4. When can a composite index support a tenant-scoped query better than separate single-column indexes?
5. What write costs does every additional index introduce?
6. How can a low-selectivity index be useless or harmful?
7. Why might a covering index improve reads but increase storage/write cost?
8. Which indexes should protect uniqueness/invariants versus only performance?
9. How would you test index usefulness under one very large tenant and many small tenants?
10. **Challenge:** design the evidence needed before adding an index for `(TenantId, CustomerId, CreatedAt)` and explain how column order would depend on query predicates/sort patterns.

# 059 — Top 5 common ways to improve API performance

## Identification
- **PDF pages:** `119-120`
- **Original archive pages:** `232-233`
- **Duplicate group:** `ARCH-DUP-02`; earlier occurrence `016` completed independently.
- **Classification:** `KEEP / NEEDS MEASUREMENT`; duplicate occurrence adds no new infrastructure decision.

## SOURCE
The same five techniques are presented:
- result pagination;
- asynchronous logging through a buffer with periodic flush;
- data caching, with Redis as an example;
- request/response payload compression such as gzip;
- database connection pooling.

The visual labels these five performance levers and shows a cache-aside-style flow plus a connection pool.

## Duplicate-occurrence audit
This occurrence's own pages and visual were inspected. Its content materially matches archive occurrence `016`; it remains a separate completed ledger row rather than being auto-completed from the earlier duplicate.

## INFERENCE
All five techniques trade one resource for another. None is “free performance”:
- pagination adds navigation/consistency contract;
- async logging adds buffering/loss/backpressure behavior;
- cache adds invalidation/staleness/cold-start behavior;
- compression trades CPU for bandwidth;
- pooling trades connection-open cost for bounded shared capacity and queueing.

## EXTERNAL KNOWLEDGE / caveats
- Pagination is not the same as streaming a response. It is usually multiple bounded requests/pages with a continuation contract.
- Asynchronous logging can lose buffered telemetry on process failure unless the durability requirement says otherwise; authoritative audit cannot exist only in a lossy buffer.
- Redis is not required for caching; in-process/edge/provider caches may be more appropriate depending on scope.
- Compression can hurt tiny payloads or CPU-bound systems and needs BREACH/secret-reflection awareness in some security-sensitive contexts.
- Oversized DB pools can overwhelm a database rather than improve throughput.

## Implications for the Current Implementation

# 060 — REST API Vs. GraphQL

## Identification
- **PDF pages:** `121-122`
- **Original archive pages:** `234-235`
- **Classification:** `FIT BY SURFACE`; REST/task HTTP and GraphQL are complementary candidates rather than a project-wide winner/loser decision.

## SOURCE
The article compares:

**REST**
- standard HTTP methods such as GET/POST/PUT/DELETE for CRUD;
- simple/uniform interface between applications/services;
- straightforward caching;
- may require multiple round trips to assemble related data from separate endpoints.

**GraphQL**
- one endpoint where clients request exact fields/nested data;
- returns a payload shaped to the requested fields;
- supports Mutations and Subscriptions;
- useful for aggregating multiple sources and rapidly evolving frontend needs;
- can permit abusive/expensive queries if not safeguarded;
- caching can be more complicated.

The visual contrasts multiple REST calls to User/Order services with one GraphQL query resolving nested user/order fields.

## INFERENCE
The real trade-off is not “REST old, GraphQL new” or “REST wins because it is simpler.” REST favors explicit server-owned resources/commands and familiar HTTP semantics. GraphQL favors client-driven read composition and can materially improve nested/variable UI reads, while requiring the server to own query planning, authorization, cost control and schema governance.

## EXTERNAL KNOWLEDGE / caveats
- GraphQL often shifts significant complexity to the **server as well as the client**: resolver design, field/resource authorization, N+1 avoidance, DataLoader/batching, query depth/complexity, persisted queries, introspection policy and schema deprecation.
- REST does not inherently require many network round trips; composite/task endpoints, embedded resources, BFFs or tailored projections can solve some composition needs.
- GraphQL's “single endpoint” does not mean one backend call; the server may fan out to many stores/services and needs deadline/backpressure/partial-error policy.
- Field-level authorization can be difficult when nested results span tenant/resource boundaries.
- GraphQL Subscriptions are a live delivery mechanism; they should not become durable business truth. Reconnect still needs durable state/status.
- Caching is possible in GraphQL but differs from ordinary URL/resource HTTP caching and often needs normalized client caches/persisted-query strategies.

## Implications for the Current Implementation

### Where REST/task-oriented HTTP is a strong SquiFlow fit
- explicit business commands such as approval/refund/publication/reconciliation where server-owned intent is valuable;
- ordinary resource/file/status operations with bounded shapes;
- surfaces that benefit from conventional HTTP status, conditional/idempotency/cache semantics;
- external/partner APIs where HTTP/OpenAPI familiarity and predictable contracts are useful.

### Where GraphQL may be a stronger SquiFlow fit
- tenant Web dashboard/overview reads spanning customer/order/quotation/payment/inventory summaries;
- Platform Admin read dashboards combining several operational/control-plane views;
- configurable or rapidly evolving read-heavy UI screens where client-selected fields/nested composition materially reduce over-fetch, under-fetch, or repeated bespoke REST aggregation endpoints.

### Complementary architecture
- GraphQL does not need to replace REST/task HTTP if it is introduced.
- Material commands can remain explicit task-oriented HTTP while read-heavy UI composition uses GraphQL.
- gRPC remains a separate candidate for Workstation sync/high-frequency typed RPC.
- SignalR/WebSocket-style channels remain suitable for live UI signaling.
- outbox/Worker remains the durable path for long-running/after-commit consequences.

### GraphQL adoption gate if a real read surface appears
- tenant/resource/field authorization;
- query depth/complexity/cost/time/result-size limits;
- batching/N+1 strategy;
- schema/deprecation ownership;
- cache/freshness contract;
- persisted-query/introspection policy appropriate to the audience;
- observability that exposes resolver/query cost and DB amplification;
- representative comparison against a tailored REST/query endpoint for the same UI.

### What remains unchanged
GraphQL would not replace semantic idempotency, expected-version concurrency, TenantContext, OpenFGA, durable Workstation sync correctness, DB/domain authority, or durable async work semantics.

**Current status:** REST/task HTTP is used/planned where its explicit command/resource properties already fit. GraphQL is a **positive candidate for specific read-composition surfaces**, not a globally deferred/rejected technology. No GraphQL implementation commitment is made from the comparison article alone.

## Critical questions
1. Which problem does GraphQL solve better than ordinary fixed REST resources?
2. Why can GraphQL reduce client round trips while increasing server-side work?
3. What is the GraphQL N+1 problem?
4. How do query-depth and cost limits protect a GraphQL server?
5. Why is field-level authorization harder than one endpoint-level permission check?
6. How can REST provide a tailored aggregate view without becoming GraphQL?
7. Why are GraphQL Subscriptions not durable business delivery?
8. What cache keys/freshness concerns arise when clients choose arbitrary field sets?
9. Which concrete SquiFlow Web/Admin read surface would benefit enough from GraphQL to justify its query-governance cost?
10. **Challenge:** a tenant can query `customer { orders { payments { ... } } }`. Design the authorization/cost boundaries needed to prevent cross-tenant leakage and unbounded database work.
