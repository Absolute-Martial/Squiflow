## Proposed first case

Use one already committed program-attributed Order with exactly one catalog-priced, in-house, non-stock service line whose quantity is measured in that line's existing unit code. Record actual work completion and in-person customer pickup as separate facts. This candidate requires no quotation, artwork, upload, customer artwork approval, supplier, stock movement, deposit/payment prerequisite, invoice/document, external notification, or client portal. None of those exclusions claims they are unnecessary in other cases.

This narrows the first case to a measurable service with an operator-recorded pickup. It does not claim that a real customer has been interviewed or that this is the product's observed first journey. Product Foundation still owns the exact actors, start/end condition, manual steps and customer evidence. Commitment already freezes the priced line and customer/program attribution; fulfillment and pickup must not edit or reinterpret them.

## Proposed facts and transitions

| Concern | Proposed rule for owner review |
|---|---|
| Quantity and unit | Reuse the committed catalog line's stable `UnitId`, retained unit code and precision; introduce no conversion. Completion and pickup quantities must be positive, exact, within the remaining eligible amount, and within that retained unit precision (at most four decimal places). Reject zero, excess, negative input and rounding. The proposal's tolerance is zero. At first start, verify and retain the catalog item's non-stock classification through the owning public Catalog boundary; later catalog changes do not reinterpret work already started. |
| Actual work | Append operator-recorded good-completion quantities. `work completed` means good completed quantity equals the committed quantity and no unresolved stopped, disputed or defective disposition blocks it. Completion never changes Order price, line quantity, attribution or commitment revision. |
| Pickup | Append separately recorded pickup quantities, each no greater than currently good, pickup-eligible completed quantity not already handed off. Partial work and partial pickup remain independently visible; completing work does not imply pickup, and pickup does not imply invoice, payment, acceptance or settlement. |
| Stopped / disputed / defective | Keep a durable, actionable whole-line blocking disposition with a required reason and optional affected quantity bounded by the ordered quantity. It does not itself add or remove completion/pickup quantities. While unresolved, further completion and pickup are denied and the work cannot be described as complete. Resolution is a separate attributable event with a required reason describing the resolution; it does not manufacture completed quantity. Previously recorded physical handoffs remain historical facts. No timer or scheduler resolves these dispositions. |
| Stage guidance | An explicit start event records actor/server time. Derive `not-started`, `in-progress`, `paused`, `ready-for-pickup`, or `handed-off` from start, current blocking disposition and net quantities. An unresolved disposition takes precedence. A stage label never creates completion, pickup, stock or financial effects; a general tenant workflow runtime remains out of scope. |
| Pickup evidence | Record server UTC time, actor account, quantity/unit, and a required recipient label of 1–128 Unicode scalar values. Evidence is explicitly `operator-recorded`; no customer signature, identity-document number, photo or legal delivery proof is claimed. Do not expose recipient text or reasons in ordinary diagnostics or inbox summaries. |
| Reasons | Require an outer-trimmed reason of 1–512 Unicode scalar values for stopped, disputed, defective and correction events; reject malformed UTF-16 and control characters. Preserve the reason in protected business history, not logs. |

Apply the same malformed-text/control checks before trimming recipient labels. Command bodies are bounded at 8 KiB; progress inbox pages at 50 items and protected history pages at 10. Recipient labels and reasons appear only in protected detail/history.

Actual completion and pickup are immutable events. A current summary is derived from those events and their valid corrections, not from a manually editable `fulfilled` Boolean. A proposed fulfillment revision advances for every accepted work, disposition, pickup or correction command; it is independent of the frozen Order revision. Only the explicit quantity rules above can advance the completion/handoff totals.

## Proposed authority, concurrency and correction

Propose independent delegated permissions `orders.fulfillment.view`, `orders.fulfillment.work.record`, `orders.fulfillment.handoff.record`, and `orders.fulfillment.correct`. No Owner title grants these permissions automatically; there is no implicit Own/Assigned scope. Every command and replay checks current active tenant membership and its current permission. Work/handoff reads disclose only the minimum committed line identity, quantity/unit and actual progress; priced Order detail remains behind existing `orders.view` authority.

Each command names the tenant Order, expected fulfillment revision, and caller-scoped idempotency key. The same key and same intent replays the retained result; changed intent conflicts. Concurrent commands serialize against the fulfillment revision, with one winner and a stale-revision result for a loser. Tenant-scoped foreign keys and RLS protect every retained event and query. An Order must be committed before a fulfillment record can start; the Order's committed facts stay immutable.

Entry mistakes use a separate `orders.fulfillment.correct` right **and** a current initial Owner with recent trusted Tenant Web strong authentication. The correction command also requires the expected fulfillment revision, target event and bounded reason. Originals are never edited or deleted: append a linked void/correction event, and where needed a replacement fact. A void is allowed only for an entry that did not occur in reality and only when dependent facts remain valid. Net good completion must stay within `0..ordered quantity`; net handoff must stay within `0..net good completion`. Correction cannot imply that picked-up goods physically returned, undo frozen financial facts, create a customer return, or claim a legal/payment remedy. Those outcomes require their own future contracts.

## Acceptance and receiving obligations

The owner accepted this single case and its quantity scale/tolerance, unit identity, completion-versus-pickup distinction, disposition behavior, recipient/reason limits, permission IDs, and initial-Owner correction/step-up rule. Implementation must add native PostgreSQL evidence for partial and zero/excess quantities, split pickup, two-actor revision races, idempotent replay, tenant isolation, stopped/disputed/defective recovery, and correction rollback/replay. CoreApi/OpenFGA tests must prove current membership, explicit permissions and step-up. Qualification must remain pending until the exact normal repository gate and focused host checks pass on the integrated source.

The initial authorization prerequisite and first service fulfillment/pickup scope are locally qualified under the receiving receipt; returns and broader customer evidence remain absent. This proposal does not close the wider open choices around other service/product types, multiple Order lines, artwork, outsourced work, stock, deadlines, delivery, recipient proof, returns, invoice timing or payment. It does not change product version `v0.0.1` or expand COM-012/013.
