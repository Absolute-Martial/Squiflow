# COM-020 gap review — 2026-10-10

## Scope and disposition

This read-only review compared the current host-neutral invoice issue application and its focused tests with the five recommendations in [the COM-019–021 proposal](COM_019_021_DECISION_PROPOSAL.md). No confirmed defect was found in COM-020's deliberately partial, provider-neutral scope. The five differences below depend on owner choices that remain unaccepted; they are not defects in the current partial implementation. No source, test, or owner-contract files were changed for this review.

COM-019 remains `DECISION_REQUIRED`. There is no invoice persistence adapter or live issue-authority implementation in this scope. This review does not qualify durable issuance, live OpenFGA/API authority, or the repository gate.

## Current authority and replay behavior

`IssueInvoice.ExecuteAsync` checks its `IInvoiceIssueAuthority` port before looking up an idempotency receipt, and returns an exact receipt before querying mutable Order or Customer facts ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L327-L398)). The request fingerprint includes Order identity, expected revision, and debtor selection ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L561-L587)). The focused tests cover authority denial before receipt disclosure, exact replay after source/customer changes without rereads, and same-key changed-debtor conflict ([InvoiceIssueTests.cs](../../tests/unit/Application.Invoices.Tests/InvoiceIssueTests.cs#L298-L414)).

This proves host-neutral orchestration against ports and an in-memory store. It does not prove that a production authority port checks current membership and billing permission, or that a durable store scopes receipts and commits invoice facts atomically. Those remain separate COM-021/022 work and evidence.

## Deltas if the owner accepts the proposal

1. **One full invoice per committed Order.** The application checks committed state and exact revision, then calls `CommitAsync`; its port has no already-issued-for-Order outcome ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L348-L398)). The test store scopes receipts by tenant/account/key, so it allows another key to issue the same Order ([InvoiceIssueTests.cs](../../tests/unit/Application.Invoices.Tests/InvoiceIssueTests.cs#L607-L667)). If accepted, add a stable allocation-conflict result and enforce one issue per tenant/Order atomically in COM-021. Test a second key and concurrent attempts against PostgreSQL.

2. **Organization anchor and reference scope.** `SourceCustomerContext` is optional in both candidate and retained facts. Individual debtor selection does not require it ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L175-L209), [InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L481-L505)); the active-individual test issues an unattributed Order ([InvoiceIssueTests.cs](../../tests/unit/Application.Invoices.Tests/InvoiceIssueTests.cs#L174-L199)). If accepted, require frozen organization attribution for every debtor selection, reject unattributed Orders, and retain the organization used as reference anchor separately from debtor identity. Cover organization, program, individual, and unattributed cases.

3. **Per-organization ordinal and gap behavior.** Retained facts have a tenant invoice GUID and a nonblank `BusinessReference`, but no explicit organization anchor or numeric ordinal ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L66-L83), [InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L160-L172)). The test store's global counter and `ORG-TEST-*` string are illustrative only ([InvoiceIssueTests.cs](../../tests/unit/Application.Invoices.Tests/InvoiceIssueTests.cs#L607-L667)). If accepted, retain the organization ordinal distinctly from the tenant invoice GUID and prove per-organization uniqueness, retry stability, concurrency, and permitted gaps in PostgreSQL.

4. **UTC-derived business date, with no caller date.** `IssueInvoiceRequest` has no date input, and the store port owns the authoritative issue instant/date ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L24-L28), [InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L280-L299)). `InvoiceIssuedFacts` validates a UTC timestamp and nondefault date independently; committed-result validation does not require the date to equal the UTC date ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L98-L110), [InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L768-L786)). If accepted, derive the date from the issue transaction's authoritative UTC instant and validate it. Test the UTC-midnight boundary, absence of caller backdating/future dating, and unchanged replay.

5. **Active-only individual selection.** Active individuals can issue; inactive individuals currently return `ContractDecisionRequired` ([InvoiceIssue.cs](../../modules/invoices/Application.Invoices/InvoiceIssue.cs#L481-L505)). Both paths have focused tests ([InvoiceIssueTests.cs](../../tests/unit/Application.Invoices.Tests/InvoiceIssueTests.cs#L117-L199)). The proposed rule would replace the unresolved-decision outcome with a stable rejection for a new issue. If accepted, update that outcome and test that no candidate is committed; also prove a prior issued snapshot can still replay after the current record becomes inactive.
