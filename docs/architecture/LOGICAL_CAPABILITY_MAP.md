# Logical Capability Map

**Status:** Planning and ownership map, not a feature catalog, project list, delivery commitment, or implementation claim.

**Authority boundary:** This document groups candidate responsibilities and routes them to focused owners. `README.IMPLEMENTATION.md` owns current executable truth; focused domain, security, sync, workstation, operations, and admin documents own behavior. A name here does not create a module, assembly, service, database, API, or tenant-selectable feature.

## Reading the map

The proposed names are useful discovery prompts. A logical capability earns a stable boundary only when it owns distinct meaning, authority, lifecycle, invariants, or change pressure. Foundation primitives, business capabilities, provider adapters, host processes, and operational functions are different kinds of responsibility. A tenant-selected feature is yet another concept. Do not assign all of them the same module shape or create a project per name. Use `docs/architecture/REPOSITORY_STRUCTURE.md` for physical boundaries and `docs/architecture/AUTHORITATIVE_CAPABILITY_MODULES.md` for business ownership across hosts.

For material **active** responsibility the gate states remain `NOT_INTRODUCED`, `PRODUCTION_HONEST`, or `BLOCKED`. Candidate names below are `NOT_INTRODUCED` unless the narrow current implementation scope is explicitly listed here or in `README.IMPLEMENTATION.md`. `BLOCKED = none` for the current declared implementation.

## Current narrow implementation

| Logical owner | `PRODUCTION_HONEST` scope | Outside that scope (`NOT_INTRODUCED`) |
|---|---|---|
| Application Profiles | Bounded shipped-feature graph validation and deterministic effective-selection compilation | Production catalog, durable tenant profile authority, publication and production profile resolution |
| Branding | Deployment-wide public brand validation and bootstrap response | Tenant-specific branding |
| Identity Access | Exact OIDC identity-to-account binding, validated-token account resolution | Login/session flows, provisioning and user administration |
| Tenancy | Active membership listing and membership-derived tenant context | Tenant provisioning and tenant administration |
| Customers | Immutable tenant-owned customer organizations and child programs with bounded create/read/browse, caller-scoped idempotency and isolated PostgreSQL persistence | Legal debtor/account, contact/address, credit and customer administration lifecycle |
| Access control at CoreApi | Pinned-model OpenFGA checks for tenant workspace, Customers and Orders after current membership, with fail-closed provider behavior and distinct customer organization/program create/view plus order create/view/abandon relations | Owner/Staff and custom-role administration, tuple lifecycle and reconciliation, general permission catalog |
| Orders | Immutable priced draft create/read/browse and one-way abandon, caller-scoped semantic idempotency, optional organization/program attribution, and tenant-isolated PostgreSQL persistence. Abandon requires expected revision, records abandoning account/timestamp, advances revision, and preserves priced content plus the original create receipt. | Draft editing/deletion, submission, fulfillment, cancellation, returns, invoice/payment and the broader order lifecycle |

CoreApi and DbMigrator are executable hosts, not additional business capabilities. Their exact current routes and migration claims are in `README.IMPLEMENTATION.md`. A general Foundation or Application Kernel project, Workstation, Guard, SyncApi, Worker, AdminApi and Web UI are `NOT_INTRODUCED`.

## Responsibilities the proposed list does not name clearly

The current architecture also calls out **Branding**, **Tenant Application Profile authority/publication**, **tenant-selectable forms and typed supplementary information**, **resource-consumption accounting and hard limits**, **semantic idempotency and authoritative reconciliation**, **object-byte storage and recovery**, and **client-customer portal authority**. They should be visible during journey design but do not automatically earn separate modules. The business model additionally describes **commercial relationship/account and contacts**, **fulfillment/outsourced production**, **returns/refunds**, and **receivables/payables** where a real journey requires them. Product discovery and domain language must settle the boundaries before code or stable public identifiers are introduced. Owners: `docs/product/PRODUCT_FOUNDATION.md`, `docs/domain/BUSINESS_MODEL.md`, `docs/requirements/RESOURCE_CONSUMPTION_AND_LIMITS.md`, and the focused architecture/security owner for each responsibility.

Revisit this map when a useful journey introduces a responsibility, when two proposed names prove to own the same business meaning, or when a real authority/provider/process boundary requires a different split. Update the focused owner and current implementation record with that change; this map alone does not qualify a gate.
