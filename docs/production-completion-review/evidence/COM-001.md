## Current commercial operations that already exist

### Customers

The current Customers capability owns:

- tenant-owned organization create/read/browse;
- organization child-program create/read/browse;
- individual customer billing-record create/read;
- individual active/inactive availability transition with expected revision and
  caller-scoped semantic idempotency.

`CustomerIndividualSnapshot` retains display name, optional email, optional phone,
availability, revision, creation actor/time and optional availability-change
actor/time. `Application.Customers` references Tenancy only; it has no IdentityAccess,
Invoice or debtor-authority dependency. The record is therefore a customer/person
billing record, not a sign-in account and not debtor assignment by itself.

Permanent evidence already named by the focused owner includes:

- `CustomerIndividualTests`;
- `CustomerIndividualPostgresTests`, especially
  `IndividualCreateReplayAndAvailabilityRetainOriginalFacts`,
  `IndividualAvailabilityIsRevisionCheckedAndTenantIsolated`,
  `IndividualRowsAndReceiptsRequireTenantContextAndRuntimeCannotEditIdentity`, and
  `UncommittedIndividualCreateAndReceiptRollBackTogether`;
- `CustomerIndividualEndpointTests`, especially
  `CreateReadAvailabilityAndRetriesPreserveHistoricalResultsAndIndependentPermissions`.

### Orders and pricing

The current Orders capability owns priced draft create/read/browse, non-persisting
price preview, full priced draft replacement, abandon, direct commitment, action
guidance and retained command history.

`EndpointAccess` binds current authority as follows:

- create: `CreateOrderRequirement` **and** `ApplyManualPriceRequirement`;
- price preview: `CreateOrderRequirement` **and** `ApplyManualPriceRequirement`;
- full replacement/revision: `EditOrderRequirement` **and**
  `ApplyManualPriceRequirement`;
- commit: independent `CommitOrderRequirement`;
- read/history/action guidance: view authority; abandonment: independent abandon
  authority.

The CoreApi application-authorization middleware resolves the current account and
current active membership before executing these declared requirements. Handler
code therefore cannot access a command receipt first and use replay to bypass a
revoked current permission. The same current requirement set protects retries.

Current regression anchors include:

- `TenantOrderEndpointTests.CurrentMemberWithCreateAndPricingPermissionsCanCreateAnOrderDraft`;
- `OrderPricePreviewTests.PreviewNeedsNoIdempotencyKeyAndAgreesWithCreationWithoutSavingAnOrder`;
- `OpenFgaTenantAuthorizationTests.RealServerRequiresPersistedOrderPermissionsAndUsesPinnedModel`;
- existing revise/replay endpoint tests under `Application.CoreApi.Tests`;
- PostgreSQL command/replay/concurrency cases in `OrderMigrationAndRlsTests`.

### Direct commitment freezes the priced order; it does not perform finance or fulfillment

`CommitOrderDraft` fingerprints only the order identity + expected revision and
passes the request to the order store. PostgreSQL `TryCommitOrder.sql` changes only
state, revision, `committed_at` and `committed_by_account_id`. It does not rewrite
summary, currency, lines, prices, total or customer/program attribution.

`202610030001_OrderCommitment` adds a trigger that rejects terminal rewrites and
rejects a draft-to-committed transition if the protected priced/attribution facts
change. Restrictive line policies permit mutation only while the parent is still a
draft. `PostgresOrderDraftStore.CommitAsync` performs the conditional state change,
reads the resulting snapshot and inserts the version-three commitment receipt in
the same tenant transaction.

The strongest existing regression names are:

- `OrderCommitmentPostgresTests.CommitmentFreezesAttributedFactsAndRetainsAnAtomicHistoricalReceipt`;
- `RuntimeCannotRewriteCommittedFactsOrInsertAdditionalLines`;
- `ReceiptFailureRollsBackCommitmentBeforeRetryCanSucceed`;
- `ConcurrentCommitCommandsProduceOnlyOneEffect`;
- `OrderCommitEndpointTests.CommitmentUsesExistingFactsAndClosesDraftActionsWithoutFinancialEffects`.

There is no CoreApi invoice endpoint and neither Orders nor Customers references
`Application.Invoices`. The Invoices project has no PostgreSQL adapter/migration.
Therefore direct order commitment currently creates **no invoice, fulfillment,
stock reservation, receivable, payment or settlement effect**.

## Arithmetic and historical compatibility that later commercial work must preserve

Current order-entry arithmetic uses decimal precision/scale `19,4`; line totals are
rounded to four decimal places with `MidpointRounding.ToEven` before the rounded
lines are summed. Preview and create share the same pricing implementation. Invoice
issue validates the same committed-order arithmetic rather than selecting a new
price.

Orders receipt compatibility is deliberately versioned:

- historical pre-envelope receipts remain readable for non-commit operations;
- schema version 1 represents legacy draft facts;
- schema version 2 retains customer attribution facts;
- schema version 3 is required for commitment;
- partial/unknown/mismatched envelopes fail closed.

`PostgresOrderDraftStore.History` reads retained receipt snapshots, validates
revision continuity and validates terminal actor/timestamp facts rather than
reconstructing historical prices from current state.

Existing real-PostgreSQL regressions include:

- `PersistedLegacyReceiptsReplayAlongsideVersionedCreateAndAbandonReceipts`;
- `UnsupportedOrMismatchedReceiptEnvelopesFailClosed`;
- `RevisionReplacesPricedContentAndReplaysItsCommittedSnapshot`;
- commitment-history regressions in `OrderCommitmentPostgresTests`.

## Tenant/database preservation boundary

Orders and Customers adapters use explicit tenant predicates plus transaction-local
`app.current_tenant` state and forced PostgreSQL RLS. Runtime SQL is adapter-owned
embedded SQL. Current integration regressions cover wrong-tenant access, RLS WITH
CHECK behavior, transaction-local tenant reset and restricted runtime privileges.

Examples include:

- `OrderMigrationAndRlsTests.DatabaseRejectsForeignTenantAndWrongOrganizationProgramAttribution`;
- `RuntimeRoleCanOnlyCreateAndReadTheTransactionTenant`;
- `RuntimeRoleRlsWithCheckRejectsMissingAndWrongTenantInsertsForEveryOrderTable`;
- `TransactionLocalTenantContextDoesNotLeakFromAOneConnectionPoolAfterCommitOrRollback`;
- analogous individual-customer RLS/tenant tests in `CustomerIndividualPostgresTests`.

Later commercial work must not replace these database guarantees with host-only
tenant filtering.

## Incoming Invoices work: present, deliberately partial

`Application.Invoices/InvoiceIssue.cs` is present and must **not** be recreated.
Its host-neutral orchestration currently provides:

- current billing-authority port check before receipt disclosure;
- caller-scoped semantic replay/idempotency flow;
- committed Order + exact expected-revision + NPR eligibility checks;
- decimal `19,4` and `ToEven` committed-fact verification;
- organization/program/individual debtor resolution through current Customers
  queries;
- immutable issued-line/debtor fact contracts and defensive line copying;
- explicit safe outcomes for current invalid/ineligible cases;
- fail-closed handling for unsupported individual availability.

The focused suite `Application.Invoices.Tests/InvoiceIssueTests.cs` includes valid
organization issuance, mismatched program/organization rejection, missing/unknown
individual handling, inactive-individual decision blocking, arithmetic bounds,
replay without rereading changed Order/Customer state, authority-before-replay,
idempotency conflicts and immutable retained facts.

This is **not** durable invoicing. There is no invoice PostgreSQL project,
migration, numbering/reference allocator, HTTP endpoint, OpenFGA adapter, PDF,
receivable or payment effect.

## Security/static review findings

No new commercial security defect was demonstrated by this inventory. Current
source preserves these important sequencing properties:

- current authenticated account + active membership are resolved before tenant
  resource authorization;
- create/preview/revise require the distinct manual-pricing permission in addition
  to create/edit authority;
- command replay remains behind current authorization rather than acting as an
  authorization bypass;
- tenant-safe not-found behavior and explicit tenant/RLS predicates remain in the
  current persistence paths;
- Customers individual identity is not coupled to login/account identity;
- invoice issue rechecks current billing authority before returning an existing
  receipt.

This static review does not make live-provider, concurrency or PostgreSQL evidence
fresh.
